* Context: one meal beside a fortnight

GhanaLSS 1987-88 and 1988-89 =food_acquired= serve, on the
=s='produced'= side, =Y12B.VFOODCPD= -- the answer to 12B q5, "How
much would it cost to buy the amount they ate each time?" -- as the
row's =Expenditure=.  The =s='purchased'= side serves =Y12A.CFOODBLV=,
"How much have they spent since my visit?", a bounded recall of about
a fortnight.  Nothing in the frame distinguishes the two: same table,
same columns, same =visit = 1=, same =u = 'Value'=.  A user pooling the
two sides, or pooling these waves with 2016-17's six five-day recalls,
is comparing one eating occasion with thirty days and cannot know it.

The instrument never asked a "since my last visit" question in 12B.
It asked the number of months in the past twelve the item was eaten
(=MFOODCLY=), how many times per day/week/month/quarter/half-year/year
(=TFOODC=, =UTFOODC=), and the value of one occasion (=VFOODCPD=).  GSS
itself annualised those into =EXPEND.HPFOOD=; the product
=VFOODCPD x TFOODC x (30.4 / days_per_unit) x MFOODCLY= reproduces
=HPFOOD= with median ratio 1.02 in both rounds.  Any commensurable
number the library serves for these rows is therefore a
/construction/ from four raw answers under a stated assumption, not a
survey answer.

That is the general shape, and it is not rare.  Known instances before
the census (each with its disclosure today):

| derivation                                                    | disclosed by                          |
|---------------------------------------------------------------+---------------------------------------|
| food kg factors by price-ratio inference (GH #850)            | per-row =KgFactorSource= + =attrs=    |
| EHCVM =MonthsSpent=: binary =s01q12= Oui -> 12, Non -> 0      | CLAUDE.md prose                       |
| GhanaLSS 2005-06 merged-=j= farmgate =Price= = qty-weighted mean | script comment                     |
| Uganda 2015-16 =a5aq8= / 100 guard (GH #829)                  | script + CONTENTS.org                 |
| =age_handler= DOB-derived fractional =Age=                    | CLAUDE.md gotcha                      |
| =u = 'Value'=: =Quantity := Expenditure=                      | an index convention (visible)         |
| GhanaLSS 1987-89 =VFOODCPD= as a recall value                 | nothing (defect, 2026-09-11)          |

Only the first is discoverable from the frame; the sixth is
discoverable because it changed the vocabulary; the rest are knowable
only by reading prose.

* The precept, and the two ways of failing it

The project's precept is to respect the information in the original
survey.  Two obvious responses both fail it:

- Serve the raw answer and document the window in prose :: the
  documentation-only option.  The frame still says =Expenditure=; the
  prose is read by nobody at the moment of pooling.  This is the #323
  failure mode -- "a warning nobody reads" -- in a different costume,
  and it is the state the 1980s waves have been in.
- Serve the constructed number silently :: what the kg inference did
  before #850.  Commensurable, and indistinguishable from a survey
  answer.

The precept is satisfied only if all of the following hold:

1. the raw answers are retrievable exactly, by their original names,
   at the served grain;
2. the served row is labelled derived, in a way that survives
   concatenation, caching and =Feature()=;
3. the derivation is a named, tested, reproducible function whose
   assumptions are stated with their evidence, not arithmetic buried in
   a wave script;
4. there is exactly ONE construction per parquet.  A derivation
   function takes no options: the cache is content-addressed and a
   cached parquet must be one identifiable construction, not one of
   several (decided 2026-09-11).  A user who wants the value under a
   different assumption re-derives it from the raw inputs (1), which
   is what (1) is for.

* Mechanism

Three carriers, because no single one does all three jobs.

** Which derivations get a key

The column is a signal only if it is rare.  Rule: a derivation that
is ALREADY visible in the frame is exempt -- an index value
(=u = 'Value'=, which says in the vocabulary that =Quantity= is a
currency amount) or a per-row source column of its own
(=KgFactorSource= on the kg factors).  The key is for derivations that
are otherwise invisible: a served column whose number is a
construction the frame does not announce.  Whether the kg inference
should migrate onto the mechanism or keep its own column is deferred
to the census; the two must not both fire on one row.

** The =Derivation= column (row-level prominence)

A nullable string column on the served table.  =NA= on a reported
row; on a derived row, the registry key of the derivation
(=GhanaLSS::food_acquired::12b-fortnight=).  Where two derivations touch one row the
keys are joined with =+= in sorted order.

- Why a column and not =attrs= :: =attrs= survive an operation only
  when every input agrees, so =Feature()='s concat drops them (see
  CLAUDE.md, "attrs survive ... only when every input agrees").  A
  column rides through concat, groupby, cache and parquet.
- Why a column and not an index value :: =u = 'Value'= shows an index
  value is the MOST prominent carrier, because it changes the
  vocabulary.  But =s= means source-of-acquisition and =u= means unit;
  an =s = 'produced-derived'= would silently drop those rows from
  every =s == 'produced'= selection, which is the mirror image of the
  trap being fixed.  The grain is the grain.
- Declared =optional: true= under =Columns= in the canonical
  =data_info.yml= for each table that can carry it, with one shared
  note.  A country with no derivations never emits it and
  =Feature()='s concat fills =NA=.
- Cost :: one nullable string column, =NA= on the vast majority of
  rows; pyarrow stores it as a dictionary.  Adding it to a wave's
  parquet moves that wave's cache hash -- the same waves whose script
  changes to stamp it.
- Trap :: =_SCHEME_NON_COLUMN_KEYS= (=country.py=) is
  ={index, materialize, backend, aggregation}=, so a =derivation:= key
  in a =data_scheme.yml= table entry would be read as a required
  column.  The registry lives in its own file (next), never in the
  scheme.

** The registry (the derivation as a named, evidenced object)

=countries/<C>/_/derivations.yml=, a sibling of =population.yml= and
=recall.yml= (a new =.yml= sibling moves no cache hash; a block in
=data_scheme.yml= would cold-rebuild the corpus).  One entry per key:

#+begin_example
GhanaLSS::food_acquired::12b-fortnight:
  waves: ['1987-88', '1988-89']
  columns: [Expenditure, Quantity]
  rows: {s: produced}                       # which rows carry the key
  rule: >-
    Expenditure = VFOODCPD * TFOODC * (14 / days_per_unit[UTFOODC]) * MFOODCLY / 12;
    Quantity = Expenditure (u = 'Value')
  function: lsms_library.countries.GhanaLSS._.ghanalss:derive_12b_fortnight_value
  inputs:   lsms_library.countries.GhanaLSS._.ghanalss:inputs_12b
  raw_variables: [Y12B.MFOODCLY, Y12B.TFOODC, Y12B.UTFOODC, Y12B.VFOODCPD]
  assumptions:
    - text: the window is the nominal fortnight of 12A ("in theory this period is two weeks")
      basis: questionnaire
      evidence: 1988-89 Interviewer manual printed p.70
    - text: the interview fortnight is a random draw from the year (factor MFOODCLY/12)
      basis: modelling-choice
      evidence: SkunkWorks/derived_values.org, "First instance"
  validated_against: EXPEND.HPFOOD (GSS annual construction), median ratio 1.02
  contents: GhanaLSS/_/CONTENTS.org, "12B is a value per eating occasion"
  since: 2026-09-11
#+end_example

- Key format (decided 2026-09-11) :: =country::table::name=, three
  slots, an empty slot meaning "all".  The WAVE is not in the key: every
  served row already carries =t=, so it would repeat the index, and a
  rule spanning two rounds (12B) would need two identical entries.
  Scope lives in the entry: =waves:= is a list or =all=.  Where a rule
  genuinely differs by wave it is a different derivation with a
  different NAME, each scoped to its waves (Nigeria:
  =Nigeria::food_acquired::purchase-30d-transaction= for W4 beside
  =...::consumption-from-purchases= for W1), which is more informative
  than a wave number and lets =ll.derivations()= filter by wave from
  the entries.  An empty country slot is a FRAMEWORK-level derivation
  (=::household_roster::age-dob=), recorded in a =derivations.yml=
  beside the package's canonical =data_info.yml= rather than under a
  country; an empty table slot would be a country-wide rule (no case
  in the census yet).  A row's =Derivation= value is the literal key;
  empty slots resolve from the row's own country and =t=.
- The =basis= vocabulary is =derivations.yml='s OWN, defined in its
  own loader: the recall ladder's values (=questionnaire= >
  =variable-label= > =config-comment= > =filename=) plus
  =modelling-choice=, for an assumption no document can supply.
  =recall.py='s loader rejects any basis outside =BASIS_LADDER= and
  is not touched; do not reuse it.  A modelling choice is not
  evidence and must not be laundered into one; naming it is the
  point.
- The loader refuses an entry missing =rule=, =function=, =inputs=,
  =raw_variables= or =assumptions= (each with a =basis=) -- the
  =PopulationRecord= discipline: a record that cannot say what it did
  and why is not a record.
- Why YAML + dotted callables rather than a decorator :: a decorator
  (cf. =_build_registry.build_transform=) registers only when the
  country module is imported, so a corpus-wide listing would have to
  import every country module.  The YAML is readable without importing
  anything, packages into a wheel, and the cache fingerprint already
  covers the country module's source.  A drift test checks both
  directions: every =function= / =inputs= path resolves, and every
  function named =derive_*= in a country module is registered.
- API :: =ll.derivations()= -- the corpus table (the coverage-matrix
  shape; an unregistered derivation found by the census is then a
  visible gap).  =Country(c).derivations(table=None)= -- the
  country's entries.  =df.attrs['derivations']= --
  ={country: {key: {rows: n, columns, waves}}}=, attached in
  =_finalize_result= (in =_EXCLUDED_CALLABLES=, so it moves no cache
  hash) and re-merged by =Feature()= the way =recall.merge_attrs=
  does.  =Country.notes()= already surfaces CONTENTS.org; the
  =contents= field is a pointer into it.

** Raw-input retrieval (the exact survey answers, by name)

=Country(c).derivation_inputs(key)= calls the registry's =inputs=
callable, which re-reads the source through =get_dataframe= and
returns a frame at the served grain (=t, i, j= for 12B) whose columns
are the ORIGINAL variable names (=MFOODCLY, TFOODC, UTFOODC,
VFOODCPD=), so it joins to the served table and reads against the
questionnaire.  "Joins to the served table" is a promise the framework
has to keep, not the inputs callable: =Country.derivation_inputs=
re-keys =i= through =updated_ids= exactly as =_finalize_result= does
for every served table (found 2026-09-11: GhanaLSS 1988-89 serves
=101332= / =101332_1= -- a panel re-key plus a split-household suffix
-- where =Y12B.DAT= says =200103=, so an un-walked raw frame had no
row for the served household).  Slow and exact; nothing is stored.  A cached companion
parquet is a possible later tier if the call is used enough to want
one -- the registry key is what such a cache would be named by.

** One level up: derived tables and =Feature()= (decided 2026-09-11: follow-on, and a different carrier)

=food_expenditures= / =food_quantities= / =food_prices= are computed
at read time from =food_acquired=, and =Feature()= concatenates across
countries.  An earlier draft of this note proposed carrying the row
label through both by set-union of keys within each group.  @ligon's
call: that is a follow-on, and at that level the mechanism is NOT a
per-row column but an ATTRIBUTE -- a summary saying that at the lower
level there is something to explore.  A derived table did not derive
those rows; it should point at the table that did, not relabel them.

So: =df.attrs['derivations']= on a derived table (and on a =Feature()=
result, per country) lists the keys present in its inputs with their
row counts and the input table's name -- ={'GhanaLSS':
{'GhanaLSS::food_acquired::12b-fortnight': {'rows': 44149, 'in':
'food_acquired'}}}=.  The row label stops at the table where the
derivation was made.  Two known constraints on the follow-on:
=attrs= die at =Feature()='s concat, so the re-merge must be explicit
(=recall.merge_attrs= is the intended precedent and has NO caller
today -- the census found =attrs['recall']= already dies there); and
the derived tables' groupby must not be asked to reduce the string
column, which the first instance avoids by leaving it to fall away at
the sum.

** Site 1: the declared-index collapse

=_normalize_dataframe_index= (=country.py=) reduces a non-unique
declared index, and =food_acquired= is in =_ADDITIVE_MEASURE_COLUMNS=,
so measures SUM there while a string column gets =first()= -- which
would silently keep one of two keys.  The set-union rule applies at
Site 1 as well, and the wave-script uniqueness assert (Trap 9 in
GhanaLSS's CONTENTS.org) remains the first guard: a derived row
should never reach Site 1 non-unique.  Both, not either.

** No warning at pooling time (decided 2026-09-11)

A =PopulationHeterogeneityWarning=-style warning at =Feature()= was
considered and declined: at that level the mechanism is the =attrs=
summary (previous section), which says what is below and where to
look; a warning would repeat it as noise.  =Country(...)= calls have
the column itself.

* First instance: GhanaLSS 1987-88 / 1988-89 own production

- Function :: =ghanalss.derive_12b_fortnight_value(months, times, unit_code, value_each_time)= (the =derive_= prefix is what the drift test keys on)
  with =days_per_unit = {3: 1, 4: 7, 5: 30.4, 6: 91.3, 7: 182.6, 8: 365}=
  (the 12B legend: DAY 3, WEEK 4, MONTH 5, QUARTER 6, HALF YEAR 7,
  YEAR 8) and =window_days = 14= as a module constant, not an argument.
- Construction (decided 2026-09-11) :: the YEAR-AVERAGE fortnight,
  =value_each_time * times * (14 / days_per_unit) * months / 12=, i.e.
  GSS's own annual construction =HPFOOD= divided by 26.  Worked
  example agreed with @ligon: 6 months of the 12, 12 times a month,
  10 cedis each time -> 120 a month in season, 720 a year (=HPFOOD=),
  55.3 for an in-season fortnight, and 27.6 for a fortnight drawn at
  random from the year (the 6/12 is the chance the fortnight lands in
  season).  Chosen because it is unbiased over the sample -- the
  purchase side is a realised fortnight but the form does not record
  WHICH months were cited, so the in-season figure is right for some
  households and zero is right for the rest, unknowably -- and because
  it defers to the construction the people who collected the data
  used.  The in-season alternative (no =months / 12=) and GSS's annual
  are described in the docstring and computable from
  =derivation_inputs=; the served value is this one.
- Test :: the annualising core of the function applied to =Y12B= and
  summed per household must reproduce =EXPEND.HPFOOD= to within 3% at
  the median (measured 1.020 / 1.020 for both rounds); a static test
  that the wave scripts stamp =Derivation= on every produced row and
  on no purchased row.
- Effect :: 44,112 served produced rows (20,808 + 23,374 source rows before the =j= collapse) relabelled and rescaled; row counts unchanged.
- CONTENTS.org :: correct l.1242 / l.1258 (12B is not "since my last
  visit"); record the manual's two-week fallback rule for 12A.

** What fits the mechanism, restated after the census

The agents' "won't fit a per-row key" lists mostly dissolve once the
key is read as naming an OPERATION and =derivation_inputs= is defined
at the INPUT grain (@ligon, 2026-09-11: "a row computed from a groupby
operation could refer to the groupby operation"):

- reducers (sum / mean / first / median over a group) :: the key names
  the reduction; the inputs callable returns the group members with the
  group key, so the suppressed alternatives are exactly what comes back;
- chained pipelines (Tanzania =Quantity=: hakuna -> 0, fillna, floor,
  x factor, 0 -> NaN) :: ONE key naming the pipeline, steps listed in
  order in the entry; inputs = the column before step one;
- several columns on one row with different rules :: the entry's
  =columns= field; the row carries =a+b=;
- index-value derivations (=u := 'Unknown'=, =season := 'annual'=) ::
  the key sits on the row; the entry names the level;
- branch selections (=age_handler=, GPS-vs-estimate, weighted-mean-vs-
  first, "derived by X unless X fails") :: one key PER BRANCH, so the
  path taken is on the row and countable;
- served under a name that implies a different window or question
  (Nigeria W4, the EHCVM last purchase, Uganda intercropped) :: an
  entry whose =rule= is the identity and whose =assumptions= carry the
  semantics.  The function is trivial; the registry is the point;
- many-row inputs (nutrition matrix products, sales summed over
  species, factors learned from another wave) :: the inputs callable
  returns a FRAME at whatever grain the inputs have; nothing requires
  it to return one row per served row.

Two things remain outside the column and live in the registry alone:

- deletions :: a row that was dropped has nowhere to carry a key.
  Registry entry with =rows: 0=, an inputs callable returning the
  deleted rows, surfaced through =attrs= / =ll.derivations()= -- the
  same class as the grain-collapse reports, and reported the same way;
- build/read composition :: a derivation whose served value depends on
  cache state (Ethiopia shocks: YAML maps Increase -> True, the legacy
  script path -> False, and the Makefile still builds the script) is a
  defect to fix, not a derivation to label.

* Alternatives considered

- Options on the derivation function :: rejected (2026-09-11).  A
  cached parquet must be one construction; options would need a
  registry of parquets in the cache.
- Documentation only :: rejected; a trap for downstream users.
- An index value :: rejected for the vocabulary reason above; noted
  because it is the one carrier that is more prominent than a column.
- =attrs= only :: rejected; dies at =Feature()= concat.
- Decorator registry :: rejected in favour of YAML + dotted callables
  (importability); the drift test keeps them honest.
- Raw inputs as extra served columns :: rejected for the canonical
  tables (per-wave columns break the cross-country interface); this
  is what =derivation_inputs= is for.

* Costs

- Cache :: measured on the first instance (2026-09-11): the mechanism
  alone (loader, attach in =_finalize_result=, the =.yml= siblings, the
  =data_info.yml= declaration) moved 0 of 14 probed hashes; the
  instance moved every GhanaLSS table and nothing else -- 5 of 14 --
  because the derivation function lives in the country module
  ={country}.py=, which is in EVERY table's input hash.  So the cost of
  a new instance is one country re-warm, not one wave; an earlier
  draft of this line said "only the waves whose scripts stamp the
  column" and was wrong.
- Discipline :: once the mechanism exists an unregistered derivation
  is a defect.  =make api-audit= should grow a check that greps wave
  scripts for arithmetic on served columns and asks for a key.
- Retrofit :: the known instances above become issues, one each, after
  the first instance lands; the census sizes that queue.
