* The three =groupby().first()= sites in =malawi.py= (GH #637)

Reviewed for *key soundness* -- the only thing that makes a
=.first()= wrong.  =.first()= defaults to =skipna=True=, so a group of
several rows collapses to a *composite* assembled from the first
non-null value of each column independently, i.e. a row that appears
nowhere in the survey.  That is *usually correct*: NULL is absence, not
contradiction.  It is wrong only when the duplicate rows describe
*different real entities*, which is a broken identifier and is fixed at
the identifier (#323 D1), never by =skipna=False=.

*Method.*  =DataFrameGroupBy.first= was patched in-process and the wave
scripts driven with =runpy=.  All three tables are =materialize: make=,
so an in-process patch cannot see them if they are built through the
subprocess -- an earlier probe of a site like this reported a
meaningless "0" for exactly that reason.  Run cold, in an isolated
=LSMS_DATA_DIR=.

| site (=malawi.py=)            | groups >1 row | verdict                       |
|-------------------------------+---------------+-------------------------------|
| =plot_features_for_wave=      |             0 | key sound; =.first()= no-op   |
| =food_coping_for_wave=        |             0 | key sound; =.first()= no-op   |
| =months_food_inadequate_for_wave= |         0 | key sound; =.first()= no-op   |

*No composite is ever built at any of the three*, because no group ever
has more than one row to build one from.  For the two Module-H sites
the rows in equal the groups out *exactly* -- 61,355 / 19,994 / 62,232
/ 57,157 for =food_coping= and 12,271 / 4,000 / 12,447 / 11,434 for
=months_food_inadequate=, the latter being precisely each wave's Module
H household count.

** The three traps, and which check answers each

*"They're only exact duplicates" is not reassurance* and *a key can
look invariant merely by being null*.  Both are disposed of by the same
exact equality above: a household id shared by two rows, or two
distinct ids merged by =format_id=, would each surface as a duplicate
group, and there are none; and no key column is null in either
Module-H table.  Confirmed at source: =case_id= / =y2_hhid= are unique
in Module H and =format_id= collapses no two of them.

*A broken key can produce ZERO duplicates* -- the Tanzania inversion,
which turns the duplicate-count instrument inside out.
=Tanzania/2008-15='s =shocks= built =i= from the panel-LINE index
instead of the household id; the namespaces shared no values, so every
replicated line became its own distinct "household" and
=groupby().first()= reported 0 duplicate groups, indistinguishable
from a sound key.  So *"0 duplicates" is not sufficient*.  The check
that catches it is a *per-wave* namespace overlap against the roster --
per wave, never in aggregate, because clean waves otherwise carry
broken ones.  Run for all three tables:

| table                  | 2010-11 | 2013-14 | 2016-17 | 2019-20 |
|------------------------+---------+---------+---------+---------|
| plot_features          |    100% |    100% |    100% |    100% |
| food_coping            |    100% |    100% |    100% |    100% |
| months_food_inadequate |    100% |    100% |    100% |    100% |

And not vacuously: the id strings match literally (=101011000014= on
both sides), and the row counts show no namespace inflation -- rows
never exceed source households x strategies.

This was worth running rather than waving away, because *2019-20 has
the surface shape of a namespace split*: its =data_info.yml= runs
=case_id= through =cs_i= (='cs-19-' + format_id=) for =sample= /
=household_roster= / =cluster_features=, while all three wave scripts
pass =i_prefix=''= / bare =format_id=.

*That asymmetry is a deliberate, already-recorded decision, not a
defect* -- see "plot_features (GH #167)" below: "2016-17 cross-sectional
id is =cs-17-=-prefixed in =sample()= ...; the wave script applies the
same prefix so XS plots are not ~100% orphaned.  *All other halves emit
the raw wave hhid* and rely on framework id_walk / =panel_ids=
chaining."  2019-20 is one of those other halves.  The measurement
confirms the documented expectation rather than contradicting it: the
=cs-19-= prefix survives to the API on *neither* side (0 of 14,612 ids
carry it, in any table), so both sides are in the raw =case_id=
namespace and =i= joins exactly.  2016-17 reaches the same place by the
other route -- prefixed on both sides.  A test pins the overlap per
wave so neither route can drift.

=plot_features= showed 4 apparent duplicate groups (3 in 2016-17
Cross_Sectional, 1 in its Panel half).  Every one of them consists
entirely of rows whose =plot_id= is *NULL* -- there are *zero*
duplicate groups on a real plot id in any wave, so =(hhid, plotkey)=
identifies the plot and no two plots collide on it.

* crop_production: the SALE has its OWN condition too (GH #833, fixed 2026-09-24)

The sequel to "the SALE has its OWN unit" above, on the other half of the
same pair.  Module I (and, from 2016-17, Module Q) asks the sale's
shelled/unshelled state in its own column, on the harvest's own code list:

: ag_i02c  How much of the harvested[CROP]was sold in total?(S/U)
:          {1 S: SHELLED, 2 U: UNSHELLED, 3 NOT APPLICABLE}   -- every wave
: ag_q02c  S/U, same labels                                    -- 2016-17, 2019-20 ONLY

*Idiosyncrasy: Module Q has no =ag_q02c= before 2016-17.*  2010-11
=ag_mod_q.dta= and 2013-14 =AG_MOD_Q_13.dta= carry no S/U column at all, so
every perennial sale in those two waves is =unknown_condition= on the sale
side -- as every Module P harvest row is on the harvest side, in every wave
(P asks no condition question).  Perennial sales therefore attach on the
unknown wildcard only, and that is the survey, not a gap in the wiring.
Where Q does ask (2016-17 / 2019-20) the answer is overwhelmingly =3=
(NOT APPLICABLE: 527 + 94 and 1,087 + 172 rows against 49 + 6 and 133 + 18
=S=), which is compatible with P's =unknown_condition= and so changes
nothing.

** The rule

=_sale_block= now reads the sale's S/U through the same =_crop_conditions=
map as the harvest (NULL and an absent column -> =unknown_condition=), and
groups on =(i, _crop_code, u, condition_sold)=.  =assemble_crop_production=
attaches a sale to a harvest row iff the crop is single-plot (unchanged),
the units are equal (GH #824, unchanged), and the two conditions are
*compatible*: EQUAL, or either side =unknown_condition=.  Two answers that
differ are a contradiction, and =shell_not_applicable= against =shelled= /
=unshelled= IS one (decision, 2026-09-24: both are answers; the survey did
not say "don't know", it said "no shell" on one side and "shelled" on the
other) *[REVERSED the same day by @ligon's ruling, part (b): not-applicable
IS the basis where shelling does not apply -- see "the sale-basis LADDER"
below; the sentence stands only as the record of the morning's decision]*.
The pairing is m:m in principle (a household can sell one crop in
one unit shelled AND unshelled; a plot-crop can be harvested in one unit
shelled AND unshelled), so it is decided per candidate pair: a sale lands
only where it is compatible with exactly one harvest row and that row with
exactly one sale.  Everything else is suppressed and counted in one of two
tallies -- the #854 =attrs['sale_suppressed']= (AMBIGUOUS: more than one
compatible pairing; shape unchanged) and the new
=attrs['sale_basis_mismatch']= (a harvest row in the sale's unit exists and
every one contradicts the sale).  Each has its own =SaleAttachmentWarning=.
This is the #824 rule applied to the second half of the pair: a sale that
cannot be expressed at the row's declared grain is not attached.

*Checked, not assumed*: a Module I / Q line for a crop the household did NOT
sell carries NULL quantity, value AND condition, and =_sale_block= sums it
to a zero-valued =unknown_condition= sale.  Had such a line shared an
=(i, crop, u)= key with a real sale it would have made the real sale
ambiguous.  Measured on all four waves: *0* keys mix an unsold line with a
sold one.  The reason is NOT that "the unsold lines have no unit" (this
paragraph used to say so): 2 unsold 2010-11 lines DO carry a unit, and they
collide with nothing; the rest sit under =u = NULL= and pair only with a
harvest row whose unit is likewise NULL.  Those zero-quantity pairings are
served as =Quantity_sold = Value_sold = 0.0= (the survey's "did not sell"),
as they have been since before #833, and carry no =Derivation= key -- see
"the sale-basis LADDER" below.

* crop_production: can PRICE decide a sale's shelled/unshelled basis?  (probe, 2026-09-24)

Read-only diagnosis serving @ligon's 2026-09-24 ruling that the
=shell_not_applicable=-vs-S/U class the GH #833 fix suppresses (465 sales,
40.65M MWK, mostly Tobacco and Cotton) is "really a missing data problem,
decipherable by looking at prices perhaps".  Scripts, outputs and the
proposed (unimplemented) derivation:
=slurm_logs/backlog_fix_2026-09-24/malawi_sale_basis/README.org=.  What the
measurement established, stated here because each is an idiosyncrasy of
this survey and not of the wiring:

- *Price identifies the basis for Groundnut only.*  Over the 14,791
  agreeing sales (sale S/U == harvest S/U), a shelled unit of groundnut
  sells at 1.6-2.2x an unshelled one per 50 kg bag, 3.7x per kilogramme,
  4.4x per large pail (Mann-Whitney P(S>U) 0.78-0.98; leave-one-out
  nearest-median recall ~80% per basis).  For Maize, Rice, Soyabean and
  Pigeon Pea the two bases sell at the SAME price per native unit (ratio
  0.94-1.00, P 0.42-0.54), so the S/U answer carries no price content
  there and no price rule can decide a contradiction on those crops.
- *On Tobacco and Cotton "shelled" is not a basis.*  The harvest side is
  =shell_not_applicable= 100% of the time in 2010-11 (Tobacco 1,411 / 0 /
  0; Cotton 252 / 0 / 0) and 86-97% afterwards; a sale coded S sells at
  the NA price in 7 of 9 cells with >= 10 on each (P 0.47-0.59).  The
  instrument predicts this: both the IHS3 and IHS5 agriculture
  questionnaires scope the question as "FOR ALL APPLICABLE CROPS, MAKE
  SURE TO ASK WHETHER THE REPORTED VALUE IS SHELLED OR UNSHELLED", with no
  crop list and no ginned / cured option, so S on cotton or tobacco is an
  enumerator's application of a code the instrument gives no meaning on
  that crop.  Whether that makes NA compatible with S/U for those crops is
  a decision, not a measurement; the money it governs is Tobacco 109
  sales / 24.76M and Cotton 57 / 2.04M of the 465.
- *The 465 class runs 2:1 the OTHER way from "a sale with no recorded
  basis".*  307 sales / 22.63M MWK have a stated S/U on the SALE and a
  not-applicable HARVEST row; only 158 / 18.02M are a not-applicable sale
  against an S/U harvest row.  Under the price rule with the gates that
  survive validation (>= 10 agreeing sales per basis in the reference
  cell, the cell SEPARATES at P outside (0.25, 0.75), margin > 0.5 x gap),
  *17 sales / 477,800 MWK* of the 158 attach (1 / 0 / 2 / 14 by wave; all
  17 inferred unshelled, all Groundnut, all at the =(t, crop, u)= grain --
  a per-wave build cannot pool across waves), and 448 / 40.17M stay
  suppressed.
- *On the 647 genuine S-vs-U contradictions the SALE field is the more
  reliable one, but not reliable enough for a rule*: on Groundnut the
  price sides with the sale's own answer 61% (sale S / harvest U) and 77%
  (sale U / harvest S) of the time against a ~80% ceiling if the sale were
  always right and ~20% floor if the harvest were.  That supports

** The vocabulary: a bare FORM axis, and why Uganda's tokens are wrong here

=ag_g13c='s Stata value labels are identical in every wave that asks it:
=1 'S: SHELLED'=, =2 'U: UNSHELLED'=, =3 'NOT APPLICABLE'= (2013-14 drops the
=S:= / =U:= prefixes; the codes are the same).  *Module G asks no dryness
question at all.*

Uganda's =harvest_conditions= crosses a DRYNESS family (green / fresh /
dry-at-harvest / dried) with a FORM (with shell / in cob / in pods / grain).
Borrowing =dried_grain= for Malawi's SHELLED would assert a dryness the
instrument never recorded -- and the whole point of the level is to say what
was measured.  So Malawi extends the *form* axis with bare tokens, which is
exactly what =data_info.yml= tells a country to do ("a country asking
something Uganda does not should extend this list rather than force-fit a
foreign category").  New table =harmonize_crop_condition= in
=categorical_mapping.org=; new tokens =shelled= / =unshelled= /
=shell_not_applicable= in =data_info.yml=.

not pedantry: the first is the survey's own answer (code 3 -- this crop has
no shell to speak of), the second is the sentinel =malawi.py= mints for a
NULL or off-scheme code and for every perennial Module-P row, which asks no

** Why the join keys on the VARIETY (2026-09-10, red-team item 2)

The first cut of the loader keyed on our collapsed =crop=, reduced the file's
varieties with an agreement-or-drop rule, and refused 23 + 8 keys.  The
red-team pass measured what that costs and the answer was not noise: *6,890
served rows*, entirely on Groundnut, Rice and Citrus -- the country's
second-biggest crop among them.  And in 19 of the 23 seasonal refusals the
SOLE dissenter is the catch-all ="OTHER GROUNDNUT (SPECIFY)"= / ="OTHER RICE
(SPECIFY)"=; the named varieties agree exactly.  The remaining 4 are a real
and economically meaningful split -- unshelled paddy in a 50 kg bag is *29.04
kg* for =RICE LOCAL= against *49.00* for eight improved varieties in Central
(1.69x).  The 8 tree refusals are not varieties at all: =harmonize_crop= maps
ORANGE, LEMON and NAARTJE all to ='Citrus'= and the file weighs them
differently (Southern 50 kg Bag: 38.0 / 52.0 / 55.0).  That refusal is a
symptom of *our* harmonisation being coarse, not of the file being ambiguous.

:   //NOTE THAT WE MERGE ON CROP_CODE_LONG INTENTIONALLY

** =Feature('crop_production')= EXCLUDES Malawi until the framework fix lands (2026-09-10)

*Stated here because the level was kept on purpose, and because the next
person to audit =Feature('crop_production')= will otherwise read Malawi's
absence as a build failure.*

=crop_production= is deliberately not registered in =lsms_library/data_info.yml='s
=index_info= (the plot-level ag features' index NAMES diverge -- =plot= vs
=plot_id=, =crop= vs =j= -- and that comment defers the harmonisation).  So
=Feature.__call__= falls through to the modal-index-shape filter, which DROPS
any frame whose =index.names= tuple is not the modal one, with a named
=UserWarning=.  Adding =condition= moved Malawi from the 8-country modal shape
=(t,i,plot,crop,u)= into a shape of its own, so:

: Feature('crop_production')(['Malawi','Togo','Benin'])
:   -> (20619, 4)  countries kept: Benin, Togo
:   UserWarning: crop_production: excluded 1 country frame(s) ['Malawi'] with a
:   divergent index shape ... (kept modal shape [...,'plot','crop','u',...])

Malawi's *131,548 rows* -- 81% of that assembly, and the largest single frame
in the modal group -- are gone from every =Feature('crop_production')= call.
The degrade is LOUD, which is the library's stated contract, so this is not a
silent-corruption defect; it is a real functional regression with a known
cause and a known fix.

*It is NOT fixed by removing the level*, and the level must not be removed:
=condition= is what makes the shipped table joinable at all (see the table
above -- without it the transform refuses outright), and Uganda already
carries =condition= and is already excluded by the same rule, so the rule
would have to be fixed for Uganda regardless.  The fix is to register
=crop_production= in =index_info= with a canonical shape and let
=fabricate_missing_levels= give the =condition=-less countries a NaN
=condition= so they are KEPT -- the mechanism =interview_date= already uses
for =visit= (GH #506).  That is in hand on branch
=fix/feature-canonical-index-crop-production=; this branch's merge is held
until it lands.  GH #775 / #569.

** =KG_FACTOR_MAX= rejects 12 shipped rows that are probably right

=shipped_implausible = 4,639= is one thing: *ox-carts*.  Twelve shipped
factors exceed the cross-country cap of 250 kg/unit -- Maize 388.4-682.0,
Sugar Cane 610.0-631.4, Sweet Potato 365.4, Irish Potato 358.0 -- and an
ox-cart of maize really does weigh several hundred kilograms.  This is the
screen catching a physically plausible container, not a mis-key.  *The cap
was NOT touched* (it is a cross-country constant tuned on Uganda's data-entry
errors, and #854 says count-never-clip), so those rows fall through to
=none= -- *not* =inferred=: the library's label parser cannot read "Ox-Cart"
either, so a rejected shipped ox-cart factor leaves the row with NO harvest
weight at all.

*The proposal for @ligon, with the rows it moves* (also in
=.coder/ledger/854-malawi-shipped-factors.md= §7; NOT implemented here):

1. *Keep =KG_FACTOR_MAX = 250= as the default and add a per-unit override* --
   a small =_KG_FACTOR_MAX_BY_UNIT= table for bulk-transport containers,
   =ox-cart: 800= (and =cart: 800=, =wheelbarrow: 200=), matched on the same
   stripped-lower-cased unit text =_KG_UNIT_KEYS= already uses.  The screen
   already reads the row's unit from =df=, so it is one lookup inside
   =_screen_reported_factors=.  *Rows moved: 4,639* (Maize 4,452, Sweet Potato
   132, Sugar Cane 45, Irish Potato 10) from =none= to =shipped=.  Do NOT
   raise the global cap: it exists to catch a quantity or a calendar year
   keyed into the factor field, and those live on kg / bag / tin units.
2. *Add a FLOOR.*  The screen has a ceiling and no floor, and the live
   instance is in this very table: *Citrus / Ox-Cart = 18.9 kg*.  A cartload
   of oranges weighing 19 kg is exactly as wrong as 682 is high, and it passes
   unremarked today.  (Under the variety key this particular row is withdrawn
   anyway -- the file gives ORANGE, LEMON and NAARTJE different weights and we
   no longer collapse them -- but the *absence of a floor* is general.)
3. *The one factor not to defend*: Maize / unshelled / Central = *682.00*, at

4. *Whoever changes the cap must first measure Uganda's reported (250, 1000]
   band.*  Uganda is the country the cap was tuned on, and the red-team pass
   could not build it.  Nigeria was measured: *zero* of its 19,678 non-null
   reported =KgFactor= rows are above 250, so a per-unit override changes

The internal check that says these are measurements and not mis-keys needs no
outside number: divide each ox-cart factor by the SAME
crop/condition/region's 50 kg Bag factor and you get *8.4 to 9.4 bags per
cartload* for maize, 6.5 for the potatoes -- which is what a two-ox cart
carries.  Only the 682.00 (15.4 bags) falls outside.

* Sampling Design
** Overview
Malawi has five waves from two survey programs:
- IHS2 (2004-05): cross-sectional, 11,280 households
- IHS3 (2010-11): cross-sectional, 12,271 households
- IHPS (2013-14): panel only (tracked from IHS3), 4,000 households
- IHS4 (2016-17): cross-sectional (12,447) + panel (2,508) = 14,955 households
- IHS5 (2019-20): cross-sectional (11,434) + panel (3,178) = 14,612 households
  (this line read "= 14,552" until 2026-07; the two addends were right and
  the total was a typo.  14,612 is what =sample()=, =household_roster()= and
  =cluster_features='s =df_main= all return for the wave.)

** Strata
District serves as the stratification variable across all waves (~30-32
districts). The 2013-14 IHPS file also has an explicit =stratum= column
with 6 Region x Rural values, but we use =district= for consistency.
District names vary slightly across waves (e.g., "Blanytyre" vs
"Blantyre", "Nkhatabay" vs "Nkhata Bay"); these are harmonized via the
=strata= table in =categorical_mapping.org=.

** Cluster (PSU)
- 2004-05: =psu= (string, 564 unique EAs)  -- *was* =ea=; see below
- 2010-11 onward: =ea_id= (string, 200--800 unique EAs per wave)

Every wave's =v= is the same object in the same format: the *fully qualified
8-digit Malawi enumeration-area code*, =region(1) + district(2) + TA(2) +
EA(3)= -- e.g. =10101016= is EA 016 of TA 01 of district 01 (Chitipa) of
region 1 (North).

*** GH #323: 2004-05's cluster key was not a cluster key

Until this was fixed, 2004-05 declared =v: ea=.  =ea= is *the EA's sequence
number within its Traditional Authority*, so it takes only *110 distinct
values for IHS2's 564 enumeration areas*.  Keyed on =ea=, roughly five
unrelated EAs -- in different TAs, districts and regions -- merged into one
=v=, and the household -> cluster projection in =Wave.cluster_features= then
resolved the disagreement with =groupby().first()=: one arbitrary household's
answer, served as the cluster's.

What that destroyed, measured cold:

| quantity                                            | =v: ea= | =v: psu= |
|-----------------------------------------------------+---------+----------|
| clusters                                            |     110 |      564 |
| districts present in =cluster_features=             |      20 |       26 |
| settlement strata present in =cluster_features=     | 1 (all =Rural=) |        2 |
| contested cluster-attribute cells (of 330 / 1,692)  |     164 |    *0* |

The urban stratum did not merely lose rows -- it disappeared.  All 110
surviving clusters came out =Rural=, because =first()= happened to reach a
rural household in every merged group.  Six of Malawi's 26 districts vanished
from =cluster_features= entirely.  Both facts were invisible at the API: the
table looked complete, it was just wrong.

=psu= is the fully qualified code, already present in =sec_a.dta=: 564 values,
*exactly 20 households each* (the IHS2 design), and *zero* households in a
cluster disagreeing about their cluster's region, district or urban/rural
status.  It is declared identically in =sample= and in =cluster_features=,
because =_join_v_from_sample= joins the two through =v= and they cannot be
allowed to drift.

Note the *frame vintage*: 2004-05 shares only 3 codes with 2010-11.  IHS2 is
drawn from the 1998 census frame and IHS3+ from the 2008 frame, so the code
*format* is common across all five waves but the code *sets* are not.  A
cross-wave join on =v= is meaningful from 2010-11 onward and not before.

*The hook* -- ONE implementation, =malawi.ihps_panel_cluster_features= (in
=_/malawi.py=, with =IHPS_STAYER_KM=, =IHPS_STATUS=, =IHPS_PANEL_ID= and the
=ihps_baseline_status= mapping), called by a one-line =cluster_features= in
each IHPS wave's =_/mapping.py= that passes only where that wave reads the
status from.  The status column =_ihps_baseline_status= (='stayer'= /
='moved'= / ='unrecorded'=, dropped by the hook) is a file override on the
panel cover in 2016-17 / 2019-20 and a plain =df_main= myvar in 2013-14.
The shared function is deliberately not named =cluster_features=: every
callable in =malawi.py= is a country-level formatting function, and that
name would run as the table's =df_edit= hook in 2004-05 and 2010-11 too.
1. *Finds* each panel EA's fix from its stayers, and *raises* if they
   disagree.
2. *Keeps* every panel coordinate that equals the fix and blanks the rest --
   judged by coordinate, not by distance alone, because the distance only
   finds the fix.  418 movers and 1 unrecorded household (2016-17) and 29
   movers (2019-20) sit exactly on their EA's fix and keep it: 1,861 / 2,165
   panel households keep a coordinate.  This also settles the unrecorded
   case the way 2013-14's measurement does (=fillna(0) <= 1=): an unrecorded
   household on the fix keeps it.  Coordinates are blanked, never rows
   dropped.
3. *Puts stayers first.*  A mover on the fix is as complete a row as a
   stayer, but its =Region= / =District= / =Rural= describe where it lives
   now; the grain collapse breaks ties by order (=most_complete_row=), so
   stayer-first means the cluster takes a stayer's attributes.  Without it
   one 2016-17 EA served =Rural= from a mover while its stayers are all
   Urban.
4. *Fails closed.*  A panel household (id =NNNN-NNN=, the =y{2,3,4}_hhid=
   shape) with a NULL status means =dist_to_IHS3location= did not arrive --
   renamed or misspelled upstream, which =missing_ok= turns into an all-NaN
   column, and every mover's location would then be served.  The hook
   raises; so does a status on a non-panel id.  Measured end to end with
   the variable misspelled in 2019-20: =Country('Malawi').cluster_features()=
   raises =RuntimeError= ("3178 of 3178 panel households have NO baseline
   status").
The status is a STRING on purpose: a first version returned =+inf= for an
unrecorded distance, and =grab_data='s >1e99 missing-value rule rewrote it to
NaN.

*** 2004-05 (IHS2, catalog 2307)

**** Declared universe -- and a caveat about its strength

There is *no field or heading labelled "Universe"* anywhere in this wave's
documentation, and the World Bank DDI XML for study 2307 has *no =<universe>=
element at all* (verified 2026-07-21: =grep= over the fetched DDI returns zero
matches).  The nearest statement is embedded in the Sampling Procedure
narrative:

#+begin_quote
The sample for IHS-2 was drawn using a two-stage stratified sampling procedure
from a sample frame using the 1998 Population Census Enumeration Areas (EAs).
The population covered by the IHS-2 was all individuals living in selected
households. The sample frame includes all three regions of Malawi: north, centre
and south.
#+end_quote

Source :: =2004-05/Documentation/ddi-documentation-english_microdata-2307.pdf=,
PDF p. 3, "Sampling" -> "Sampling Procedure".  Identical text is in the catalog
DDI's =<sampProc>= element.

*This statement is circular* and should not be treated as a universe.  "all
individuals living in selected households" describes the *sample*, not the
population the sample stands for.  Malawi IHS2 is one of the corpus's named
examples of circular documentation (alongside GhanaLSS 1988-89).  Note also that
the unit named here is *individuals*, not households.

**** Exclusions

#+begin_quote
Each of the twenty-seven districts was considered as a separate sub-stratum of
the main rural stratum (for IHS-2, Likoma District was excluded because of
difficulty in travel to the island, so only twenty-six administrative districts
were considered). Thus the total number of strata in the survey was thirty:
twenty-six districts and four urban centers.
#+end_quote

Source :: same PDF, p. 3.

- *Geographic* :: Likoma District excluded, on stated travel/logistics grounds.
  This is the one hard, design-level exclusion documented for IHS2.
- *Population* :: NO institutional-population exclusion is stated for IHS2.
  IHS3 onward state one; IHS2's documentation is silent.  Recorded as silence,
  not as evidence of inclusion.

* GH #1278: two unsubstantiated string-based longitudinal matches (decision open)

At =10ad99d62=, the seven =function: cs_i= declarations in 2019-20

or merge inputs use bare IHS5 =case_id= and join the 2019-20 sample; the served

*New idiosyncrasy, source-backed on 2026-10-30:* all 11,434 IHS5
cross-sectional identifiers are unique and nonmissing and share no value
with the 3,178 raw or canonical 2019 IHPS identifiers. They also share no
key or value with any of the three committed =updated_ids= maps. However,
*two* are equal to identifiers in the 12,271-household IHS3 2010-11 sample.
These are two unsubstantiated string-based longitudinal matches: equality does
not establish that they name the same physical households, and independent
redraws could sample a household again, so different physical households are
not proved either.
The =local_tools.panel_attrition= helper intersects identifier sets; on the
actual 2010/2019 *sample spine*, its transition count is 1,454. A counterfactual
that prefixes only the 11,434 IHS5 identifiers makes it 1,452, with all sample
rows, native payloads and 3,178 panel identifiers unchanged. This is NOT a
run of =Country.panel_attrition= on an all-wave roster.

The documentation is in tension: the GH #637 entry calls the bare-2019
asymmetry "a deliberate, already-recorded decision", whereas the GH #1260
entry says the =cs_i= comments "describe intent, not behaviour". Neither
statement establishes that the two cross-sample coincidences are links.
The GH #894 / PR #1265 crosswalk remains exact: rebuilding its frame from
its three declared cover sources reproduces the committed maps; it does not
link the independent IHS5 half.

*No namespace repair is selected here.* Retaining bare identifiers and
removing dead declarations preserves existing within-wave joins, but leaves
