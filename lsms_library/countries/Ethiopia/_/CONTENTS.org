*** Unit handling

The =u= (unit) index level on =food_acquired= is canonical at
parquet-write time via in-script title-casing plus a small typo
patch in =ethiopia.py:food_acquired=.  Source labels are read with
=convert_categoricals=True= (so they arrive as strings like
=KILOGRAM=, =Meduim Cup=, =Kubaya 100Ml=), then normalised to
=Kilogram=, =Medium Cup=, =Kubaya/Cup 100Ml=, etc., before the
parquet is written.  See =lsms_library/countries/Ethiopia/_/ethiopia.py=
around lines 220-231 for the exact regex / =str.title()= calls.

*CORRECTED 2026-09-18 (GH #832).*  This paragraph used to read "No =u=
table is wired into =_/categorical_mapping.org=; the framework's
auto-discovery on =u= would be a no-op (the labels are already
canonical)."  *Both halves are false.*  A =#+name: u= table has been in
that file since the 2026-06-14 "Unit #0" pass (its own section header says
so), it IS auto-discovered by name on the =u= index/column of every
Ethiopia table, and it is not identity: =Digigimosh -> Other (Specify)=,
=KILOGRAM -> Kg=, =Littere -> Liter=, =pices -> Pieces= and ~30 more rows
all relabel at API time.  The "Unit #0 is FOUNDATION ONLY" claim in that
table's own header ("the mapping is identity for every food_acquired
unit") is the likely origin of the error -- it was true of the rows that
existed on the day it was written, and the table has grown since.

Two live consequences, so this is not a cosmetic correction:

- a =u= spelling can be fixed EITHER in that table (API-time, affects the
  served frame only) OR in =_clean_unit_label= (build-time, affects the
  shipped-conversion-factor loader too, because that loader decodes its
  own =unit_cd= through the same function).  They are not
  interchangeable, and picking the wrong one silently de-synchronises the
  two sides of the factor join.  GH #832 used the table for
  =Other(Specify)= and =_clean_unit_label= for the Zorba mojibake, for
  exactly that reason.
- an edit to that table moves every Ethiopia cache hash, same as a
  country-module edit.

The =_/conversion_to_kgs.json= file is a kg-per-unit factor
lookup consumed by =food_quantities= derivation -- it is a
separate concern from =u= label canonicalisation.  Its keys are
the same canonical unit labels (=Kilogram=, =Litre=, etc.), so
preserving the in-script normalisation above is what keeps that
join working.

For the cross-country canonical-=u= roadmap, see GH #223.

* Sampling Design
** Overview

Two-stage stratified cluster sample. Enumeration Areas (EAs) are
the primary sampling unit (PSU). The Ethiopia Socioeconomic Survey
(ESS) is part of the LSMS-ISA program, covering rural and small-town
areas in waves 1-3, expanding to include all urban areas from wave 2
onward.

ESS data are collected using a post-planting / post-harvest (PP/PH)
design, but the =sample= feature uses the household-level cover page
(=sect_cover_hh_w{N}.dta=), which provides one row per household per
wave (not per visit).

World Bank Microdata Library catalog entries:
- Wave 1 (2011-12): https://microdata.worldbank.org/index.php/catalog/2053
- Wave 2 (2013-14): https://microdata.worldbank.org/index.php/catalog/2247
- Wave 3 (2015-16): https://microdata.worldbank.org/index.php/catalog/2783
- Wave 4 (2018-19): https://microdata.worldbank.org/index.php/catalog/3823
- Wave 5 (2021-22): https://microdata.worldbank.org/index.php/catalog/6161

** Strata

Ethiopia has no explicit strata variable. Strata are constructed as
Region x Urban/Rural (=saq01= x =rural= or =saq14=), following the
ESS sampling documentation. The number of strata varies by wave
because the coverage expanded over time:

| Wave    | Region variable | Rural variable | Strata count | Notes                    |
|---------+-----------------+----------------+--------------+--------------------------|
| 2011-12 | =saq01=         | =rural=        |           18 | No Addis Ababa, Dire Dawa Urban |
| 2013-14 | =saq01=         | =rural=        |           21 | Adds Addis Ababa, Dire Dawa Urban |
| 2015-16 | =saq01=         | =rural=        |           21 | Same coverage as wave 2  |
| 2018-19 | =saq01=         | =saq14=        |           21 | ALL CAPS in source data  |
| 2021-22 | =saq01=         | =saq14=        |           19 | Tigray excluded (conflict) |

The =rural= column in waves 1-3 has varying labels: "rural" / "small
town" (w1), "Rural" / "Small town (urban)" / "Large town (urban)" (w2),
"RURAL" / "SMALL TOWN" / "Meduim and large town" (w3). All non-rural
categories are mapped to "Urban".

Strata labels are harmonized across waves via =categorical_mapping.org=
(fixes casing and spelling differences in region names).

** Cluster (PSU) identifier

The cluster identifier (=v= in the library's index convention) is the
Enumeration Area ID:

| Wave    | Variable  | Type   |
|---------+-----------+--------|
| 2011-12 | =ea_id=   | string |
| 2013-14 | =ea_id2=  | string |
| 2015-16 | =ea_id2=  | string |
| 2018-19 | =ea_id=   | string |
| 2021-22 | =ea_id=   | string |

Waves 2-3 use =ea_id2= (the wave-2 re-identified EA), while waves
1, 4, and 5 use =ea_id=. The EA ID format is a long numeric string
(e.g., "010101088801601") encoding region/zone/woreda/town/EA.

*The two code spaces are disjoint* (GH #942, measured 2026-10-19 through
=Country('Ethiopia').sample()=): none of the 3,776 panel households linked
across 2011-12 -> 2013-14 keeps its =v=, yet their 333 cluster pairs are a
*complete bijection* -- every W1 EA maps to exactly one W2 EA, no violation.
So =v= is renumbered, not redrawn, at that boundary, and
=Ethiopia/_/sampling.yml= declares it =cluster_id_continuity: wave-scoped=: a
=Country('Ethiopia')= frame carrying =v= across 2011-12 -> 2013-14 raises a
=ClusterIdentityWarning= (rows unchanged).  2013-14 -> 2015-16 (=ea_id2= both
sides) keeps all 4,887; 2018-19 starts Panel II and links to nothing.
Unverified, and the first thing to check before deriving a crosswalk:
=Pub_ETH_HouseholdGeovars_Y2= is listed below as carrying both =ea_id= and
=ea_id2=, i.e. the survey may ship the crosswalk itself.

| 2021-22 | 4959 |  2674 |       53.9% |  2285 |

*This is not urbanisation, and it is not a reweighting.*  Note the *Rural*
column: 3466 -> 3115 across a decade, essentially flat, while Urban grows
seven-fold.  The sample is being *extended into urban strata*, not shifted.

ESS1 was designed for "rural and small town areas" (see 2011-12 below).  So
=Urban= in 2011-12 denotes *small towns only*, while from ESS2 it denotes *any
urban area, including Addis Ababa*.  The same canonical value denotes two
different populations, and until this note nothing in the config, the schema or
this file said so.

*** What breaks

- A pooled regression with an urban dummy silently mixes two definitions.
- Any wave-over-wave comparison of an urban/rural gap is confounded by the
  definition shift.
- The 12.7% -> 36.8% step between ESS1 and ESS2 is *mostly* that shift, not a
  change in Ethiopia.

*** Related, and not the same thing

- =Rural= for 2013-14 and 2015-16 additionally *collapses* a small-town / large-
  town distinction that exists in the source (3,621 households).  See the
  corpus-wide audit in PR #682, which proposes a separate =SettlementType=
  column for within-urban tiers rather than more =Rural= values.
- ESS4 / ESPS-5 put *zero* of their urban households through the agriculture
  questionnaire while urban is 54% of the sample, whereas ESS1--ESS3 did.  That
  is a *module-conditionality* change, a second regime shift in the same
  country, and it is likewise invisible at the API.

*** Not claimed here

The often-quoted "small town = under 10,000" threshold is *not* verified in
this repo.  It should be confirmed against the survey report before anyone
relies on it or repeats it in a tracked file.

** Sub-samples and oversamples INSIDE a wave

Ethiopia's specialization is entirely internal to waves.  There is no
special-population wave; there are three distinct structures living inside the
ordinary ones, and a user who averages across them without noticing will get
the wrong answer.

*** 1. Every rural EA is 10/12 agricultural BY DESIGN (all five waves)

The rural sample is not a simple draw of rural households.  It is drawn from
the Agricultural Sample Survey's household sample, topped up with exactly two
non-agricultural households.  ESS1 DDI (2053), PDF p. 3, verbatim:

#+begin_quote
The second stage of sampling was the selection of households to be interviewed in each EA. For rural EAs, a total of 12 households are sampled in each EA. Of these, 10 households were randomly selected from the sample of 30 AgSS households. The AgSS households are households which are involved in farming or livestock activities. Another 2 households were randomly selected from all other households in the rural EA (those not involved in agriculture or livestock). In some EAs, there is only one or no such households, in which case, less than two non-agricultural households were surveyed and more agricultural households were interviewed instead so that the total number of households per EA remains the same.
#+end_quote

The same 10 + 2 structure is still in force in ESPS-5, per catalog 6161
=sampling_procedure=:

#+begin_quote
From the rural EAs, 10 agricultural households are selected as a subsample of the households selected for the AgSS, and 2 non-agricultural households are selected from the non-agriculture households list in that specific EA.
#+end_quote

So farm households are *structurally oversampled within every rural EA*, in
every wave, and the fallback rule above means the agricultural share rises
above 10/12 in sparse EAs.  Unweighted rural means are not rural-population
means.  Small-town and urban EAs have no such stratification (12 per small-town
EA, 15 per large-town EA, drawn without regard to economic activity).

*** 2. ESS2/ESS3 carry a panel AND a fresh urban cross-section in one wave

The 100 large-town EAs added in ESS2 are a new independent draw, not a
follow-up.  ESS2 DDI (2247), PDF p. 6, "Sampling Procedure", verbatim:

#+begin_quote
ESS is designed to collect panel data in rural and urban areas on a range of household and community level characteristics linked to agricultural activities. The first wave was implemented in 2011-12 and the second wave is implemented in 2013-14. The first wave, ERSS, covered only rural and small town areas. The second wave, ESS, added samples from large town areas. The second wave is nationally representative. The existing panel data (2011/12-2013/14) is only for rural and small towns. Large towns were added during the second wave and, so far, there is only one round.
#+end_quote

Same page: "A total of 3,776 panel households and 1,486 new households (total
5,262 households) were interviewed with a response rate of 96.2 percent."  So a
single library wave =2013-14= mixes a rural/small-town *panel* cohort with an
urban *refreshment* cohort that has no wave-1 antecedent.

This is visible in the config, and is already documented elsewhere in this
file: see "GH #323 ... individual_education (2013-14, 2015-16)", where
=household_id= / =individual_id= are blank for exactly that urban refreshment
sample (5,248 of 23,785 rows in =sect2_hh_w2.dta=).  The documentary statement
above is the *reason* those ids are blank.  Cross-reference, do not duplicate.

Catalog 3823, =series_info=: "The 2018/19 ESS (ESS4) is a new panel. It is not

* plot_features (GH #167)

ESS land characteristics, one row per FIELD, index =(t, i, plot_id)=.
Built with =materialize: make= because it requires a cross-file join
that =data_info.yml= cannot express.

** Source granularity and the holder_id join

ESS records farmland at two levels in the post-planting (pp) round:
  - =sect2_pp_w{N}.dta= : one row per PARCEL, carrying the lasting
    parcel attributes Tenure (acquisition mode) and SoilType.
  - =sect3_pp_w{N}.dta= : one row per FIELD, carrying field-level
    Area and Irrigated.
We emit one row per field and broadcast the parcel attributes onto
each of the parcel's fields via a LEFT JOIN.

*** The join key MUST include holder_id

A single household can host several "holders" (decision-makers), each
of whom numbers their parcels from 1.  Joining on
=(household_id, parcel_id)= alone collides those and INFLATES the
result by +265..+1567 rows/wave with =plot_id= collisions.  The
correct key is =(holder_id, household_id, parcel_id)=.  Verified
empirically: with =holder_id= in the key the merged field count equals
the raw sect3 row count EXACTLY in every wave (0 inflation), and
=plot_id = holder_id_parcel_id_field_id= is globally unique within
=(t, i)=.  Per-wave field rows: W1 32025, W2 33147, W3 33305,
W4 19339, W5 14878 (= 132694 total).

** Household id emitted as =i= (W2/W3 use household_id2)

The emitted =i= must match =sample().i=.  The =sample= and
=household_roster= features index on:
  - W1 (2011-12): =household_id=
  - W2 (2013-14): =household_id2=
  - W3 (2015-16): =household_id2=
  - W4 (2018-19): =household_id=
  - W5 (2021-22): =household_id=
For W2/W3, only =household_id2= overlaps the sample spine (99.3% vs
0.0% for =household_id=).  plot_features therefore EMITS
=household_id2= as =i= for W2/W3 (NOT =household_id=), even though the
sect3<->sect2 JOIN itself uses =household_id= (present in both files
and consistent within a wave).  Overall orphan rate vs =sample()=
after id_walk: 1.4% (W1 0.0%, W2 0.7%, W3 0.7%, W4 4.2%, W5 2.0%) --
a handful of farm households slightly off the cover-page spine.

** GPS redaction

The public ESS plot GPS coordinates are 100% replaced with the literal
string =**CONFIDENTIAL**= in every wave (=pp_s3q06_a/_b= in W2/W3,
=s3q09__Latitude/__Longitude= in W4/W5; W1 has no coordinate columns).
We therefore DEFER Latitude/Longitude -- they are NOT emitted.  Note
the GPS-*measured field area* (square metres; =pp_s3q05_a= W1-W3,
=s3q08= W4-W5) is NOT redacted and is the primary Area source.

** Area and the local-unit gap

Area is GPS square-metres / 10000 -> hectares where present
(=AreaUnit= = 'hectares').  Where only a farmer estimate in a
non-metric local unit (Timad, Kert, Boy, Senga, Tilm, Medeb, Rope,
Ermija) exists, we cannot convert -- =Area= is NaN and =AreaUnit=
carries the native unit name.  GPS area covers ~80-97% of fields per
wave.

*Correction (2026-09-09).*  This section used to say the local-unit
factors "are NOT in the repo".  That is wrong: =ET_local_area_unit_conversion.dta=
has DVC sidecars in 2011-12, 2013-14, 2015-16 and 2018-19 -- three
distinct blobs across those four sidecars (2015-16 and 2018-19 share one
md5) -- and all three are already in the local DVC cache.  A repo-wide
grep of =*.py=, =*.yml=, =*.org= and every =Makefile= finds zero
references to the file: it is held, not wired.  There is no 2021-22
sidecar because the World Bank did not ship the file for W5; EPAR's
do-file says so outright (=EPAR_UW_Ethiopia_ESS_W5.do:324=): "Note that
this file does not exist in the WB W5 download. EPAR borrowed the land
unit conversion factor file from previous ESS waves." Wired by GH #853 --
see the next paragraph.

*Wired 2026-09-09 (GH #853).*  =ethiopia.local_area_unit_factors()= reads
the table and =plot_features_for_wave= applies it to fields with NO GPS
measurement whose only area is a farmer estimate in a local unit.  GPS
stays preferred and is never overridden: *0* previously-non-null =Area=
values changed.

| wave    | fields gaining Area | Area NaN before -> after | implausible (counted, SERVED) |
|---------+---------------------+--------------------------+-------------------------------|
| 2011-12 |                 967 |            5,933 -> 4,966 |                            26 |
| 2013-14 |               1,152 |            2,485 -> 1,333 |                             3 |
| 2015-16 |                 135 |            1,072 ->   937 |                             2 |
| 2018-19 |                  19 |               99 ->    80 |                             2 |
| 2021-22 |                   0 |              138 ->   138 |                             0 |
| TOTAL   |               2,273 |            9,727 -> 7,454 |                            33 |

*2021-22 gains nothing and that is the decision, not an oversight.*  The
WB shipped no file for ESPS-5; EPAR borrows an earlier wave's
(=W5.do:324=) and we do NOT.  Borrowing would mint a 2021-22 =Area= out
of a 2018-19 woreda table with nothing in the returned data saying so.
=local_area_unit_factors('2021-22')= RAISES rather than silently
serving another wave's numbers.  If we ever borrow, it is a documented
decision here and a warning at build time -- 135 W5 fields are what it
would buy.

*Implausibility is SERVED and COUNTED.  Nothing is refused and nothing is
clipped.*  Every row the woreda table can convert is converted and kept,
exactly as the survey's estimate times the World Bank's factor.  The count
-- 33 rows, 1.5% of 2,273 -- is reported to the build log against a single
corpus-consistent reference: *5x the 99th percentile of GPS-measured field
area in the row's own region and wave*.

An earlier version of this code REFUSED such rows (left =Area= NaN) against
the wave's own GPS *maximum*.  Both halves of that were wrong.  The maximum
is set by a single GPS outlier and ran 4.93 / 9.91 / 19.81 / 126.41 /
425.71 ha across the five waves against a p99 of ~1 ha in every one, so the
same converted 18 ha field was refused in 2011-12 and would have been served
in 2013-14 -- a 43x swing in what "refused" meant.  And *a refusal is a clip
by another name*: NaN-ing a row on the strength of a screen deletes the
survey's own answer.  The within-region GPS p99 is by contrast stable --
0.60 to 3.07 ha over all four convertible waves x nine regions -- so a
flagged row means the same thing everywhere.  K = 5 flags 26/3/2/2; K = 10
would flag 3 and say nothing.

*CAVEAT ON THE FACTORS THEMSELVES, measured and NOT adjudicated.*  Converted
areas sit systematically above the GPS distribution even after conditioning
on region: the ratio of the converted median to the GPS median runs *2.4x to
17.6x in every large (wave, region) cell, never below 2.4x* -- e.g. 2011-12
region 3 2.4x, region 7 9.2x; 2013-14 region 3 2.7x; 2015-16 region 7 14.0x;
2018-19 region 1 17.6x.  National ratios (4.9x / 4.0x / 6.2x / 27.3x) overstate
it, so composition explains part but not most.  A selection story is available
(a field the enumerator could not walk is large or remote) and so is a
factor-inflation story; nothing in this repo separates them.  *Treat a
converted =Area= as a coarser measurement than a GPS one, not as its equal.*

*2018-19's cell is thin and unrepresentative -- do not read it as typical.*
Its 19 converted fields are ALL the WB table serves in that wave; they have a
median of 0.90 ha against a wave GPS median of 0.033 ha, 17 of the 19 sit in
region 1, and the set includes a 33-Timad estimate (8.11 ha) and three
8-to-14-Timad estimates in one woreda.  Anyone running =yield_kg= on W4
should know that.

*Coverage is intrinsically partial and the rest is NOT a gap to fill.*
The table has 259 rows: 206 woredas x 4 local units (Timad 198, Boy 33,
Senga 18, Kert 10) in 9 regions.  It says nothing about Tilm, Medeb,
Rope, Ermija or "Other", nor about the woredas it omits.  EPAR fills
those holes from its own weighted zone / region / national medians of
=GPS area / reported area= (=W5.do:657-711=); that is imputation from the
survey's own data, a different and later layer, and it is NOT done here.

*Join on the RAW integer triple =(saq01, saq02, saq03)= x local unit --
and note EPAR's own join is mis-keyed.*  EPAR pads and concatenates
region/zone/woreda into hierarchical strings on both sides, but the two
paddings DISAGREE: their general helper pads the REGION only (=W5.do:198=)
and leaves =saq02=/=saq03= unpadded, so zone 1 of region 1 becomes ="011"=,
while the conversion-file block pads all three (=:330= zone, =:336= woreda)
giving ="0101"=.  Both sides are strings, so Stata raises nothing.  Their
merge reports ==13,312 not matched== and ==1,566 matched== (=:695-696=) and
==// 19 changes== (=:703=); the denominator 14,878 is DERIVED (13,312 +
1,566) and does equal =sect3_pp_w5.dta='s row count, but EPAR never writes
it.  The raw integer triple is the same hierarchy without the collision
risk.

*A converted row keeps its NATIVE =AreaUnit=.*  =Area= non-null vs null
is the record of whether the woreda table could serve the row, and
='hectares'= continues to mean exactly "this area came from the GPS
measurement".  That is what the canonical schema asks for
(=lsms_library/data_info.yml= =plot_features.AreaUnit=: "original survey
unit before conversion to hectares").

** livestock: =SalesValue=, NOT a herd value and NOT a per-animal price

The ESS section-8 roster records no current herd-value question in ANY wave.
The only monetary field it carries is =ls_s8aq60= (W1/W2) / =ls_s8_2q14=
(W4/W5): "What was the total value of sales of [LIVESTOCK] in the last 12
months? (BIRR)".  That column is called *=SalesValue=* (canonical vocabulary
in =lsms_library/data_info.yml=, =Columns: livestock:=).  It was called
=Value= until 2026-08-24.

Three properties, all load-bearing:

- It is *ADDITIVE* over =animal= -- it is a total, so summing per-species rows
  to a household total is legitimate.
- It values *HeadSold*, not HeadCount, so it is a transaction FLOW.  It must
  NOT be summed into a livestock-wealth aggregate; that would be =HerdValue=,
  which Ethiopia does not have.
- It is *NOT a per-animal price*.  Uganda / Malawi / Nigeria's
  =ValuePerAnimal= is a reservation price per head; Ethiopia's is a total.  A
  per-animal sale price here is =SalesValue / HeadSold=.

*Measured, so the distinction is checkable*: among rows where the household
sold nothing, only *2.0%* carry a positive value -- versus *98.0%* in Nigeria
and *92.1%* in Malawi, where the price is asked regardless of any sale.
Correlation with HeadCount does NOT separate these cases (neither a unit price
nor a sales total tracks the herd size), which is why the sold-nothing
conditional and the questionnaire wording are the tests to use.

** W4/W5 permanent crops: a 12-month window (GH #1256, 2026-10-23)

ESS4 folds W1-W3's §12 tree/fruit/root module into §9 and §11 and puts a
PERMANENT crop on a fixed twelve months, not the season (ESS4 post-harvest
questionnaire,
=2018-19/Documentation/2018_19_ethiopian_socioeconomic_survey_post_harvest_agricultural_questionnaire.pdf=):

- §9 Q4, PDF p.3: "Have you harvested any of the [CROP] from this [FIELD]?
  (for permanent crop harvested between March 10, 2018 to March 9, 2019)";
  Q5 is that harvest's quantity -- served as =Quantity=;
- §11 Q1, PDF p.8: "LIST ALL CROPS HARVESTED DURING THIS AGRICULTURAL
  SEASON.  FOR PERMANENT CROPS PLEASE INCLUDE CROP HARVESTED BETWEEN MARCH
  10, 2018 TO MARCH 9, 2019)"; Q7 / Q11 / Q12 sell "the harvested [CROP]" --
  served as =Quantity_sold= / =Value_sold=.  Q2-Q4 (last completed
  production period, harvest in the last 12 months, trees) are §12's
  questions, asked of [TREES/FRUIT/ROOT CROP].

So all three numeric columns are in the window on a permanent-crop row.

*Which crops.*  The instrument names "permanent crops" and lists none.  The
crop row's own flag is the post-planting roster's §4 Q15 (=s4q15=): W4 "IS
THIS CROP A FRUIT TREE CROP?" (answered Yes on 95-99% of coffee, enset,
chat, gesho, banana, mango, avocado rows -- a permanent/tree flag in
practice), W5 variable label "IS THIS CROP A Permanent/TREE CROP?".  *No W5
questionnaire is held*: the W5 window is read from the data alone -- its §11
carries the same block (=s11q02= "completed production period", =s11q03a1=
"harvested in last 12 months") and its §4 the same flag; W5's dates are not
known.  Two alternatives were measured and not used:
- the WB perennial code list (=PERENNIAL_CROP_CODES=, the =perennial=
  column) disagrees with the flag on whole codes -- §4 rows flagged Yes,
  W4 / W5: Berbere 1/235, 1/153; Garlic 0/213, 0/135; Ginger 0/40, 0/25;
  Other tuber 2/126, 5/68; Red Kidney Beans 4/308, 0/316 (GH #1252);
- §11's permanent block being answered (Q2) marks 1,206 W5 lines of
  non-perennial crops, so it is not a crop-type marker there.

*Stamp.*  =crop_production_for_wave= (colmap =pl_permanent='s4q15'=, W4/W5

* shocks: one builder, and what "affected" means (GH #875, 2026-09-12)

Until now Ethiopia =shocks= had *two builders for the same columns, with
different rules*, and which one you got depended on the build path and on
the cache state rather than on the code:

- *YAML path* (what =data_scheme.yml= actually declares -- no
  =materialize:=, so =Wave.grab_data= reads each wave's =data_info.yml=):
  =Decrease -> True=, =Increase -> True=, =Did Not Change -> False=,
  anything else NA.  This is the corpus convention (cf. Malawi 2016-17
  =data_info.yml=) and is what the served table has in fact carried.
- *Script path* (=2011-12,2013-14,2015-16,2018-19/_/shocks.py= plus the
  country concatenator =_/shocks.py=, wired into =_/Makefile=):
  =Increase -> *False*=, =.fillna(False)= (an imputation the YAML does not
  make, turning "not asked / no shock" into a definite "no"), the household
  level named =j= against the declared =(t, i, Shock)=, and
  =Occurrence.fillna(0)=.  =make build country=Ethiopia= could not even
  finish it: there is no 2021-22 wave script, so the concatenator read the
  YAML-written W5 parquet and =change_id= raised =KeyError: 'j'=.

runs; its hashless wave parquets are graded =legacy= by =Wave.grab_data=,

* food_acquired reads Q3/Q5/Q6 directly; =produced= is no longer a residual (GH #874, 2026-09-12)

** What was served before, and why it was wrong

The wave scripts read only Q2 (total consumed), Q3 (purchased) and Q4
(spend).  =ethiopia.food_acquired= then derived
=Produced = (Q2 - Q3).clip(lower=0)= and handed that to
=build_transforms.food_acquired_to_canonical=, whose contract inverts it:
=purchased = Quantity - Produced=.  So the table served

: produced  = clip(Q2 - Q3, 0)      -- a RESIDUAL, never an answer
: purchased = min(Q2, Q3)           -- not Q3

even though SECTION 5A / 6A asks each source directly (see "Food prices:
what the ESS asks" above for the verbatim six questions).  Consequences:
gifts and food aid (Q6) were served as *own production*; Ethiopia had no
=s='inkind'= row at all, in any wave; a household that bought more than it
ate that week had its purchase truncated to Q2 while keeping the full Q4
spend; and Q5/Q6 -- populated on essentially every consumed row -- were
never read.  Cross-country this meant =Feature('food_acquired')= mixed
Nigeria's reported own production with Ethiopia's residual under one
=s='produced'= label.

** What is served now

One long-form row per REPORTED source, each carrying *its own unit code*
(=hh_s5aq0{3,5,6}_b= / =s6aq0{3,5,6}b=); nothing is derived, nothing is
clipped, nothing is min'd:

| s         | Quantity | unit | Expenditure |
|-----------+----------+------+-------------|
| purchased | Q3       | Q3's | Q4          |
| produced  | Q5       | Q5's | NaN         |
| inkind    | Q6       | Q6's | NaN         |

Q2 is read but NOT served as a row -- it is the sum of the three, and it is
used only to screen self-contradictory answers.  Expenditure stays NaN on
=produced= / =inkind= because *the ESS asks no value of own consumption*
(documented above); Q4 is the module's only monetary field.

The old single-=u= approximation is gone with the helper that required it.
It was disclosed in the docstring as a ~0.3% accuracy loss, and *in 2011-12
that understated it by orders of magnitude*: 99 of 19,266 positive Q3 rows
and 69 of 10,226 positive Q5 rows disagree with the Q2 unit, and they carry
17.0M and 40.4M of those columns' raw totals respectively -- they are
1000x data-entry slips ("Onion, Q2 = 1,400 Gram, Q3 = 1,400,000 Tuba";
"Sorghum, Q2 = 10,000, Q5 = 10,600,000").  =min(Q2, Q3)= was accidentally
suppressing them.  They are now served as the survey recorded them.
