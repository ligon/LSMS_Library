* THE LESSON FROM v0.10.1 (read this before the next release)
=poetry-dynamic-versioning= REWRITES =pyproject.toml= to build and restores it
after.  A killed build never restores, and it changes *three coupled things*:

: dynamic = ["version"]  ->  dynamic = []
: version = "0.0.0"      ->  version = "<computed>"   (moved into [project])
: enable = true          ->  enable = false

v0.10.1 took three attempts because I reverted only the middle one and wrote a
guard that checked only the middle one -- so the guard passed on a broken file
and certified it clean.  =publish.yml= then failed with "Building 0.0.0 from
v0.10.1".  Nothing reached PyPI (build failed, publish skipped).

=tests/test_version_placeholder.py= now asserts all three, verified against the
actual broken file.  *A guard covering one of three coupled invariants is worse
than none.*

Practical rule: *do not run =poetry build= on the condo slice.*  It gets killed
(exit 144) partway and leaves the mutation.  =poetry run= and =poetry version=
are fine, though they too can be killed under load -- an EMPTY =poetry version
-s= means "killed", not "version is wrong"; re-run with a longer timeout.  CI
builds the wheel from the tag anyway.  To inspect wheel contents locally, drive
=poetry.core.masonry.api.build_wheel= directly (no venv creation, no mutation).
