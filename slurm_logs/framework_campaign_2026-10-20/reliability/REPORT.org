* Concrete protection proposal, unapplied

The read-only repository API identifies owner.type=User and visibility=public.
GitHub's documented merge queue availability is public organization-owned repositories or private organization repositories with Enterprise Cloud; present ownership therefore prevents the queue route assumed by PR #1049.
Official source: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue .

Minimal available route, for human approval:
1. Change the =data-tests= job condition in ci.yml:427 to also run on =github.event_name == 'pull_request' && github.base_ref == 'development'=.
2. Keep the existing credential-gate assertion, so missing credentials are a failure rather than a green skip.
3. Add =data-tests= to ruleset25124452's required checks after observing a genuine successful PR-triggered run.

=ruleset-change.json= is the exact one-entry JSON Patch against the captured current state.
=proposed-development-ruleset.json= is the complete proposed PUT payload, preserving name, target, enforcement, conditions, deletion/non-fast-forward rules, existing unit-tests requirement, strict=false, do_not_enforce_on_create=false and the role5 always-bypass.
No GitHub protection settings were changed; permission/protection changes need explicit human approval.
The proposal generator is runnable and makes no API calls.
Refresh the captured ruleset before any approved application to avoid overwriting a concurrent administrator edit.

Simply requiring the current skipped =data-tests= job does not close #932: GitHub accepts skipped required jobs as success.
Official source: https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-jobs-with-conditions .
With PR execution enabled, same-repository development PRs obtain credentialed checks; fork PRs receive no secrets and must fail the credential assertion until a maintainer reviews and imports the exact changes into a trusted same-repository PR branch.
Do not bypass this by executing untrusted fork code with secrets under pull_request_target.
A manual workflow_dispatch remains useful release evidence but does not satisfy a PR required check under GitHub's documented eligible-event rule.
Official source: https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks .

Preserving strict=false and administrator bypass means the proposal does not prohibit every direct/bypass merge or guarantee testing against the newest base.
Requiring up-to-date branches, removing bypass, requiring PRs or moving repository ownership would be separate permission/policy decisions.
Before0.16.0, the exact final integration head should still receive the credentialed full run and Windows cold build.
