* =reproduce.py= --- the defect, and the fix's witness

=Country._relabel_j= built its rename dict with

#+begin_example
  rdict = table[['Preferred Label', target]].dropna().set_index(...)[target].to_dict()
#+end_example

The =.dropna()= is there so a food the requested column does not label keeps
its Preferred Label.  It only catches =NaN=.  =all_dfs_from_orgfile= returns
*empty strings* for blank org cells, so in a table whose blanks parse that way
every unlabelled food was renamed to the empty string, and because =food_expenditures= /
=food_quantities= call =_relabel_j= with =reaggregate=True=, they were all
*summed into one unnamed =j= bucket*.

Measured on =Country('GhanaLSS').food_expenditures()=, warm, before the fix:

| =labels==  |      rows | Expenditure | blank =j= rows | blank rows | distinct PL | *served foods merged* |
|------------+-----------+-------------+----------------+------------+-------------+-----------------------|
| (none)     | 1,404,564 | 15,637,502,178 |        --- |        --- |         --- | ---                   |
| =1987-88=  |   896,764 | conserved   |         55,314 |        146 |         142 | *129 -> 1*            |
| =1991-92=  | 1,166,544 | conserved   |         54,758 |         90 |          85 | 77 -> 1               |
| =2016-17=  | 1,298,082 | conserved   |         48,264 |         37 |          34 | 29 -> 1               |
| =FCT Code= | 1,268,800 | conserved   |         46,092 |         24 |          24 | 21 -> 1               |

*Three counts differ and only the last is "foods merged"*: blank crosswalk
ROWS, then the distinct Preferred Labels the old dict mapped to the empty
string, then those that actually appear in the served frame.  The first version
of this README quoted the row count as the food count in all four rows.

*Expenditure is conserved in every case*, which is precisely why the defect was
silent: nothing was lost, it was merged, and a conservation check --- the
obvious test --- passes either way.  Row identity is what witnesses it, which
is why =tests/test_food_labels.py= asserts on the surviving row values and not
on the total.

Corpus-wide, *13* =(country, column)= pairs merge at least one food: GhanaLSS
all eight columns (worst =1988-89=, 143 distinct labels), GhanaSPS four
(=FCT Label= 77 of 98), Panama one.  It bit exactly where =.dropna()= had
nothing to catch: GhanaLSS's wave columns carry 0 NaN and 146 empty strings,
while Mali's carry 127 real NaN.

*Mali is NOT affected, and an earlier version of this file said it was* --
while also saying, two sentences later, that Mali's NaN were always handled.
Both could not be true.  The sweep had counted blank-Preferred-Label rows,
which key the empty string to itself and merge nothing; excluding them drops
Mali's three columns and GhanaSPS's =Food Codes= and takes 17 pairs to 13.
Those rows are themselves a parse artefact: =all_dfs_from_orgfile= reads Mali's
=| # crop_production ...= comment rows and GhanaSPS's trailing padding rows as
data.

*Not yet pinned*: why blanks parse as =NaN= in some tables and as empty strings
in others.  Both files are uniformly padded, so raggedness is not the
explanation.  The fix does not depend on the answer --- blank is treated as
absent either way --- but the question is open.

*A third behaviour, deliberate.*  =to_dict()= was last-wins over ALL rows
including blank ones, so a Preferred Label duplicated with a real label early
and a blank later served the empty string; filtering before the dict makes the
sibling row's real label win.  Six served foods move under =1987-88=
(=Rice=, =Sugar=, =Cassava (flour)=, ...).  That follows the =.dropna()=
principle, but "keeps its Preferred Label" does not describe it, so it has its
own test.  Related and undocumented: GhanaLSS's crosswalk is many-to-one, so
for the 10 duplicated Preferred Labels the reverse lookup is arbitrary ---
=Cassava (flour)=, =Rice= and =Sugar= each carry two distinct 2016-17 labels
and last-in-file silently wins.

*Cache cost is asymmetric across the two commits.*  The code fix moves *0 of
119* country table hashes: =_relabel_j= is not reached from =_finalize_result=
at all, but from the generated accessor in =Country.__getattr__= after
=_aggregate_wave_data= returns, and no =@build_transform=-tagged callable
references it.  The prose commit moves *17 of 119* --- every GhanaLSS table ---
because =Wave._input_hash= folds =corg:categorical_mapping.org=.  Merging this
branch therefore costs a GhanaLSS re-warm.  =CONTENTS.org= is the one =.org=
the hasher skips (=_ORG_HASH_SKIP=), so prose that does not have to live beside
the table belongs there.

*Relation to GH #787.*  That issue's finding 2 is the neighbouring case, a =j=
value *absent* from the rename dict passing through unrenamed.  This is a =j=
value *present* in it and mapped to nothing.  #787 could not have seen it: its
table A puts GhanaLSS and GhanaSPS in the "no food label table, every =labels==
raises" bucket, which was true when it was written.  GH #783 / #789 then
migrated six stranded vocabularies *into* =categorical_mapping.org=, making
=labels== reachable for those countries for the first time --- so the two
countries with the worst blank counts are exactly the two that migration newly
enabled.

* =verify_ghanalss_aggregate_prose.py= --- the six claims in the file's own prose

Checks every measured claim in the "No =Aggregate Label= column, deliberately"
passage of =GhanaLSS/_/categorical_mapping.org=.  Four were exact; two had gone
stale and are corrected in the same commit as this directory:

| claim                                  | when written | now  |
|----------------------------------------+--------------+------|
| no =Aggregate Label= on country table  | true         | true |
| seven wave tables carry one            | 7            | 7    |
| 195 distinct Preferred Labels          | 195          | 195  |
| 9 appear in no wave table              | 9            | 9    |
| =labels='Aggregate'= raises            | true         | true |
| *N take two Aggregate values*          | *14*         | *13* |
| *a wave value carries mojibake*        | *yes*        | *no* |

The two are one event.  At the prose's own commit (=98a0b7a21=) the count was
14 and *the fourteenth was the mojibake row* --- 2012-13 code 262's Aggregate
read =Cooked Rice and Stew= followed by two mojibake characters, against code
254's clean twin, so the label carried two Aggregate values.  =5dd3720fe=
repaired it on a *parallel branch* (earlier in wall-clock time, not an
ancestor), which merged in afterwards.  The prose was never revisited;
=CONTENTS.org= records the repair, so the two files had been contradicting each
other since.

The passage's conclusion --- withhold the column --- survives unchanged.  13
conflicts and 9 orphans is ample.  Only the evidence drifted.
