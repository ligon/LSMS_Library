#+title: Draft: report to the World Bank LSMS team -- UNPS 2015-16 AGSEC5 sale values scaled by 1/100
#+author: drafted by Sue (Claude Fable 5.1) for Ethan Ligon to review and send
#+date: 2026-09-08

To: lsms@worldbank.org
Subject: UGA_2015_UNPS_v02 (catalog 3460): AGSEC5A/AGSEC5B sale values (a5aq8, a5bq8) appear divided by 100

Dear LSMS team,

While comparing farm-gate and market prices across the Uganda National Panel
Survey waves we found that the crop sale values in the 2015-16 agriculture
files are two orders of magnitude below every neighbouring wave, and the
pattern in the data points to a processing step rather than to the
questionnaire or to respondents.  Details, in case they are useful to you:

1. In UGA_2015_UNPS_v02_M_STATA14, AGSEC5A.dta and AGSEC5B.dta store a5aq8 and
   a5bq8 ("What was the value? UShs") as Stata doubles; in the 2010-11, 2011-12,
   2013-14, 2018-19 and 2019-20 releases the same variables are int32.  Of the
   432 variables common to the 2013-14 and 2015-16 AGSEC files, these two are
   the only ones whose storage type changed.

2. a5aq8 x 100 is an exact integer on 100.00% of the 6,906 sale records, and
   its "roundness" reproduces the 2013-14 raw column: the share of values
   divisible by 100 / 1,000 / 10,000 is 0.9949 / 0.9510 / 0.6690 in 2015-16 (x100)
   against 0.9988 / 0.9561 / 0.6701 in 2013-14.  Median a5aq8 is 850 against
   80,000 in 2013-14; the maximum is 80,000 against 10,277,500.

3. On records whose sold unit is kilograms, the implied price is 10 UShs/kg
   (median) against 1,000 (2011-12), 1,000 (2013-14) and 1,300 (2019-20);
   99.25% of those records imply under 100 UShs/kg.  The 2015-16 consumption
   module values maize at about 700 UShs/kg in the same households, so this is
   not a currency or price-level effect.

4. The questionnaire text is unchanged: unps_2015_16_agriculture_qx.pdf,
   Section 5A p.13 and 5B p.21, reads "What was the value?  UShs", identical to
   the 2013-14 instrument.  The DDI documentation for catalog 3460 has no
   variable-level codebook and an empty Data Processing section, so we could
   not find a documented rescaling.

5. The file we hold is byte-identical to the currently distributed release
   (AGSEC5A.dta md5 3117b28c356a480a896701efd7779b47), so the issue is in the
   live v02 distribution.  Separately, UGA_2015_UNPS_v02_M_CSV.zip is served
   truncated (2,943,685 bytes; the zip central directory lies past EOF; two
   downloads).

Two smaller observations from the same files: the 5A file is labelled "second
season of 2014" and 5B "first season of 2015" (offset from the other waves'
labelling), and A5AQ7D is upper-case where every other wave uses lower-case.

Your own harmonised LSMS-ISA dataset already treats these variables this way:
in the harmonisation code (lsms-worldbank/LSMS-ISA-harmonised-dataset,
UGA_UNPS5.do line 272 and UGA_UNPS5_S2.do line 280) the sale value is built
as `gen harvest_sold_value = a5aq8 * 100` -- the only Uganda wave that is
rescaled, in all three releases -- and the released wave-5 median of 541.7
UShs/kg sits between wave 4 (500.0) and wave 7 (600.0).  So the correction
exists inside the Bank; what is missing is that it never reached the
distributed microdata or its documentation, and other users of catalog 3460
have no way to know.  At least one widely used derived product built directly
on the raw files (the Evans School EPAR Agricultural Indicator Curation,
report 335, Uganda UNPS W5) reads a5aq8 unscaled, and its published wave-5
land productivity is about one hundredth of wave 4's as a result.

We are applying the same x100 in our own pipeline
(https://github.com/ligon/LSMS_Library/issues/829).  Could the correction be
pushed into the catalog 3460 distribution -- a corrected v03, or failing that
a note in the study documentation and a comment in the harmonisation
do-file -- so that the next user is not caught by it?

With thanks for the surveys,
