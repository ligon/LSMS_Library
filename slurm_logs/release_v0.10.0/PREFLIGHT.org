** Upgrade hazard: not one, and why
A user upgrading v0.9.1 -> v0.10.0 does *not* hit this.  The null-read guard
edits =get_dataframe=, which moves every table's =lsms_cache_hash= (37/37
probed), so the whole corpus rebuilds cold on first use.  The staleness here was
local: a cache built from mid-range =development= code, where no such
invalidation separates it from the tip.

* Residual: tests/test_pakistan_cluster_features.py::test_extraction_is_cluster_grain
NOT release-blocking; the delivered data is correct (300 clusters, =(t, v)=
grain, Region + Rural).  The test asserts the *wave-level* parquet exists as a
proxy for "the extraction is cluster-grain".  It does not exist because
=Pakistan/_/= ships no =Makefile= while =data_scheme.yml= declares
=materialize: make=, so =make= has no rule and the country table is satisfied by
the YAML path without the wave script ever running.

This is a widespread pre-existing pattern, not something this release
introduced: *14 countries* declare =materialize: make= with no =_/Makefile=
(Albania, Benin, Guinea-Bissau, Guyana, India, Iraq, Kazakhstan, Kosovo,
Liberia, Pakistan, Serbia and Montenegro, South Africa, Tajikistan,
Timor-Leste).  =country.py='s =run_make_target= has a =try_script= Python
fallback for when =make= fails, but whether it ran here is *not* established --
the absent wave parquet is evidence against it, since that script writes one.
Stating observables only: =make= is declared, no Makefile exists, the wave
parquet is absent, and the delivered table is correct.  Which path satisfied the
country-level build is left open in GH #740 rather than guessed at.
