* Scope and method

Read-only census of every SERVED value (a column, or an index value such as
u) in the Ethiopia and Nigeria tables that is produced by something other
than a rename / decode / re-index of one raw field.  Inputs read as text:
all 77 + 68 wave scripts under lsms_library/countries/{Ethiopia,Nigeria},
the country modules _/ethiopia.py (3000 lines) and _/nigeria.py (2259
lines), every _/*.py, every mapping.py and data_info.yml, both
_/data_scheme.yml, both _/Makefile, both _/CONTENTS.org (grep by variable
name), lsms_library/build_transforms.py and the relevant parts of
local_tools.py / country.py / transformations.py.  Nothing was executed:
no Country()/Feature() call, no wave script, no dvc CLI, no edit to a
tracked file.  GitNexus MCP did not connect; grep/sed were the declared
substitute.

Framework derived tables (food_expenditures / food_prices /
food_quantities / household_characteristics, kg inference in
transformations.conversion_to_kgs, GPS collapse in
country._collapse_to_cluster_grain, weight normalisation) are another
agent's and are only mentioned where a country script (a) feeds them a
country-side input, or (b) computes its own version.

Kinds: the brief's list (scale / annualise / product / ratio /
categorical->number / impute / encoding / selection / guard) plus two the
brief has no slot for and which this group needs:

- sum :: a served number that is a sum or a signed difference over several
  raw fields or several raw ROWS (person-days, PP+PH totals, sub-code
  folds, residuals).
- window :: no arithmetic at all; the served number is a raw answer whose
  RECALL WINDOW or question semantics differ from the column's name or from
  the same column in a sibling wave.  These are the 12B-shaped rows.

Ids E1..E39 are Ethiopia (E39 is an uncounted pointer row), N1..N38 Nigeria; the notes in section 2 use them.
"pp"/"ph" = post-planting / post-harvest round.  Line numbers are on the
development branch at commit 36efe55c.

* 2. Per-derivation notes (baked assumptions; are the raw inputs recoverable from the served table?)

** Ethiopia

- E1 / E2 / E3 (food_acquired residual) :: Assumes total - purchased == own
  production.  The questionnaire (CONTENTS.org:1467-1495) asks total (Q2),
  purchased (Q3), own-produced (Q5) and gift (Q6) separately; only Q2 and
  Q3 are read, so 'produced' absorbs gifts, food aid and any rounding
  disagreement between Q2 and Q3.  Because the framework helper then
  recomputes purchased as Q2 - Produced, the served purchased Quantity is
  min(Q2, Q3): a household reporting Q3 > Q2 (purchased more than it ate)
  is served Q2 with the Q3 Expenditure riding on it.  A Q2 = NaN, Q3 > 0
  row is served purchased = 0.  Not recoverable: Q2 can be rebuilt as
  purchased + produced only where Q3 <= Q2; Q3 itself is gone whenever it
  exceeded Q2; Q5 and Q6 were never read; the purchased row's own unit
  (hh_s5aq03_b) is gone.  Disclosed as a design decision in the DESIGN doc
  and the docstring, but the min() consequence is stated nowhere.  Nigeria
  N1 shows the alternative (each source's reported quantity) is available
  in the same survey family.

- E4 / E5 (plot area) :: E4 is a pure scale (sqm -> ha) and is recoverable.
  E5 bakes in the WB woreda-level conversion table, a national fallback
  where the woreda row is missing, and a region-99 pooled row; the
  farmer's numeric estimate (pp_s3q02_a) is NOT served, only its unit name
  in AreaUnit, so a converted Area cannot be undone.  The 5x plausibility
  screen counts and names but never alters.  2021-22 non-GPS fields stay
  NA rather than borrowing a table -- a wave-varying rule for the same
  column.  AreaUnit means two different things on GPS rows ('hectares')
  and converted rows (native unit name while Area is in hectares).

- E6 / E7 / E10 (one raw field, three served booleans) :: pp_s3q03 feeds
  Fallow (== 3, plot_features), intercropped (== 2, W1 crop_production)
  and the cultivated filter (in {1, 2}, plot_labor).  Not a defect, but a
  registry keyed on served column must name the same raw field three
  times with three predicates.  E7's yes-code flip (2 = Yes in W1-W3,
  1 = Yes in W4-W5) is passed from the wave script, so the rule is
  correct but lives in two files per wave.

- E8 (Ethiopian -> Gregorian month) :: Pagume (13) mapped to September
  with Meskerem; the year is not carried, so a harvest reported in
  Pagume/Meskerem straddling the Gregorian year cannot be re-dated.
  Recoverable up to that fold.  Nigeria N8 serves 'YYYY-MM' strings in
  the same column.

- E9 (perennial) :: hard-coded WB crop-code list; recoverable (j is
  served).

- E11 / E12 / E15 (u constants and fills) :: W1 harvest u := 'Kg' drops
  the grams remainder (ph_s9q12_b), a sub-kilogram loss on every W1 row.
  W1-W2 sale unit := 'Kg' is an assumption the W3+ files contradict by
  shipping a unit column.  'Other (Specify)' is a fill of an INDEX value:
  a row whose unit was blank is indistinguishable from one whose unit was
  recorded as Other.  Not recoverable.

- E13 / E14 (sales) :: sold-flag No -> 0.0 conflates "did not sell" with
  "sold zero"; the single-plot attach rule means a holder growing the
  same crop on two plots gets NA sales on both, so sales are
  systematically missing for larger holders.  Value_sold is summed over
  a (holder, crop) group of source rows: the served number is not any
  raw row.  Raw sales not recoverable from the served table.

- E16 / E17 (seed kg + g) :: kg + g * 0.001 in W1 and W3 only; W2 and
  W4-W5 are kg-only, so the sub-kilogram precision differs by wave.
  Quantity_purchased := 0.0 where the purchase flag is No (same
  conflation as E13), and the (holder, crop) -> single-plot attach rule
  as E14.

- E18 / E19 / E20 :: Improved yes-codes widen from (2,) to (2, 3, 4) at
  W4 (a categorical->number rule that changes meaning between waves);
  W4-W5 seed rows with s4q15 == 1 are dropped (a row filter that alters
  which plots appear); fertilizer Quantity == 0 -> NA turns a reported
  zero into missing.

- E21 (livestock species sums) :: Bulls / Oxen / Cows / Heifers / Calves
  -> Cattle, summed over holders.  The raw sub-code breakdown is not
  served; the all-zero drop removes households that reported owning none.
  Not recoverable.

- E22 / E23 (anthropometry) :: Height > 200 cm -> NA is a WB rule on unit
  errors; the raw value is gone.  Age_months = years * 12 discards the
  months remainder whenever years is present (a 2 y 7 m child is served
  24 months), and falls back to the months column only where years is
  missing.  Recoverable to the year, not the month.

- E24 / E25 / E26 (plot_labor) :: PersonDays are products summed over
  3 hired groups x 2 rounds (+ member slots for family), so no served
  number is a raw answer; the rule d.where(n != 0, 0) * n treats a
  reported day count with zero workers as zero.  Wage is a MEAN of daily
  wages across men / women / children where n != 0, then averaged again
  across pp and ph; it is not weighted by n or d and ignores W5 in-kind
  wages.  The member-slot count changes by wave (6/8, 7/8, 4/4).  Not
  recoverable.

- E27 / E28 (people_last7days) :: W1-W3 dummies are hours > 0, so a
  person who worked with zero recorded hours is served not-working; W4-W5
  use the survey's yes/no.  Industry is blanked where the employment gate
  is No or missing.

- E29 / E30 (community prices) :: whole + cents / 100 and whole +
  decimal / 1000 are exact and recoverable; the W4-W5 availability gate
  and the keep-first dedup are selections that drop rows silently.

- E31 (food_coping) :: Days outside 0..7 -> NA; the raw value is gone.

- E32 (shocks, two live rules) :: The YAML mapping serves Increase -> True
  (an INCREASE in income counts as "affected"); the legacy wave scripts
  and _/shocks.py serve Increase -> False and fill missing with False /
  Occurrence 0.  data_scheme.yml declares no materialize for shocks, so
  the YAML path is authoritative on a cold build, but the Makefile still
  builds the script path, and a hashless script-written L2-wave parquet
  grades legacy and is trusted once.  Which rule a warm cache is serving
  cannot be told from the served table.  Neither rule is documented.

- E33 (Age, W2 only) :: Ethiopian-calendar DOB converted to Gregorian,
  then differenced against a synthetic mid-year interview date
  ('07/01/2013'); precedence DOB > corrected age > years > months // 12.
  W1 and W3 never see a DOB.  So the same Age column is DOB-precise
  (fractional, then rounded by _enforce_canonical_dtypes) in W2 and
  integer-reported elsewhere.  Not recoverable to the raw fields.

- E34 (FIES_score) :: sum of 8 booleans, NA only if all 8 are NA -- a
  household answering 3 of 8 gets a score over 3.

- E35 (panel_weight copy) :: served panel_weight is not a longitudinal
  weight; a user reading the column name is misled in every Ethiopia
  wave.

- E36 (nutrition) :: a matrix product of framework food_quantities (kg)
  with an FCT scaled 100 g -> 1 kg, with missing nutrients set to 0.
  Depends on the framework kg inference (GH #850) and therefore moved
  with it.  The script also carries a literal API key (not reproduced
  here).

- E37 / E38 (conversion factors) :: E37 is a dead artifact (no live
  consumer; the docstring at ethiopia.py:282 still names it).  E38 is a
  callable the analyst may apply; the duplicate-resolution and
  Leafy-Greens drops are baked into that callable, not into any served
  table.

- E39 (MonthsAway / WeeksAway pointer) :: served raw in both column
  names; the months-present conversion is the framework's.  What is
  country-side is the split itself: the same residence question is a
  months column through W3 and a weeks column from W4, so any registry
  entry for the roster residence variable is (country, wave)-grain.

** Nigeria

- N1 / N2 / N3 (purchased quantity, three meanings) :: W1 serves
  "consumption that came from purchases" (7 d), W2-W3 serve "quantity
  purchased" (7 d, an acquisition that can exceed consumption), W4 serves
  "quantity of the most recent purchase within 30 days" with the amount
  paid for THAT purchase as Expenditure.  All three sit under the same
  (t, i, j, s='purchased') key with the same column names, and in W4 the
  produced / inkind rows of the same household-item are 7-day
  consumption.  No arithmetic happened; nothing in the served table says
  which window a row is.  W1 and Ethiopia E2 are comparable; W2-W4 are
  not, in two different ways.  Disclosed in data_scheme.yml and
  CONTENTS.org for W4, in the W2 docstring for W2-W3.

- N4 / N5 :: Quantity_kg = Quantity * survey factor is recoverable
  (both operands served).  u.fillna('None') is an index-value fill:
  rows whose unit was blank cannot be told from a unit literally coded
  None.

- N6 (KgFactor sentinel) :: 0 -> NA assumes the survey's zero is
  "no factor", not "zero kilograms".  Recoverable (NA rows are exactly
  the zeros), but the unwired sibling factors (sa3iq6d_conv, sa3iq15_conv,
  sa3iiq1_conv) mean the served factor may not pair with the container
  the harvest was reported in.

- N7 (_canon_unit) :: size qualifiers stripped from u in three tables but
  not in food_acquired.  A 'Large Derica' and a 'Small Derica' harvest
  become one u, and a kg factor keyed on the stripped label is wrong for
  one of them.  Not recoverable.  CONTENTS.org documents the
  community_prices instance (the size field is unread) but not the crop
  and inputs instances.

- N8 / N9 / N10 / N11 :: 'YYYY-MM' strings (recoverable); sale unit
  assumed equal to harvest unit (sa3q11b unread -- not recoverable);
  intercropped from a 7-code planting variable collapsed to a boolean
  (recoverable only as the boolean); keep-first dedup (rows dropped
  silently).

- N12 / N13 / N14 / N15 / N16 (plot_inputs) :: the sum-or-largest
  channel rule means the served seed Quantity is either a sum or one of
  four channels, and the table does not say which.  Purchased is a sum
  over commercial channels.  Fertilizer u := 'Kg' in W1-W2 is an
  assumption the questionnaire does not state (the quantity has no unit
  column).  Animal traction Quantity = two summed fields with u :=
  'days'.  Improved uses three different code sets across W3 / W4 / W5,
  and in W4 a certified-seed question overrides the improved question.
  None recoverable beyond the boolean / the sum.

- N17 (livestock) :: keep-if-own-or-any-nonzero drops households that
  answered the module with all zeros; keep-largest on duplicates is a
  reducer applied to a broken key.

- N18 / N19 / N20 / N21 (plot_features) :: acre / ha / sqm are converted,
  every other farmer unit (heaps, ridges, stands, plots) -> NA -- unlike
  Ethiopia E5, which converts them with a shipped table.  Area > 1000 ha
  -> NA discards the raw estimate.  AreaUnit is always the farmer's unit
  label, so on a GPS row Area is hectares while AreaUnit says (e.g.)
  'Heaps'; Ethiopia E4 writes 'hectares' on those rows.  Fallow's W1
  override from a second question is a wave-only rule.

- N22 (median of three readings) :: mirrors the WB; the three raw
  readings are not served, so the measurement error the median removed
  cannot be recovered.

- N23 / N24 / N25 (plot_labor) :: family days (n * d).where(n.notna(),
  d) treats a missing worker count as "the days are the total"; W4 reads
  a shipped total instead of computing one, so the same column is
  computed in W1-W3 and copied in W4.  Wage = sum n * d * w is the TOTAL
  cash paid on the plot, while Ethiopia's Wage in the same column is a
  MEAN daily wage.  Neither the daily wage nor the components are
  recoverable.  W5 is unwired (documented partial).

- N26 / N27 / N28 / N29 / N30 (people_last7days) :: the joblogic
  allocation gives ALL of a person's hours (two jobs summed) to one
  activity by precedence farm > wage > self-business; a farmer with a
  wage job is served zero wage hours.  Non-working-age persons are
  served zeros, not NA, so a mean over the table includes children as
  zero-hour workers.  W3-W4 read direct hours; W5 reads a different
  module with different rules (OR of two questions; a code > 0 test).
  Not recoverable.

- N31 / N32 (community_prices) :: W1-W2 u is imputed from a hand-typed
  questionnaire table keyed by item, and j = code // 10 -- both are
  encodings of an assumption about the shipped file's coding.  The
  dedup is .first() while the docstring promises a median: a disclosure
  that is wrong.

- N33 (nonfood windows) :: 7-day, 30-day and longer recall amounts are
  pooled into one Expenditure with no window column; the same 12B shape
  as N3, on a table the framework does not annualise.  Recorded as
  WAITING in CONTENTS.org since the fix needs a RecallWindow column.

- N34 (Age) :: DOB availability differs by wave and by round (W4 has
  year only; W5 has month + a survey-CALCULATED year and no day), so
  the DOB-vs-reported precedence in age_handler produces a
  fractional-precision Age in some rounds and an integer one in others,
  and in W5 the "DOB-derived" value is derived from a field the survey
  itself derived from reported age.  Sentinel clamps discard the raw
  value.  Not recoverable.

- N35 / N36 :: date composition (recoverable); panel_weight := weight
  (same misnomer as E35, W1 only).

- N37 / N38 (dead scripts) :: not in data_scheme, and the Makefile's
  food_expenditures / food_quantities targets depend on wave scripts that

** What would not fit a per-row Derivation column + registry

- Many-row inputs.  E14 (sales summed over a (holder, crop) group and
  attached to one plot), E21 (species sums over sub-codes and holders),
  E24-E26 / N23-N25 (products summed over groups, slots and rounds), E36
  (a matrix product), N12 (sum-or-largest over channels): the retrieval
  callable behind a registry key must return a FRAME of source rows, not
  a value, and for N12 must also say which branch fired.
- Derivations on INDEX values.  E3 (u of the total stamped on the
  purchased row), E11 / E12 / N14 (u := 'Kg'), E15 / N5 ('Other
  (Specify)' / 'None' fills), N7 (size stripped from u), N31 (u imputed
  per item).  A column describes a cell; these describe the key.  The
  registry needs an entry per index LEVEL as well as per column.
- Build-path ambiguity.  E32: two rules for one column, selected by
  which path wrote the cache.  A per-row stamp is only truthful if
  written at build time by the path that actually ran; a registry keyed
  on (country, table, column) cannot express "depends on cache state".
- Read-time framework derivations riding on country tables.  E2's
  min() arises from composing a country script with
  build_transforms.food_acquired_to_canonical; E36 depends on the GH #850
  kg inference; a parquet-stamped column cannot carry a rule applied
  after the parquet is read.  The registry entry must name both layers.
- Window / meaning attributes with no arithmetic.  N2, N3, N33 (and the
  cross-country meaning splits above): a Derivation key that names a
  FUNCTION has nothing to point at.  The design needs a window /
  question-semantics field (per row in N3, since the three s values of
  one household-item differ) rather than only a function key.
- Wave-varying rules for one column.  The list above has 20-odd cases
  where the rule is (country, wave, column)-grain; a registry keyed on
  (country, table, column) would have to carry a wave dimension or the
  per-row stamp would have to name the wave's rule id.
- One raw field, several predicates.  pp_s3q03 -> Fallow (== 3),
  intercropped (== 2), cultivated filter (in {1, 2}) (E6 / E10 / E26): a
  registry keyed on raw field is one-to-many; keyed on served column it
  repeats the field.  Either is fine, but the design must pick.
- Row filters and dedups (E19, E30, N11, N17, N21 W1 override, the
  all-zero drops): they change WHICH rows exist, so there is no row to
  stamp; only a table-level entry can record them.
- Dead scripts (N37, N38, E37): a registry built from what is served
  will not see them, and the shadowing history says they are the ones
  that bite.
