* 2. Per-derivation notes

** B1 -- the >1e99 sentinel
Fires per source file inside =get_data=: it takes the maximum over every
non-object/non-datetime/non-category column and, if that single value exceeds
1e99, does =df.replace(na, np.nan)= over the WHOLE frame.  One value, all
columns.  The raw value is gone from the wave parquet; nothing counts how
many cells it touched.  It is a build-path guard that alters values, disclosed
by one un-typed =UserWarning=.

** B2 -- age_handler: five derivations in one callable
It is called from the wave formatting layer (=mapping.py= / =<wave>.py=
functions referenced from =data_info.yml='s =myvars=, or from the wave
=household_roster.py= scripts; Nigeria/Ethiopia/Uganda wrap it in
=_age_helpers.py=), so it runs inside =df_data_grabber= and its output is the
=Age= that lands in the L2-wave parquet.  The raw components are NOT
recoverable from =household_roster=: the served table carries one =Age= and
no DOB, no reported-age column, no flag saying which branch fired.  The five
rules, each of which the brief would count separately:
- screen: reported age outside [0,120] or a date part outside [0,2100) is
  treated as absent (this is what retired the per-wave =_clean_age= lambdas);
- impute: an invalid or missing day of birth becomes the 15th (=_safe_dob=,
  and the year+month-only branch);
- ratio: fractional age = days / 365.25, rounded to 2 dp;
- selection: when both a plausible reported age and a DOB age exist, the DOB
  age wins if =abs(int(reported) - dob_age) <= 1=, otherwise =int(reported)=
  (the reported age is TRUNCATED, not rounded, before the comparison);
- fallback: =interview_year - birth_year= clamped to [0,120] else NaN.
Two faces at read time: =household_roster()= serves =Age= after R1's
=.round()= to Int64, while =roster_to_characteristics= (R4) is fed the
PRE-finalize frame from =_aggregate_wave_data= and therefore sees the
fractional value -- its infant test =age < 1= depends on that.  The
per-country Ethiopian-calendar conversion before =age_handler= is a country
derivation and belongs to that group's census.

** B3/B4/B5/B6 -- the canonical food_acquired reshape
- B3 is a difference of two raw fields plus a clip.  The total is
  recoverable by summing the two =s= rows of one (t,i,j,u) EXCEPT where the
  clip fired (Produced > Quantity), where the served purchased quantity is 0
  and the negative residual is lost.
- B6 is the one wave-level aggregation the YAML path performs on
  food_acquired.  Its =sum= runs with pandas' default =min_count=0=, so a
  group whose Expenditure (or Produced) is entirely NaN is served as 0.0 --
  the exact "fabricated zero" =_normalize_dataframe_index= was changed to
  avoid (=min_count=1=, GH #323).  Reached only for the nine YAML-path
  food_acquired countries and only when no data_root parquet exists for
  the wave.
- B5 and B6 both pick a =Price= for duplicate rows, by different rules
  (mean vs first); B7/R13 then OVERWRITE it with Expenditure/Quantity after
  the additive sum.  See section 6.

** B7 -- Price re-derived after the additive collapse
=data_info.yml= (Columns > food_acquired > Price) says the market price is
"back-calculated in _finalize_result if not stored".  It is not: nothing in
=_finalize_result= touches =Price= (grep of =country.py= for ='Price'= finds
only :1741 and :5925-5953).  The re-derivation happens in
=_normalize_dataframe_index= (BUILD; the L2-country parquet is written
post-collapse) and in =Feature._collapse_duplicate_index= (READ), and only
when a =Price= column is ALREADY present and the group had duplicates.  A
doc/code mismatch worth fixing when the derivation registry is designed.

** B9 -- coalesce_coord_bin
The single transformer registered in =_DERIVED_TRANSFORMERS=.  It is an
imputation of a missing cluster id from a numeric rule (0.05-degree grid
centre of the modified GPS), applied at build time in Uganda 2009-10 to
=sample= and =cluster_features= so the two agree by construction.  The
brief excludes id construction, but this one manufactures the identifier
from a measurement, which is why it is recorded.  =apply_derived= is the
closest existing thing to a "named, registered, YAML-dispatched
derivation": stable string key -> callable, target column from the block
key, kwargs from YAML.

** B8/B12/B11 -- the collapse families
=groupby().first()= is a selection that, on disagreeing duplicates, keeps
the first NON-NULL per column independently and can therefore serve a row
that exists nowhere in the survey.  It runs at two sites -- Site 1 on any
non-unique declared index (B8) and Site 2 inside =Wave.cluster_features=,
which projects a household-grain frame onto =(t, v)= before Site 1 can see
it (B12).  Both are audited (=_audit_index_collapse=), warned, stamped
into the parquet and replayed, but the destroyed rows are not recoverable
from any served table -- only from the source file.  Site 2 is also where
the framework's last silent AGGREGATION lived: GPS was reduced with
=.mean()= (a cluster centroid) until 2026-07-13, when it was measured to be
a no-op in 4 of 5 cells and a 783-km average in the fifth; it is now
=.first()=-ed like every other column.
=reduce_to_agreed(on_conflict='na')= is the country-side alternative; it
blanks the disagreeing cells instead, and Uganda is the only live caller
that opts into blanking.

** R1 -- rounding
=_enforce_canonical_dtypes= rounds every canonical =int= column with pandas
=.round()= (banker's rounding: 2.5 -> 2, 3.5 -> 4) before the Int64 cast.
Applied on every read; the parquet keeps the fractional value, so the raw
is recoverable from the L2 parquet but not from the API.

** R2 -- weights
Scale-preserving for every ratio, scale-destroying for every total.  There
is no attrs key; the only signal is a warning when a wave's mean is
non-positive.  Recoverable from the parquet only.  =_join_v_from_sample=
re-enters =sample()= for every household table, so this runs many times per
session; idempotence is what makes that safe.

** R4 -- roster_to_characteristics
Six distinct rules (table row R4).  The MonthsAway -> months-present
conversion is exactly the brief's "categorical/duration re-expressed" case,
and the EHCVM binary =s01q12= -> 12/0 that feeds it is a COUNTRY derivation
upstream (CLAUDE.md).  Nothing on the served frame says which of the three
residence columns decided a household, or that a wave fell back to
count-everyone; the two =UserWarning= texts are the only disclosure.  The
raw roster is fully recoverable from =household_roster()= (modulo R1's
rounding of Age, which the bucket edges then see differently from the
fractional value used here).

** R5 -- food_expenditures: the framework's own 12B-class case
The sum runs over every level not in (t,i,j,s): =u= (fine, currency is
additive) AND =visit= (GhanaLSS: up to six 5-day asks, Burkina Faso 2014:
four quarterly passages) AND anything else a country left on the index.  A
GhanaLSS number is 30 days of coverage next to Ethiopia's 7, and the only
disclosure is =attrs['recall']=, which is (a) per (country, wave), never per
row; (b) carries =recall_days=None= wherever =within_wave_variation= is set
(nine cells in five countries, including GhanaLSS 1991-92 and 2005-06 and
Nigeria W4 -- exactly the cells that most need it); and (c) is dropped by a
multi-country =Feature()= call and never re-attached: =recall.merge_attrs=
exists but has NO caller (=grep merge_attrs lsms_library/*.py= finds only
the population one at feature.py:715).  The sibling table =food_prices= (R8)
collapses the same =visit= level with a MEDIAN.  The visit detail itself
survives in =food_acquired=, so the raw inputs are recoverable from the
served corpus, just not from the derived table.

** R6/R7 -- kilograms
Three things a per-row key cannot name on its own: the rung that served the
row (six values), the group statistic behind it (a (t,j) baseline of >= 5
rows, a (t,j,u) estimate of >= 5 reports, medianed across waves), and the
counterfactual tag =baseline_refused_spread=.  The library already answers
this with a =KgFactorSource= column plus partition counts in attrs -- but
only when the analyst calls =food_kg_factors= directly; the served
=food_quantities= is summed over rows and carries the counts only.  The
index VALUE =u='kg'= is itself a derived label: a row that says =kg= may be
a survey kilogram, a parsed "50 kg Bag", or a price-ratio inference, and the
served table does not say which.  =volume_as_mass=True= (1 L = 1 kg) is a
default assumption baked into the =metric= rung.  Zero quantities and zero
expenditures are treated as missing throughout (=replace(0, nan)= at
transformations.py:971, 2514, 2634, 3977) -- a corpus-wide "0 means
missing" convention nothing discloses per row.

** R8 -- food_prices
Four modes, four formulas, one column name.  The =kgprice= docstring and
CLAUDE.md both say "reported Price x kg_factor"; the code divides
(transformations.py:2770).  Division is right (currency per unit / kg per
unit = currency per kg); the disclosure is wrong.  =_drop_unpriceable=
deletes rows and discloses the tally in =attrs['price_rows_dropped']=; the
warning fires only above a 5% residual loss, with currency-denominated
(=u='Value'=) rows excluded from both numerator and denominator.

** R10 -- market=
Two things at once: a priority rule between two Region sources, and a row
deletion (=dropna(subset=['m'])=) with no warning and no attrs.  A household
whose region is unknown in both sources disappears from the returned frame
silently.  The cluster-level fallback itself is a =first= selection:
=_market_lookup= does =drop_duplicates(subset=['t','v'])= (country.py:2254)
on the concatenated wave-level =cluster_features=, so where a wave carries
duplicate =(t, v)= rows with different Region labels the first wins,
undisclosed.  R17 (=legacy_locality=) inherits the same rule.

** R11 -- numeraire=
A per-row as-of selection of the factor plus a division, with the wave's
nominal 1 January as the fallback date for the four countries with no
=interview_date= and for any household missing one.  =attrs['conversion']=
records the target and the source table but not which rows used the
fallback; the warning names only rows with NO factor.

** R14-R16 -- the ag transforms
Never served by =Country=; the analyst calls them.  They are the most
thoroughly disclosed derivations in the codebase (per-row =*Source=
column, partition counts in attrs, a screen that rejects but never clips,
disagreement audits) and are the pattern the design should copy.  The
nominal nitrogen shares (R16) are a categorical->number table that would
become a served derivation the day =Nitrogen_kg= is registered as a table.

* 4. The @build_transform registry, precisely

** What it is
=lsms_library/_build_registry.py= is a leaf module (imports nothing from the
package).  Its state is one dict:

: _BUILD_TRANSFORMS: dict[str, tuple[Callable, tuple]] = {}
:    key   = f"{fn.__module__}.{fn.__qualname__}"
:    value = (fn, tuple(tables or ()))      # () means "every table"

** The decorator
: def build_transform(*, tables=None):
:     def deco(fn):
:         _BUILD_TRANSFORMS[f"{fn.__module__}.{fn.__qualname__}"] = (fn, tuple(tables or ()))
:         return fn
:     return deco

It is a TAG, not a wrapper: =fn= is returned unchanged, so binding and call
semantics are byte-identical (=test_tags_do_not_wrap=).  It records the
callable's identity and an optional list of OUTPUT TABLE names it is scoped
to.  It records nothing else: no column, no index level, no raw inputs, no
docstring, no formula, no disclosure text.

** What is tagged today (9 entry points, pinned by
=test_entry_point_set_is_pinned=)
- =build_transforms.food_acquired_to_canonical= (tables=['food_acquired'])
- =build_transforms._finalize_canonical_food_acquired= (['food_acquired'])
- =build_transforms.fill_v_with_coord_bin= (all tables)
- =build_transforms.apply_derived= (all tables)
- =build_transforms.add_visit_level= (['food_acquired'])
- =local_tools.df_data_grabber= (all)
- =country.Wave.grab_data= (all)
- =country.Country._aggregate_wave_data= (all -- the orchestrator)
- =country._normalize_dataframe_index= (all; country.py:5782)

=reduce_to_agreed= / =collapse_to_cluster_grain= are deliberately NOT tagged
(an all-tables tag would fold them into every table's fingerprint); they
are versioned instead through the import-closure fold below.

** How the fingerprint walks it
=build_transforms_fingerprint(table)= (lru_cached):
1. seeds =parts= with =py=<major>.<minor>= (ast.dump format drifts);
2. for each registered =(fn, tables)= in sorted qualname order, skipping
   entries whose =tables= is non-empty and does not contain =table=,
   calls =_closure_parts(fn, seen)=;
3. =_closure_parts= unwraps (=inspect.unwrap=, so lru_cache wrappers
   resolve), skips already-seen qualnames, appends
   =qualname + "=" + _norm(fn)= where =_norm= is =ast.dump= of the
   dedented source with DOCSTRINGS STRIPPED (comments and docstrings never
   move the hash; only logic does), then for every name in
   =_all_co_names(fn.__code__)= (co_names recursed through nested code
   objects -- comprehensions, lambdas, inner defs):
   - skips dunders;
   - resolves via =getattr(module, name)=, else via the AST =ImportFrom=
     map (=_import_map=, which catches the function-level cycle-dodge
     imports), else via =_resolve_methods= (a =self.<method>= reference
     matched against the classes of the module -- properties unwrapped to
     =fget=);
   - a resolved callable that is ours, not in =_EXCLUDED_MODULES=
     ({data_access, paths}) and not in =_EXCLUDED_CALLABLES= is recursed;
   - a resolved constant of type dict/list/tuple/set/frozenset/str/int/
     float/bool (and not in =_EXCLUDED_CONSTANTS=, the three runtime
     ledgers) is serialised by =_ser= -- explicit type dispatch with an
     else-REJECT (=TypeError=), so no identity =0x= repr can leak; a
     callable held inside a constant container (e.g. the
     =_DERIVED_TRANSFORMERS= dict) is replaced by its qualname AND its
     closure is folded, so a registry dict is versioned by CODE;
4. sha256 of the sorted, de-duplicated parts joined on \x1f.

=framework_imports_fingerprint(paths)= is the second route: it parses every
=_/*.py= build module of a wave/country, resolves =from lsms_library.X
import name= and =import lsms_library.X as Y= + attribute uses, and folds
those callables' closures.  This is how out-of-process wave scripts (which
the in-process walk cannot reach) and the untagged grain helpers get
versioned.

** Where it is folded
- =Wave._input_hash(table)= (country.py:838-940): =schema=LSMS_CACHE_SCHEMA=
  (manual lever, =local_tools.py:1840=, currently 5), the wave's
  data_info.yml hash, the wave/mapping module hashes, wave =*.org= inputs,
  YAML-path DVC sidecar md5 per declared source (or script text + literal
  data refs for the script path), every =_/*= file with a
  =_BUILD_INPUT_SUFFIXES= suffix in wave and country dirs, then
  =fwimp=<wave closures>:<country closures>= and =btf=<fingerprint(table)>=.
- =Country._table_cache_hash(table, waves)= (country.py:3195-3268): every
  wave hash plus =ctbl= / =cmod= / =cmap= / =cscheme= / =cmake= file hashes,
  country build inputs and =*.org=, then =btf= and =fwimp= for the country
  =_/*.py= files.  Returns None when nothing is hashable so an
  unintrospectable table never regresses the fast path.

** What would carry over to a @derivation registry
- The tag-not-wrapper decorator shape, the module-level dict, the
  =registered_entry_points()= accessor and the pinned-set drift test.
- Memoisation on function object (=_source= / =_norm= lru_caches) and
  =clear_caches()= for tests.
- The closure walk itself, if the design wants each derivation's CODE
  versioned (a stored =Derivation= key whose implementation changed should
  be detectable): =_closure_parts= + =_ser= already produce a
  deterministic content hash per callable, docstrings excluded.
- The =_DERIVED_TRANSFORMERS= idiom in =build_transforms.py= is the closer
  prototype for the KEY: an explicit, stable string
  (='coalesce_coord_bin'=) mapped to a callable, dispatched from YAML with
  =target=<column>= and kwargs, and already code-versioned because =_ser=
  folds callables held in dicts.

** What would NOT carry over
- The key is =module.qualname=.  For cache invalidation that is right (a
  rename SHOULD invalidate); for a =Derivation= vocabulary that must stay
  stable inside stored parquets and documents it is wrong -- a refactor
  would silently rename every row's label.  The registry needs a declared
  stable name, with the qualname as an attribute.
- The registry records identity and table scope ONLY.  The design wants,
  per derivation: the served column or index value, the raw input fields
  (file.variable), a formula/description, a kind, and "a callable that
  retrieves the exact raw inputs".  None of that exists; the only
  raw-source enumeration in the codebase is
  =_collect_file_paths_from_block= / =scan_script_data_refs=
  (local_tools.py:757, :1910), which yield FILE PATHS for hashing, not
  columns.
- Scope is by output TABLE; a derivation registry needs at least
  (table, column-or-level), and R6 shows an index VALUE (=u='kg'=) as the
  derived thing.
- Read-path derivations must live in a DIFFERENT dict.  =_finalize_result=
  is in =_EXCLUDED_CALLABLES=, and
  =test_no_transformations_symbol_reaches_any_fingerprint= pins that no
  symbol of =transformations.py= reaches any build fingerprint.  Tagging
  =conversion_to_kgs= or =roster_to_characteristics= with =@build_transform=
  would fail that test and cold-rebuild the corpus.  Reuse the MECHANISM
  (decorator shape, walk, serialiser), not the =_BUILD_TRANSFORMS= dict.
- BUILD vs READ is the axis the existing registry was built to separate,
  and it is also what decides whether a per-row =Derivation= column can be
  stored at all: a column stamped at build time survives in the parquet
  (and changes the parquet's content, hence its hash, hence one cold
  rebuild); a read-time derivation must re-attach its label on every read
  the way =_finalize_result= re-attaches =attrs['population']= /
  =attrs['recall']=.  Two mechanisms, not one.
- Docstrings are stripped from the fingerprint on purpose.  A derivation
  registry that wants the docstring as its disclosure text needs to read
  it separately from the same function object -- compatible, but a
  separate concern.
- The registry has no per-row anything.  The closest existing per-row
  provenance is the =*Source= column pattern (=KgFactorSource=,
  =ValuationSource=) plus attrs partition counts -- built by hand inside
  each transform, not by the registry.

** What would not fit a per-row nullable =Derivation= column + registry
- Row DELETIONS (R8, R10, R12, B8's destroyed rows, groupby's NaN-key
  drop): there is no output row to carry the label.  Only attrs, warnings,
  or a stamped audit can disclose an absence.
- MANY-TO-ONE sums (R5 over u and visit; R6 over u; R14 over u and season;
  R9 over items): the "exact raw inputs" are a set of rows, so the
  retrieval callable must return rows, not fields, and one output row can
  mix rungs (R5b's docstring gives exactly this reason for not carrying
  =ValuationSource= on the summed frame).
- CHAINED rules on one value (B2's five, then R1; R7's six-rung ladder):
  a single key names one rule; the existing answer is a =*Source= column
  plus partition counts, i.e. a small vocabulary per column rather than a
  registry key per row.
- GROUP-PARAMETERISED rules (R2 divides by the wave mean; R7's factor is a
  (t,j) baseline of >= 5 rows medianed across waves; R5b's price is the
  finest geo cell with >= 10 purchases): the key names the rule, but the
  parameter is a statistic of OTHER rows, so "retrieve the raw inputs"
  means retrieving a cell, and the cell membership changes when a wave is
  added.
- INDEX-VALUE derivations (R6 =u='kg'=, B10 =visit=1=, B9 =v='@lat,lon'=):
  the derived thing is a key, not a column; a per-row column can describe
  it but the row's identity is what changed.
- BUILD vs READ: a =Derivation= column written at build time changes the
  parquet and its hash (one cold rebuild per registration) and cannot
  describe anything =_finalize_result= does afterwards; a read-time label
  must be re-attached on every read and survives neither =merge= with a
  disagreeing frame nor =Feature()='s concat unless explicitly merged --
  the same trap =attrs['recall']= is in today.
- A per-row NULLABLE column says "no derivation" for a copied value, but B1
  and the =0 -> missing= conventions alter values that are then
  indistinguishable from genuinely missing ones; the label would have to
  be attached to a NaN.
