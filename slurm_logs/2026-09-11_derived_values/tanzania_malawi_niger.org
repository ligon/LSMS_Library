* Per-derivation notes

** Tanzania

- D01-D03 (one chained rule on one value).  The served purchased / produced /
  gift quantity is the result of an ORDERED chain: 'none' / 'hakuna' -> 0;
  fillna(0); astype(int64) floor; * unit factor; 0 -> NaN; canonical keep
  rule (qty > 0 or exp > 0).  Baked assumptions: quantities are integers in
  the unit reported (false for 1.4% of rows), a litre of anything weighs a
  kilogram, and a zero is missing.  The raw quantity and the raw unit label
  are NOT recoverable from the served table: u is always 'kg' or 'piece',
  and the integer floor is lossy.  Recoverable only from the source .dta.
  The 'consumed' quantity (quant_ttl_consume) is truncated the same way and
  then dropped by food_acquired_to_canonical (tanzania.py:699-785).
  CONTENTS discloses the floor and the unit collapse with counts; it does not
  disclose hakuna -> 0 or the density-1 assumption as such.
- D04 unitvalue_purchase is computed on the truncated quantity (so it is
  overstated by the same 1.5x median on the affected rows) but is dropped
  before the canonical parquet; the framework's food_prices recomputes
  Expenditure / Quantity from the served (truncated) columns, so the
  overstatement re-enters there.  Out of this census's scope, noted for the
  other agent.
- D05 Quantity := 0 where 'not harvested'.  A zero harvest is served where
  the instrument recorded a reason, not a quantity; the reason code is not
  served.
- D06 sale attachment.  Sales are asked per crop; harvests per plot-crop.
  The single-plot gate makes the served Value_sold depend on OTHER rows of
  the same household (how many plots grow the crop).  Multi-plot crops are
  served with NA sales although the household reported them.  Raw sales are
  recoverable only from AG_SEC_5A/7A/7B.
- D08 recorded as an absence: the crop Quantity carries no guard at all,
  and CLAUDE.md's Site Q reports without altering.  The design question is
  whether 'reported, flagged, not altered' wants a Derivation key.
- D09-D11 plot_features.  Area is a two-candidate selection (GPS preferred)
  after a one-sided clamp on the GPS candidate only, then a unit change; the
  served Area does not say which candidate it came from (SelfReportedArea
  beside it lets a reader infer it when the two differ).  Owned / Certificate
  / Fallow fold several codes into booleans; the Certificate rule composes
  three raw fields and an ownership override.
- D14-D19 livestock and labor.  HeadCount and hired PersonDays / Wage are
  sums across DIFFERENT instrument cells (breed types; men / women / children
  x activities).  Wage is a total paid, not a daily rate -- the same column
  name is a mean daily rate in Malawi (D56) and a phase total in Niger (D77).
  Family PersonDays exists only for 2020-21: two waves of one country serve
  the same column with different content (present vs absent).
- D20 zeros are imputed from dummies: an hours cell left blank by a person
  who said 'no' is served as 0, and every person below working age is served
  with 0 hours and False dummies whether or not the module was asked.
- D21-D22 community_prices.  Price is a RATIO (price paid / quantity of the
  unit priced) -- the only one of the three countries that divides.  The
  .first() over label-lumped codes discards a majority of the alternative
  prices (93% of 2019-20 groups, 90% of 2020-21 groups hold more than one
  distinct price); the discarded prices are not recoverable from the served
  table.
- D24-D26 sample / cluster_features.  Rural := 'Rural' unless 'urban' means a
  blank urb_rur is served as Rural, not NA.  Undisclosed.
- D27 life_satisfaction: a household-grain table built from one person's
  answers; the selection rule (the HEAD) is in the docstring.  Other
  members' answers are recoverable only from the source .dta.
- D30 recorded as borderline: one categorical into two booleans is a decode,
  but the 'NEITHER' -> (False, False) branch is an encoding choice.
- D31-D33 dead / fallback.  data_scheme.yml registers food_expenditures /
  food_quantities / food_prices as !make, but Country._FOOD_DERIVED derives
  them from food_acquired first (country.py ~4534-4560: 'try deriving from
  food_acquired first before falling back'), and the scripts read columns
  (quant_*, value_*, unitvalue_purchase) that the canonical parquet does not
  carry.  The median-price 'consumed value' (D31) is the country's own
  version of food_expenditures and is what the brief asked to record; if it
  ever ran it would serve a valuation, not an expenditure.  finances.py is
  not registered at all.

** Malawi

- D34-D37 kilograms.  The served Quantity_kg is q * f(region, item, unit)
  where (a) region comes from the first character of case_id (D36) in
  2010-11 / 2013-14, (b) item is matched by difflib at cutoff 0.6 (a
  non-injective, per-label fuzzy match; unmatched labels get no factor),
  (c) duplicate matches are averaged (D35) in 2016-17 / 2019-20, and (d) the
  conversion source differs by wave (ihs3_conversions.csv vs
  ihs_foodconversion_factor_2020.dta).  The factor a row received is NOT
  recoverable from the served table; the raw quantity and unit code are
  (Quantity and u are served beside Quantity_kg), so the factor can be
  back-computed as Quantity_kg / Quantity, but not which table item it was
  matched to.  This is the case the dispatcher named (GH #854).
- D37 is a claim read from source, not a run: the grams regex multiplies by
  0.01 where 0.001 is the kg factor.  A maintainer can check with
  =grep -n "0.01" Malawi/_/malawi.py Malawi/*/_/food_acquired.py= and a
  one-line test of =_extract_kg_conversion(pd.Series(['300 grams']))=.  In
  the four IHS3+ waves the value is routed through =x[c] or f= (malawi.py:206
  and the two inline copies), where =f= is a DataFrame; the expression never
  yields the fallback for a NaN factor because NaN is truthy, so as written
  the bug is dead there.  In 2004-05 (=df[cfactor_col] = fallback=) it is live
  IF any decoded unit label matches =\d+\s*g=; that census could not be run.
- D38 metric labels served as kg at density 1 (litre -> kg) with u
  overwritten: same lossy shape as Tanzania D02.
- D41-D44 plot_features: same GPS-preferred selection as Tanzania with two
  clamps (2500 acres on GPS, 1000 ha on the estimate) and a unit-code switch
  on the estimate.  The estimate's code 4 ('other') -> NA silently.
- D46 sale attachment is the Tanzania D06 rule with a second gate (one
  harvest ROW as well as one plot), and CONTENTS documents that the sold unit
  differs from the harvest unit on 22.2% of 2010-11 sale rows; a served
  Value_sold beside a u it is not measured in is the same defect as Niger
  D74.
- D50 months_food_inadequate: the served Months is a COUNT of marked cells
  in a 25-cell template (up to 25 marks possible, clipped to 12), forced to 0
  when the gate question is No.  The rule is documented; the individual
  month marks are not served.
- D56 Wage = mean of man / woman / child daily wages: a served 'Wage' that is
  the unweighted mean of up to three rates, not a rate anyone was paid.
  Documented in the docstring.  Not recoverable (the three cells are not
  served).
- D57-D58 people_last7days: farm hours are one cell in legacy waves and a
  sum of three cells in modern waves; wage hours are wage + ganyu (casual
  labour) summed in all waves; working_age is a template mark ('X') in
  legacy waves and an age threshold (5) in modern waves.  Two waves of one
  country derive the same column from different rules.
- D60-D61 FIES: the score counts Yes answers and treats a missing item as
  No unless all eight are missing; 2013-14 assigns items to concepts by
  content (hh_t15 -> HealthyDiet) whereas later waves use FAO order -- a
  documented cross-wave source difference on the same column.
- D62 2013-14 GPS: what the wave supplies is a per-household frame of
  EA-displaced coordinates of the CURRENT dwelling (tracked movers included);
  the derivation is the framework's collapse to cluster grain (.first() now;
  .mean() before 2026-07-13, which produced centroids of points up to 783 km
  apart).  Recorded here because the wave config is what puts a
  household-grain frame into a cluster table; the rule is framework-level.
- D64 the var-level concatenator keys on columns (quantity_consumed,
  'price per unit') absent from the canonical wave parquets; as written it
  cannot produce what the Makefile target promises.  Dead until rewritten.

** Niger

- D65-D66 MonthsSpent: a yes/no on 'lived here 6+ months' is served as 12
  or 0 months in the EHCVM waves while the two earlier waves serve the
  continuous months present.  A reader summing MonthsSpent across waves
  mixes a binary scaled to 12 with a count.  Disclosed in CONTENTS and
  CLAUDE.md.  The raw yes/no is recoverable (12 -> Oui, 0 -> Non) but not
  distinguishable from a genuine 12 or 0 in the earlier waves.
- D67 Age: a selection among (reported age, DOB-derived fractional age)
  made per row by age_handler, plus a date difference.  Which branch fired

** What would not fit a per-row nullable Derivation column + registry

- Several derived columns per row with different rules (plot_features:
  Area / Owned / Certificate / Fallow; people_last7days: three hours columns
  plus dummies; plot_labor: PersonDays and Wage).  One key per ROW cannot
  name per-column derivations; the column would need to be per (row, column)
  or the key would have to name a bundle.
- Ordered chains on one value (Tanzania Quantity: hakuna -> 0, fillna(0),
  floor, * factor, 0 -> NaN, keep rule).  A single key can name the chain
  as a whole, but the registry entry is then a pipeline, not a function of
  raw inputs, and the intermediate states are what a reader needs.
- Row-external selection (single-plot sale gate D06 / D46 / D73; HEAD
  reduction D27; .first() over label collisions D22; post-harvest passage
  D84; age_handler branch D67).  The served value depends on OTHER rows or
  on a per-row branch; a key names the rule but not the suppressed
  alternative, which is exactly what the 12B case needs recoverable.
- Per-row parameters from an external table (Malawi factor = f(region,
  fuzzy item, unit, wave source, mean-collapse)): the key would have to
  carry the matched table row, i.e. a payload, not a name.
- Index-value derivations (u := 'kg' D02 / D38; u := 'Unknown' D69; crop :=
  '(not crop-specific)' D70; condition := 'unknown_condition' D45): the
  derived thing is a KEY of the frame; a column keyed by that row describes
  the row's own index.
- A served value in a unit the frame does not carry (D74, D46 sale unit):
  the derivation is 'none' -- the number is raw -- and what is missing is a
  second unit column, not a derivation key.
- Dead / fallback code paths (D31-D33, D64): the registry should probably
  not name what is not served, but the data_scheme.yml registration says it
  is.
