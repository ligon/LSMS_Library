* Construction decisions by feature area (each tagged reported/imputed/aggregated, with .do:line)

- *PLOT AREAS* (=imputed=): "Plot area size = Parcel area size x (Plot area planted in parcel / Total plot area planted in parcel)" -- =Wave 7/README.md= PLOT AREAS description; code at =Wave 5/EPAR_UW_Uganda_UNPS_W5.do:320-391= (=*PLOT AREA=). A parcel-share allocation rule, not a measured plot area.
- *ALL PLOTS -- price-per-kg methodology* (=imputed=, cross-wave pooled): standardised sold/harvest quantities are converted to kg using a SEPARATE, pre-built =Nonstandard Unit Conversion Factors/UG_Conv_fact_{sold,harvest}_table{,_national}.dta= (median CF over ALL 7 available waves, regional then national fallback) -- built by =Master_Conversionfactor_table.do:32-298=; consumed at =Wave 5/EPAR_UW_Uganda_UNPS_W5.do:490-498= (sold) and =:519-529= (harvest). A per-crop, per-geography median sale price is then imputed onto every UNSOLD harvest observation using a broad-to-narrow ladder (=country -> region -> district -> county -> parish -> ea=, each level overriding the previous when it has *"> 9"* observations, i.e. >=10) at =Wave 5/...W5.do:531-540=. This is the same shape as our =median_price_valuation= ladder (crib: "WB EA -> admin -> national median ladder, >=10 obs") but EPAR pools the *conversion factors* across all 7 waves (we pool per country-wave, N>=5, per =transformations.harvest_kg=) and pools the *price* ladder narrow-overrides-broad in one pass rather than our EA-first cascade.
- *Area Harvested* (=imputed=, and admittedly so): "=gen ha_harvest=ha_planted= //no info on how much of the plot was harvested, so we assume the whole thing." -- =Wave 5/EPAR_UW_Uganda_UNPS_W5.do:625=; also stated in every wave's README point 8 ("Equivalent to area planted because the questionnaire does not include questions regarding the area harvested; included here for compatibility with indicators from other countries"). Manufactures a column our schema does not carry at all for Uganda.
- *GROSS CROP REVENUE* (=aggregated=, and silently re-derives the corrupted 2015-16 value): re-reads AGSEC5A/5B from scratch (=Wave 5/...W5.do:654-696=), rebuilds =value_sold= from raw =a5aq8=/=a5bq8= at line 656-657 with NO x100 correction and NO nulling, then at line 690 `replace value_harvest = value_sold if value_sold>value_harvest & value_sold!=.` -- so the uncorrected, ~100x-too-small 2015-16 sold value can still override (downward) an already-imputed harvest value inside the section the README calls clean. This is the exact mechanism the BRIEF's cautionary example describes (do-file lines cited there, 476-547, are the FIRST occurrence in the ALL PLOTS "Crop Values" block; the GROSS CROP REVENUE block at 654-696 is a SECOND, independent re-derivation with the same defect, not fixed by whatever masking the README implies happened upstream).
- *CROP EXPENSES / FARM LABOR* (=aggregated=): family + hired labor days combined across seasons at the plot level, =Wave 5/...W5.do:782-913= (FAMILY LABOR) and =:798-870= region for Wave 7 (HIRED LABOR at =Wave 7/...W7.do:798-869=, FAMILY LABOR =:870-960=).
- *FERTILIZER* (=reported=, with an explicit non-adjustment): N/P/K/Mixed categories only, liters treated as kg 1:1, no brand/analysis adjustment -- =Wave 5/README.md= USE OF INORGANIC FERTILIZER description (quoted in Cell 1); code at =Wave 5/...W5.do:962-1134=.
- *TLU* (=aggregated=): fixed species-level coefficients (kg-of-meat-equivalent based) applied to household animal counts -- =Wave 5/...W5.do:1509-1671=; coefficient TABLE itself is out of scope for this agent per the BRIEF (a separate agent covers factor tables).
- *LIVESTOCK INCOME* (=aggregated=): sums livestock sold-live + slaughtered-sold + products (milk, eggs) values, nets expenses (feed/vaccine/hired labor) -- =Wave 5/...W5.do:1671-2016=.
- *HOUSEHOLD IDS / WEIGHTS* (=imputed=, aggregated to external population totals): rescales the survey's own cross-sectional weight (=h_xwgt_W5= for 2015-16) to match WORLD BANK external population totals (national, then rural/urban split) via a raking-style adjustment `weight_pop_tot = weight * ${pop_tot} / (weighted HH-member total from the survey)` -- =Wave 5/...W5.do:284-320= (=*HOUSEHOLD SIZE= section, "Re-scaling survey weights to match population estimates"). This is a fundamentally different design from our =_normalise_sample_weights()= (divide by the wave's OWN mean, so weighted ratios/shares/means are invariant and =sum(weight)= is a wave's household count, not a population estimate -- crib + CLAUDE.md "Sampling Weights" section). EPAR's rescaled weight is a population-total estimator; ours is explicitly not.
- *HOUSEHOLD IDS -- weight variable choice, W5 specific* (documentation/code mismatch, not resolved either way): =Wave 5/README.md= HOUSEHOLD IDS "KNOWN ISSUES" claims "This section uses the panel weight rather than the crossectional weight which is only in gsec1. Accordingly the variable is named 'pweight'" -- but =Wave 5/EPAR_UW_Uganda_UNPS_W5.do:238= actually does `rename h_xwgt_W5 weight // using the crossectional weight that applies to all respondents`, naming the result =weight=, not =pweight=, and using the CROSS-SECTIONAL column. The comment in the code and the README's prose directly contradict each other; W7's corresponding README entry says "No issues in this section" (=Wave 7/README.md= HOUSEHOLD IDS). Reported as observed, not adjudicated -- this is an EPAR-internal inconsistency, not a claim about our own weight table.
- *LAND SIZE* (=aggregated=): total land size in hectares "including rented in and rented out plots" -- summed across parcels held, cultivated and agricultural-land subsets -- =Wave 5/README.md= LAND SIZE description; code banner =*FARM SIZE / LAND SIZE= at =Wave 5/EPAR_UW_Uganda_UNPS_W5.do:2166-2308=.
- *USE OF IMPROVED SEED* (=reported=): a binary improved-seed-use flag per priority crop, at household and individual (plot-manager) level -- =Wave 5/README.md= USE OF IMPROVED SEED description; code follows the =*SEEDS= banner at =Wave 5/EPAR_UW_Uganda_UNPS_W5.do:1187-1418=.
- *HOUSEHOLD'S DIET DIVERSITY SCORE* (=aggregated=): builds a Food Consumption Score (FCS) from =gsec15b.dta= (non-agriculture module) by mapping 16 item codes into 10 weighted food groups, capping days-eaten at 7, and summing weighted group-days into =fcs= with poor/borderline/acceptable cutoffs at 21 and 35 -- =Wave 5/EPAR_UW_Uganda_UNPS_W5.do:2866-2920= (=*HOUSEHOLD'S DIET DIVERSITY SCORE=); explicitly notes "No available data to construct rCSI module" at line 2868 (matches =Wave 5/README.md='s "The Reduced Coping Strategies Index (rCSI) was not calculated for the Uganda field survey"). Not our =food_acquired=-derived table; a different construction entirely (frequency-of-consumption based, not expenditure/quantity based).
- *Overall winsorization* (=imputed=, contradicts our crib's "no winsorization anywhere"): the household-level, individual-level and plot-level merge sections ("HOUSEHOLD VARIABLES", "PLOT VARIABLES") explicitly winsorize continuous variables at multiple thresholds -- =Wave 5/README.md=: "performs winsorization at different levels (i.e., top 1% level, top and bottom 1% level, top and bottom 5% level) for relevant continuous variables"; code sets `global wins_lower_thres 1` at =Wave 5/EPAR_UW_Uganda_UNPS_W5.do:200-202= and applies percentile clipping around line 4908 (`_pctile plot_value_harvest [aw=weight], p($wins_upper_thres)`).

* Ranked learnings (what we could take, why, what it would touch in our repo, and the risk)

1. *Strip the 2009-10 =99999= harvest-quantity sentinel.* EPAR already isolated exactly which column and exactly which value (=A5aq6a==99999=, =Wave 1/...W1.do:558=). Our own TODO (=ours: CONTENTS.org:2098-2102=) already names the defect but has no fix. Touches =ours: lsms_library/countries/Uganda/2009-10/_/= (wave-level colmap or a =drop:=/=derived:= rule in the YAML). Risk: low -- a single documented sentinel value, easy to test against the existing =tests/test_uganda_crop_condition.py= fixtures; the only care needed is not to also strip legitimate large quantities near but not equal to 99999.
2. *Wire the SOLD unit/condition, closing GH #824, using EPAR's merge keys as a template -- but audit the harvest-unit column choice first.* EPAR's =(crop_code, sold_unit_code, region)= merge pattern is a ready template for the sold-side factor our library lacks (crib: "the SOLD unit and SOLD condition are never wired," CONTENTS.org:2053-2096).
