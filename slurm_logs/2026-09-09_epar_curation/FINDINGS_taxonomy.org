- *How it differs in kind from the WB LSMS-ISA_Ag panel*
  (=slurm_logs/2026-06-13_wb_incidence_map/=): the WB panel is ONE
  already-harmonised cross-country table, built and maintained by the WB
  LSMS team itself, silently patching known survey-release defects (see
  the #829 case below). EPAR is a *per-country-wave* pipeline of ~120
  do-file sections each writing its own intermediate =.dta=, run and
  reviewed independently per wave (readme "CODING STATUS" per section), then
  collapsed to 3 final tables and a published summary-statistics workbook
  that is explicitly allowed to lag the code (README.md: "do files ... may
  not reflect the estimates published in the excel spreadsheet"). EPAR is
  closer in *shape* to our own per-wave build (one script per wave, one
  readme/CONTENTS.org-like doc per wave) than the WB panel is -- but EPAR
  bakes every aggregation into an intermediate =.dta= file, where our design
  keeps item-level parquets and pushes aggregation into
  =transformations.py= (CLAUDE.md "Derived Tables"). That single
  data-vs-code placement of the aggregation step is the central axis on
  which to read every finding below.

* EPAR construction methodology (=_Summary_statistics/EPAR_UW_335_SUMMARY_STATISTICS.do=)

- Rural-only by default: "The summary statistics are outputted only for the
  sub_population of households ... in rural areas ... modify the condition
  =if rural==1="
  (=EPAR_UW_335_SUMMARY_STATISTICS.do:21-24=). *aggregated/reported* --
  filter, not an imputation.
- Weights: =[aw=weight]= for tabstat means, =svy: mean= (survey-design,
  strata + PSU) for standard errors, one =[aw=...]= per weight TYPE listed
  above (=EPAR_UW_335_SUMMARY_STATISTICS.do:303,315,339,371=). *reported*
  weight application, standard survey-stats practice; matches our own
  weighted-ratio invariance design (CLAUDE.md "sample() and Cluster
  Identity") in spirit though not in the actual weight values (ours are
  wave-mean-normalised at API time; EPAR's are raw survey weights,
  re-scaled to WB population totals per wave --
  =EPAR_UW_Tanzania_NPS_W3.do:87-89=).
- *Winsorization is NOT in the summary-stats do-file* -- correcting one
  BRIEF assumption. It is computed per country-wave, inside each
  =EPAR_UW_{C}_W{N}.do=, before the final =HOUSEHOLD VARIABLES=/
  =PLOT VARIABLES= merges (readme.md:358, 370). Thresholds:
  =global wins_lower_thres 1= / =global wins_upper_thres 99=
  (=EPAR_UW_Tanzania_NPS_W3.do:82-83=), applied per-variable with =winsor2=,
  sometimes top-only, sometimes top+bottom, sometimes on the ratio AND its
  numerator/denominator separately (=EPAR_UW_Tanzania_NPS_W3.do:4475-4870=;
  full policy statement in the fetched estimates workbook's "General
  Construction Decisions" sheet, row "Outliers and Winsorizing" -- see
  below). Tag: *imputed* (values are REPLACED, not merely flagged) --
  exactly the construction CLAUDE.md's "No winsorization anywhere" rule
  forbids us from storing, and the recent =harvest_kg= plausibility screen
  (commit =0d3a4241=, "screen implausible reported factors; count, never
  clip") is our repo's explicit rejection of this EPAR pattern for the one
  place we came closest to needing it.
- *Priority crops*: a fixed 12-crop list -- "maize, rice, wheat, sorghum,
  pearl millet (or just millet), cowpea, groundnut, common bean, yam,
  sweet potato, cassava, banana" (=EPAR_UW_Tanzania_NPS_W3.do:94-113=,
  Tanzania's =topcropname_area= global; Uganda's own list is set in its
  own do-file header, referenced from readme.md:31-34). Drives which crops
  get their own monocrop/input/yield tables. *reported* selection (a
  curation choice, not a data transform) -- our =crop_production= carries
  every crop the survey asked about, so we have no analogous restriction to
  reconcile against; this is a place EPAR narrows and we don't.
- Gender-of-plot-decision-maker (=dm_gender=): built from up to 3 named
  decision-makers per plot, coded male-only/female-only/mixed, with an
  explicit household-head fallback when no decision-maker is recorded
  (=EPAR_UW_Tanzania_NPS_W3.do:264-273=, and again per-season at
  =:409-411=). Tag: *aggregated* (collapses 1-3 individual roster entries
  to one plot-season categorical). This construct underlies ~1,600 of the
  6,285 master-list rows (all the "Female/Male/Mixed plot managers" rows)
  and we have NO equivalent transform -- see Ranked Learnings #1.
- Smallholder / farm-size bins: see Indicator inventory above --
  =farm_size_0_0= / =_0_1= / =_1_2= / =_2_4= / =_4_more=
  (=EPAR_UW_Tanzania_NPS_W3.do:4284-4288=), built from summed plot area
  (their =farm_size_agland=). *aggregated* over item-level plot rows --
  directly analogous to our =farm_size= transform in
  =transformations.py=, no data-layer gap, a query-time bucketing we could
  trivially reproduce with =pd.cut= if ever needed.

  indicators, 138 (69%) are Household-grain, only 2 are Household-Plot and
  30 Individual (Indicator inventory, above). The household-grain file is
  itself the union of ~30 already-aggregated intermediate =.dta= files, so
  the aggregation is baked into the DATA LAYER at every step, not deferred
  to query time. This is the single structural point where our
  "aggregation in code, not data" rule (CLAUDE.md "Derived Tables",
  =_ROSTER_DERIVED=/=_FOOD_DERIVED=) diverges from EPAR's design: we would
  ship =crop_production=/=plot_inputs=/=plot_labor=/=livestock= at their
  item grain and let a =transformations.py= fn reconstruct
  =household_variables.dta='s columns on demand, never persisting the
  collapsed frame. Neither approach is wrong for EPAR's stated goal
  (a fixed, citable set of summary statistics); it is wrong for OUR goal
  (re-derivable, auditable item data) if we ever imported an EPAR
  intermediate =.dta= directly instead of reconstructing the same number
  from our own items.

** Ranked learnings (this follow-up)

1. *Build =plot_decision_makers (t, i, plot, pid, role)= as a new,
   fifth candidate feature for #439*, ahead of the deferred
   cross-country audit -- EPAR has already done the file-identification
   work in THREE countries (not just Cambodia), and the wiring cost is
   low per the previous section (columns already in an open file).
   Risk: medium -- the mixed/tie/head-fallback rule needs a documented
   =transformations.py= decision (adopt EPAR's mean-of-female rule, or
   design our own), and =role= (1st/2nd/3rd named decision-maker)
   should probably NOT be semantically load-bearing (EPAR's own
   =dm1_gender= "plot holder" vs =dm_gender= "any decision-maker"
   distinction shows role position carries some meaning that a flat
   =(plot,pid)= set would lose) -- keep =role= as an explicit column
   precisely to preserve that.
2. *=individual_assets= should be a NEW feature, not a =pid= retrofit
   onto =assets=.* =assets= is currently =(t,i,j)= household-item
   grain and is already populated for other countries; #439's
   =(t,i,j,pid)= owner-expansion grain is a different table, not a
   finer version of the same one. This pass's Ethiopia evidence
   (=women_{land,livestock,otherasset}_owner.dta=, one collapse-step
   from the target grain) is exactly the kind of real construction
   #439 asked the deferred audit to find -- it validates the design
   without needing Cambodia data access at all.
3. *EPAR's OWN CODE for Ethiopia ESS4 builds no fuller LSMS+ battery
   than Uganda's* -- Ethiopia's code reads only 2 of 5 rights and the
   readme states diet quality "cannot be constructed" there; whether
   the ESS4 INSTRUMENT itself asks more than EPAR's do-file reads is
   still open (see "Is any wave LSMS+ pilot" above -- not established
   either way without the questionnaire PDF). The #439 cross-country
   extension should budget for building =individual_assets=/
   =decision_making= against Ethiopia AND Uganda at REDUCED scope
   (fewer/thinner columns than Cambodia will support), and should not
   assume feature parity across countries once Cambodia validates the
   convention, but should also not assume the ISA panels' ceiling is
   fixed at what EPAR's code happens to read.
4. *EPAR's own two products disagree on the tie/missing rule -- pick
   and document ours, don't inherit either silently.* The 2017
   =358_Estimating-Crop-Yields= study uses an explicit categorical rule
   (all-male=1 / all-female=2 / else=mixed,
   =EPAR_UW_358_Tanzania TNPS 2012-13 LSMS-ISA_W3.do:133-135=); the
   current =335= main-code pipeline uses "mean share of named
   decision-makers who are female -> mixed if fractional; totally
   missing -> head's sex" in all three countries checked
   (=EPAR_UW_Tanzania_NPS_W3.do:263-265=,
   =EPAR_UW_Uganda_UNPS_W5.do:433-439=,
   =EPAR_UW_Ethiopia_ESS_W4.do:520-530=). The two rules are NOT
   guaranteed to agree in general (a categorical "all-male XOR
   all-female else mixed" test and a "mean share female" test partition
   the same raw ids differently whenever a plot has more than 2 named
   decision-makers with an uneven split), though this pass did not
   construct a minimal disagreeing example from real data. Whichever
   rule we pick for a
   =transformations.py= implementation, cite it as a documented,
   independent construction choice (#439 point 7's discipline), not as
   "the" EPAR rule -- there isn't one.

1. *Build a plot/season decision-maker-gender transform.* EPAR's =dm_gender=

   =plot_labor= today). Risk: medium -- if the decision-maker person-id

2. *Reconcile the median-price-valuation ladder against EPAR's Uganda
   conversion-factor table.* Our =median_price_valuation=
   (=transformations.py:2847-2884=, WB-parity, =threshold=10=, UNWEIGHTED

   =transformations.py:2847= (=median_price_valuation=) -- add an optional
   =weight_col= kwarg computing a weighted median (no core-collapse
   change, pure valuation-methodology parity). Risk: low -- purely
   additive kwarg, doesn't change default behavior.
