   =UPHI=) and this is *unresolved*, not a bug.  Relevant because EPAR's
   2008-15 wave scripts (W1-W4) are single-round and never see this --
   EPAR's coverage here is structurally different from ours (see Coverage).
2. *Extended vs. Refresh sub-panel split* (=CONTENTS.org:339-482=, panel
   design note =CONTENTS.org:1007-1038=, =.claude/skills/tanzania-panel-design.md=)

   follows the Refresh Panel *plus* a 545-household urban booster (Mbeya,
   Arusha, Mwanza, Tanga, Dodoma).  Zero household overlap between the two
   by design.  This is exactly EPAR's own W5/SDD split -- see Coverage §1.
3. *2008-15 multi-round folder* (=.claude/skills/multi-round-waves.md=) --
   one folder, four rounds via =wave_folder_map=; EPAR instead ships one
   =.do= file per round (W1-W4), so the "folder problem" does not exist on
   their side, but the *files-per-round* structure means EPAR duplicates
   ~5,000 lines of near-identical code four times (drift risk they carry
   that we do not).
4. *#835 -- =new_harmonize_units= integer-floor truncation*
   (=CONTENTS.org:1420-1448=) -- =astype(np.int64)= floors the reported
   quantity before the unit factor multiplies it; 852 rows lose their unit
   value outright and ~4,500 rows are inflated up to 1.9x.  Checked whether
   EPAR's own unit handling for crop/food quantities has an analogous
   floor -- see Construction decisions, Unit handling.
5. *#113 -- community-price <-> household link* (=CONTENTS.org:665-975=) --
   =community_prices.v= (=interview__key=) shares nothing with
   =sample().v=; the =community_cluster_xwalk= feature resolves 51/99
   (2019-20) and 458/488 (2020-21) communities to a real cluster via
   admin-code + interview-date matching.  Confirmed below that EPAR's own
   =.do= files never touch the community module at all (grep, zero hits).
6. *Three unlogged =food_acquired= idiosyncrasies from the price study*
   (=CONTENTS.org:1450-1512=, added 2026-09-08 per
   =slurm_logs/price_sources/Tanzania/REPORT.org:189-196=): (a) the stale
   #112 premise (quantities are present, not missing, in the current WB

   reads its =food_labels= build table out of =CONTENTS.org=, which the

7. *#846 -- not-asked capability verdict* (open_issues.tsv:6) -- NPS Section

* Construction decisions by feature area

** Household IDs / weights -- =reported= + =aggregated=

- EPAR renames the wave's native id/geo columns onto a common vocabulary
  per wave (=y5_crossweight -> weight=, comment "sdd = y5" marking the
  cross-wave rename convention; =...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:186-190=).
  =reported=.
- Weight *rescaling to external population totals* -- EPAR computes
  =weight_pop_tot=, =weight_pop_rur=, =weight_pop_urb=, then
  =weight_pop_rururb= by rescaling the survey weight so that
  =total hh_members [pweight=...]= matches WB population indicators
  (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:213-236=).  =imputed/aggregated=
  -- this is a genuinely different design from ours: our =sample()=
  normalises =weight=/=panel_weight= to within-wave mean 1 (CLAUDE.md,
  "Weights are normalised to within-wave mean 1 at API time"), which
  preserves ratios/shares/means but abandons any claim to a population
  total; EPAR's calibration preserves the population-total claim but ties
  every wave's weight to an external WB indicator that can itself be
  revised. Neither choice is "wrong"; they answer different questions
  (population totals vs. cross-wave-size-invariant ratios).

** Plot areas -- =reported= + =imputed=

- GPS-measured area preferred, farmer-estimated area as fallback --
  *matches our own priority order* (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:264-265=,
  =gen field_size = area_meas_hectares= then
  =replace field_size = area_est_hectares if field_size==.=; ours:
  =tanzania.py:1053=, "area_gps.where(area_gps.notna(), area_est)").
  =reported=, same choice both sides.
- Implausible-GPS-acreage handling *differs* -- see Cell 1 row 1 for the
  side-by-side comparison and citations.
- SDD (2019-20) carries *no* clamp or rescale code at all
  (=...SDD/EPAR_UW_Tanzania_NPS_SDD.do:264-280=) -- consistent with our
  own finding that the extreme-value defect is specific to the 2020-21
  GPS column, not general to the NPS instrument.

** Crop values / price-per-kg methodology ("ALL PLOTS") -- =reported= + =imputed= + =aggregated=

- *Sales price is a genuine reported unit value*: =price_kg =
  value_sold/quantity_sold= from the crop-sales module, no unit ambiguity
  because "CONVERT LOCAL UNITS INTO KILOGRAMS" is printed in the
  instrument (questionnaire quote reproduced in
  =slurm_logs/price_sources/Tanzania/REPORT.org:120-131=).  =reported=.
- *Unsold-harvest valuation is a five-rung median-price ladder*: computed
  per (region, district, ward, ea, hhid) weighted median of
  =price_kg=, with the FINEST rung carrying >=10 observations winning
  (=obs_`i'_kg >9=, loop =foreach i in country region district ward ea=
  applied in that coarse-to-fine order so the last, finest, qualifying
  assignment wins) -- =...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:387-414=.
  =imputed=.  This is methodologically very close to our own
  =median_price_valuation= (CLAUDE.md crib: "WB EA -> admin -> national
  median ladder, >=10 obs"), a genuine convergence on the same threshold
  and the same ladder shape, independently arrived at -- see Ranked
  learnings #3.
- *A third fallback layer we do not have*: where even the country median
  is unavailable, EPAR falls back to the survey's own direct valuation
  question (=replace value_harvest = ag4a_28 if value_harvest==.=,
  =...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:574-575=).  =reported= (this
  layer), stacked under two =imputed= layers above it.
- *Crop value is capped/overridden by observed sales*:
  =replace value_harvest_imputed = value_sold if value_sold>value_harvest_imputed...=
  (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:1088=, "155 changes here, suggests
  big gap between farmer estimated valuation and sales price"), and crop
  *losses* are separately capped so a household cannot report losing more
  value than it produced (=replace value_lost = value_crop_production if
  value_lost > value_crop_production=, =:1136=).  Both =imputed=.  We do
  not construct an analogous =value_crop_production= at all -- our
  =crop_production= table is REPORTED-only (Quantity, Quantity_sold,
  Value_sold, optional =KgFactor=); we never impute a value for the
  unsold portion of harvest, and we found no plausibility screen on the
  raw =Quantity= column either (Cell 3 row 1).
- *Tree-crop / intercrop area allocation* is a long chain of heuristics
  with EPAR's own admitted uncertainty in the comments ("some are
  implausibly huge... I tried estimating stand densities based on the
  estimated crop areas, but the ranges are huge",
  =...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:512-514=).  =imputed=, and openly
  fragile by EPAR's own account. We do not attempt an equivalent
  area-splitting construction; =plot_features.Area= is the whole-plot
  GPS/farmer-estimate area, with no intercrop apportionment.
- *Crop-code aggregation*: beans and cowpeas are merged into one code 931
  ("Beans-Cowpeas") in (at least) three places
  (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:386,1072,1130=). =aggregated=.
  Our =crop_production= keeps the survey's native crop codes (via
  =harmonize_crop=) and does not merge categories at the item level.

** Crop expenses -- =reported= + =imputed=

- Hired labor cost: =wages= summed directly from the wage columns
  (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:656-659=). =reported=.
- Family labor DAYS are reported (=labor_family=, FARM LABOR section
  below) but *never assigned an implicit wage*: the comment at
  =:651= states plainly that this is a "substantial" omission because
  family labor was ~90% of all plot labor days in the prior wave.  This
  matches our own design -- our =plot_labor= carries =PersonDays=/=Wage=
  per =source= (family/hired), and family-labor =Wage= is not populated
  either (we do not impute a shadow wage), so both sides leave the same
  gap, for what appear to be independent reasons (EPAR: no data to base
  an implicit cost on; us: design philosophy against imputing values into
  a REPORTED item table).
- Fertilizer nutrient decomposition (N/P/K per kg from fertilizer type)
  uses a hardcoded composition table (DAP 18-46-0, urea 46-0-0, NPK

** Household diet diversity / food security -- entirely absent from our schema

Three distinct indices are built from three different modules, none of
which we construct at all:
- *HDDS* (household dietary diversity score): 12 food groups from 7-day
  consumption (=hh_sec_j1.dta=), household consumes a group if any member
  does (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:2538-2560=). =aggregated=
  (count of food groups).  Contains the comment/code mismatch noted under
  Cell 2 ("EPAR pipeline observation").
- *FCS* (Food Consumption Score, WFP standard weights 2/3/1/4/1/4/0.5/0.5
  by food group) from a *different* consumption-frequency module
  (=hh_sec_j3.dta=, =:2569-2589=). =aggregated=.
- *rCSI* (reduced Coping Strategies Index) from a food-security-behavior
  module (=hh_sec_h.dta=, =:2599-2612=), a weighted sum of five coping

None of HDDS/FCS/rCSI has an equivalent in our =data_info.yml= schema;
=food_acquired= carries the raw acquisition rows these are built from, but
we do not derive any diversity/security index from them (see Ranked
learnings #2).

** Unit handling -- three different strategies for the same class of problem

Three distinct EPAR-side responses to "the unit reported for a quantity
doesn't match the unit needed to price it" were found in this pass, and
none of them matches our own #835 floor:
1. *Floor before scale* -- not found in EPAR's crop path (crop quantities
   are reported natively in kg per the instrument; Cell 3 row 2). This is
   our own =new_harmonize_units= behaviour (=astype(np.int64)= before the
   unit-factor multiply, CONTENTS.org:1420-1448), not EPAR's.
2. *Typo-correction rescale* -- fertilizer/pesticide quantities reported
   as an implausibly small number in what looks like the wrong unit are
   divided by 1,000 and re-flagged to the smaller unit code
   (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:672-675=, "Assuming instances of
   very small amounts are typos").  =imputed=.
3. *Silent drop-to-missing on unit mismatch* -- the Household-Consumption-
   Data project's own-production/gift valuation requires an EXACT match
   between the household's own purchase unit and its production/gift unit
   at *every* rung of the median-price ladder:
   =gen food_`f'_value=food_`f'_qty*price_unit if food_`f'_unit==food_purch_unit=
   (=Household-Consumption-Data/Tanzania_W5_Food Consumption by source.do:341=),
   repeated with the identical =food_`f'_unit==food_purch_unit= guard at
   every ladder rung (=:348,354,360,366,372=).  A household that bought
   maize in "kg" but received a gift of maize in "tins" gets no imputed
   value at any rung, for that observation -- permanently, silently, with
   no count of how many rows this affects anywhere in the script.
   =imputed= (or rather, its silent failure mode).  This is a third
   strategy distinct from both a floor and a typo-rescale, found only in
   the separate consumption project, not in the main Ag-indicators =.do=.

* Ranked learnings

1. **Own-consumption valuation via a median-price ladder (Household-
   Consumption-Data project) is directly relevant to #846/#113, and we
   should read it before finalizing the not-asked verdict.**  EPAR's
   *separate* consumption-by-source project (=Household-Consumption-Data/Tanzania_W5_Food Consumption by source.do:278-372=)
   imputes an own-production/gift consumption *value* from the household's
   own purchase-based unit price, falling back through the identical
   ea/ward/district/region/country >=10-obs ladder used everywhere else in
   EPAR's pipeline (subject to the unit-mismatch silent failure noted
   under Unit handling #3).  This does not contradict a =not-asked=
   verdict for the raw *price* field (Section J genuinely asks no price
   question for q5/q6 -- =slurm_logs/price_sources/Tanzania/REPORT.org:79-108=)
   -- EPAR needed to impute precisely because nothing was asked.  What it
   shows is that a *comparable, query-time-only* median-price valuation is
   already plausible for Tanzania own-consumption using machinery we
   already have (=median_price_valuation=), if the maintainer ever wants
   a value estimate rather than leaving =food_expenditures(basis='total')='s
   own-production component valueless.  Touches: nothing forced --
   =median_price_valuation= already exists; this is a "the demand exists,
   the machinery exists, nobody has wired the two together for Tanzania's
   own-production leg" observation.  Risk: LOW to read/decide, MEDIUM if
   implemented, because it is squarely an =imputed= construction that must
   never be baked into a parquet, and doing it wrong (e.g., picking the
   wrong obs-count threshold, or inheriting EPAR's unit-mismatch silent
   drop) would misrepresent Tanzania relative to countries where a real
   own-consumption price exists.
2. **HDDS / FCS / rCSI are constructions we do not have, built from modules
   (=hh_sec_j1=, =hh_sec_j3=, =hh_sec_h=) that overlap =food_acquired='s
   source files.**  If dietary-diversity or food-security indicators are
   ever wanted cross-country, EPAR's exact group mapping
   (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:2538-2560=) is a usable starting
   point *after* fixing the comment/code mismatch we found (Cell 2, EPAR
   pipeline observation) -- do not copy the =recode= ranges verbatim
   without re-deriving them from the item codes.  Touches: a new transform
   in =transformations.py=, no change to any item table.  Risk: MEDIUM --
   requires deciding what our own equivalent food-group taxonomy is (we
   have =harmonize_food=/=food_items.org=, not a 12-group HDDS mapping),
   and the module (=hh_sec_h= for rCSI) does not exist in our
   =data_info.yml= schema for Tanzania at all.
3. **The 5-rung geographic median-price ladder EPAR uses (ea, ward,
   district, region, country, all >=10 obs) is a closer match to our own
   =median_price_valuation= (crib: "WB EA -> admin -> national ladder,
   >=10 obs") than either side seems to have noticed, and it recurs
   identically across crop valuation (=:387-414=), livestock products
   (=:1266-1301=) and own-consumption (=Household-Consumption-Data/...do:287-329=).**
   Worth a short cross-check that our threshold and rung order are the
   same as EPAR's (both use >=10, both go finest-available-with-enough-
   obs), since two independent teams converging on the same threshold
   three times over is modest evidence the threshold is reasonable, not
   merely a magic number on either side.  Touches: documentation only (a
   one-line note in =transformations.py= or the ledger citing this
   convergence). Risk: NONE -- read-only cross-check, no code change
   implied.
4. **EPAR's disabled/enabled area-clamp choice (rescale vs. null, at 1,000
   vs. 2,500 acres) supplies an independent diagnosis worth testing against
   our own outliers before treating our clamp threshold as final.**  EPAR
   believes some outliers are *unit* errors, not *decimal-position*
   errors ("reported in units other than acres",
   =...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:254=) -- a different theory from
   our own framing.  If our own plot-area outliers were re-examined,
   EPAR's "wrong unit" theory is a testable alternative hypothesis before
   deciding 2,500 acres is the last word.  Touches:
   =tanzania.py:1046-1054= only if the re-examination finds the
   alternative theory correct. Risk: LOW to check, MEDIUM to change (would
   alter =plot_features.Area= for an unknown number of rows).
5. **A plausibility screen on raw =crop_production.Quantity= is worth
   considering, and EPAR's own single hand-fix elsewhere in the identical
   instrument is the precedent, not a model to copy.**  Cell 3 row 1
   found unscreened Tanzania 2020-21 quantities up to 7.5M kg with no
   clamp anywhere in =crop_production_for_wave= (=tanzania.py:1163=).
   EPAR's approach -- a single hardcoded per-household string match
   (=...Wave 5/EPAR_UW_Tanzania_NPS_W5.do:578-579=) -- is exactly the kind
   of un-auditable, non-general fix our own "no winsorization anywhere,
   count never clip" discipline (CLAUDE.md, harvest_kg/#818/#842/#829)
   already rejects.  The learning is the *gap*, not EPAR's remedy: a
   =crop_production= plausibility *count* (report, don't clip, exactly as
   =harvest_kg='s =KgFactor= screen already does for a different column)
   would give visibility here without importing EPAR's ad hoc deletion
   pattern.  Touches: a new count-only screen alongside
   =crop_production_for_wave= or a query-time diagnostic in
   =transformations.py=; never a silent drop in the parquet.  Risk: LOW
   to add as a report-only count; MEDIUM if anyone is tempted to make it
   a clip.
