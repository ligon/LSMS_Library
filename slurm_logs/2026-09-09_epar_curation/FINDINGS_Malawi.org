* Construction decisions by feature area (tagged reported/imputed/aggregated, .do:line)

- *Panel key construction* (=imputed=, framework-level). =MWI Panel Assembly.do= (128 lines) walks IHS3(W1)->IHPS2013(W2)->IHS4(W3)->IHS5(W4) one hop at a time: for each wave =k>1=, it computes a within-parent split index/count (=y`k'_index=, =y`k'_sum=, lines 64-83) against the PRIOR wave's household id, then assembles a single global chained string key =case_id_aux= (e.g. =101010160009-101-000-000-000=, lines 94-118) that either inherits the parent's =case_id_aux= (first child) or mints a new suffix. Read via =pandas.read_stata= on =mwi_panel_ids.dta=: 45,838 rows (12,271 + 4,000 + 14,955 + 14,612 -- exactly our four waves' household counts from CONTENTS.org's Sampling Design table), 38,458 distinct =case_id_aux= chains, no duplicate =(case_id_aux, wave)= pairs (verified), 34,419 of the 38,458 chains appear in exactly ONE wave (the un-tracked IHS3 cross-section majority). -- Our analogue: =panel_ids= (=data_scheme.yml:54-57=, index =(t, i)=, column =previous_i=) is a purely LOCAL one-hop pointer to the raw id in the wave immediately before -- declared per-wave in YAML (=2013-14/_/data_info.yml:125= -> =case_id=; =2016-17/_/data_info.yml:243= -> =y2_hhid=; =2019-20/_/data_info.yml:231= -> =y3_hhid=; 2010-11 and 2004-05 have it present but commented out, i.e. no prior wave to point to). The framework's =id_walk= composes these hops transitively AT READ TIME rather than materializing one global synthetic key at build time. Functionally the same graph-walk, different locus: EPAR bakes a derived artifact once; we keep the one-hop edges declarative and let the API compose them, consistent with "harmonize the interface, not the data."
- *Household IDs / Weights -- population rescaling* (=imputed=). =EPAR_UW_Malawi_IHS_W1.do:438-505=: raw =hh_wgt= is rescaled to WB total-population estimates SEPARATELY for rural and urban strata (=weight_pop_rur=weight*pop_rur/[rural HH total]=, =weight_pop_urb= likewise, lines 485-491), then the two are row-summed and renamed to the wave's default =weight= (lines 499-505). Repeated with wave-specific WB population globals in W2-W4. -- We explicitly do NOT do this (top-level CLAUDE.md, "Weights are normalised to within-wave mean 1 at API time"): each weight column is divided by its own non-null wave mean, so =sum(weight)= is a household count, never a population estimate, and cross-wave pooling does not reflect relative wave population share. A =weights='expansion'= kwarg was considered and "deliberately not built."
- *ALL PLOTS / crop values -- conversion-factor merge key* (=imputed=). Every wave keys the nonstandard-unit-to-kg conversion merge on =(region, crop_code_long, unit, condition)= against =Nonstandard Unit Conversion Factors/MWI_IHS_cf.dta= (=W1.do:1326=, =W2.do:991=, =W3.do:1398=, =W4.do:1357=; Wave 4 additionally derives =condition= via a crop-keyed lookup =MWI_IHS_shell_unshelled.dta= when the survey doesn't state it, =W4.do:948-950=). A default =conversion=1= is applied when the unit is already coded "kilogram" and condition is shelled/N-A (=W1.do:1327=). -- Our region-keyed conversion machinery (=malawi.py:1-197=, =conversion_table_matching_global= in =local_tools.py:2520=) is wired ONLY into =food_acquired= (consumption Modules G/H) via each wave's =food_acquired.py= (region read directly from the household cover-page module, e.g. =2019-20/_/food_acquired.py:21-28=, licensed by top-level CLAUDE.md's "Malawi's region-specific unit factors" exception to the "don't read region at wave-script level" rule). =crop_production='s =_harvest_block=/=_sale_block= (=malawi.py:915-1030=) never applies ANY region-keyed conversion factor -- harvest/sale quantities are carried in their native reported unit with no kg conversion at all, by design (crop_production is a REPORTED-grain table; kg conversion is left to a caller via =transformations.harvest_kg=, which layers reported KgFactor -> survey median -> none, per the top-level CLAUDE.md crib).
- *ALL PLOTS / crop values -- price-per-kg methodology* (=imputed=). EPAR computes =price_unit = sold_value/sold_qty= and =price_kg = sold_value/sold_qty_kg= per household-crop-unit-condition cell (=W1.do:963-966=), then a five-level median ladder (ea/ta/district/region/country, >=10 obs, =W1.do:967-991, 1338-1348=) values BOTH the sold and the harvested (including never-sold) quantity, producing =value_harvest= and, summed, =value_crop_production= (=W1.do:1355-1499=). This is squarely the "median price ladder" imputation named in the brief's crib, and matches our own =transformations.median_price_valuation='s WB-derived design (cell 1 above) -- but we never apply it to Malawi crop_production as a derived table; it exists as generic machinery a caller must invoke explicitly.
- *GROSS CROP REVENUE* (=aggregated=+=imputed=). =value_crop_production= (imputed, per above) and =value_crop_sales= (REPORTED, summed) are combined into =proportion_cropvalue_sold = value_crop_sales/value_crop_production= per household (=W1.do:1492-1506=); crop losses are =value_lost = value_harvest * (percent_lost/100)= (=W1.do:1433=), i.e. losses are VALUED via the same imputed price, not reported directly. -- We store only REPORTED =Value_sold=/=Quantity_sold= in =crop_production=; no stored or derived "gross value of production" or "proportion sold" exists for any country.
- *CROP EXPENSES / labor* (=reported=, with a documented imputation gap). All four Malawi wave readmes state the SAME structural problem: the instrument never asks the NUMBER of hired laborers, so a reported wage cannot be disambiguated as per-laborer vs. per-crew (readme.md:109 W1, readme.md:109-110 W3 "we cannot use these values to impute the value of family or nonhired (exchange) labor", README.md:108 W4 explicitly "EPAR cannot construct the value of family labor or nonhired (AKA exchange) labor MWI Waves 1, 2, 3, and 4"). EPAR's median-imputation-of-hired-wage step is consequently COMMENTED OUT for Malawi (readme text, all waves). -- Our =plot_labor= table (=(t, i, plot, source, season)=, =PersonDays=/=Wage=) stores only what is REPORTED per source and never attempts to derive a per-laborer wage rate or impute family/exchange labor value for any Malawi wave -- so this whole EPAR-documented ambiguity does not arise for us, not because we solved it but because we never construct the derived figure it would poison.
- *TLU* (=aggregated=). * Ranked learnings (what we could take, why, what it would touch, and the risk)

1. *Add a =livestock_income()= mechanical/methodology transform* (Cell 2 #5). Why: it is a real, load-bearing gap -- we have zero equivalent and EPAR builds one from data we already carry the raw ingredients for (=livestock.HeadSold=, =ValuePerAnimal=, plus a median-price ladder identical in shape to =median_price_valuation=). What it would touch: a new function in =transformations.py=, same GAP-4 "mechanical reduction, never stored" pattern as =tlu()=/=livestock_engaged()=. Risk: LOW -- pure code addition, no schema/parquet change, and the design already has the precedent (=median_price_valuation=) to build on. Caveat: our =livestock.Value= is a REPORTED hypothetical per-head value (=ag_r04=, "if sold today"), not an observed transaction price like EPAR's =income_live_sales/number_sold= -- the two inputs are NOT interchangeable, so a straight port would silently change what the number means; this needs a design note, not a copy-paste.
2. *Add an =rcsi()= transform* (Cell 2 #7). Why: rCSI is a standard, well-known food-security index (WFP), cheap to add, and we already store every ingredient it needs (=food_coping='s five per-strategy day counts). What it would touch: one new =transformations.py= function, same shape as =tlu()=. Risk: LOW.
3. *Reconsider whether =crop_production=/=food_acquired='s free-text "other (specify)" unit and crop-name recovery should be shared, not consumption-only* (Cell 2 #2, #3). Why: EPAR's harvest-side recovery of vernacular/glued-magnitude "other (specify)" units and crop names recovers real rows we currently drop to NaN/exclude. What it would touch: extending =malawi.py='s =handling_unusual_units=/=_clean_freetext_unit=/=_metric_kg_factor= family (or a parallel harvest-specific version) into =_harvest_block=/=_sale_block=; would need the raw =unit_os=/=crop_code_os= columns wired into the wave scripts, which is new plumbing, not a rename. Risk: MEDIUM -- touches a =materialize: make= script-path table (crop_production), the exact class of change CLAUDE.md's "A script is a complication" section warns to scope carefully; needs a row-count-affected measurement before landing, the same discipline the 2026-09-08 sale-unit fix used.
4. *Do NOT adopt EPAR's population-rescaled weights* (Cell 2 #9). This is a learning about risk, stated as a non-adoption: EPAR's rescale ties every wave's weight sum to a single external WB population-total estimate per wave, re-introducing exactly the population-vs-sample-size conflation our normalise-to-mean-1 design was built to avoid (top-level CLAUDE.md's "Weights are normalised to within-wave mean 1" section states the corpus-wide motivation and cost explicitly). Recorded here so a future contributor does not "discover" EPAR's approach and propose porting it without re-deriving why we rejected the pattern.
5. *If/when a shelled/unshelled =condition= grain level is added to =crop_production=* (Cell 2 #1, cross-referenced in CONTENTS.org as "a schema change and out of scope" for the 2026-09-08 fix), EPAR's per-crop shelled/unshelled DEFAULTING rules (maize/rice default unshelled, tobacco default N/A, =W1.do:1305-1311=) are a concrete, already-battle-tested starting point for the default-assignment logic, not just the schema shape.
