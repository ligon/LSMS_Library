*Sentinel: deliberately NOT the same as =u=.*  An unmapped code becomes *NA*,
not ='Unknown'=.  The task asked whether this is consistent; the answer is
that it is a deliberate, documented asymmetry, and the reasoning holds --
=data_info.yml='s "must put =Unknown=, NOT a null" rule is explicitly scoped
to DECLARED INDEX LEVELS (a null index key is deleted by
=groupby(dropna=True)=), and these two are ordinary columns with no such
hazard.

Note (not a defect): the NA therefore conflates "no sold unit recorded" with
"a code was recorded but it is outside the 46-code scheme".  Measured, that
second class is *282 rows, 0.62% of the 45 275 sale rows* (worst: 2013-14 A
83, 2009-10 A 69, 2010-11 B 51).  =u= conflates the same two cases in the
other direction (both become ='Unknown'=), so neither column distinguishes
them; nobody can currently tell the two apart on either.  Worth a sentence in
CONTENTS.org, not a change.

** What this means, precisely

- The *column* is correct and the *wiring* is correct.  =Unit_sold= is the
  survey's reported answer to "in what unit was it sold", it is read from the
  right variable in every wave, and carrying it is strictly more information
  than not carrying it.  On the *96.1% of rows where the two labels agree*
  nothing changes and everything is fine.
- The *consumer rule as written is not supported by the data.*
  =data_info.yml= says, in capitals, "=Value_sold / Quantity_sold= is a price
  per ONE =Unit_sold= -- NEVER per =u=", and =data_scheme.yml= repeats it.
  On the 3.9% of rows where the two disagree -- exactly the rows the rule
  exists to govern -- =Unit_sold= is the better denominator *less than half
  the time* (44.2-44.5%, by two independent measures).
- The honest rule is: *agreement -> either label is fine; disagreement -> the
  ROW is suspect and neither label should be used to form a price without
  further evidence* (the reported =q7d=, where it exists, is that evidence).
  The disagreement is a data-quality FLAG, not an identification of which
  unit is right.
