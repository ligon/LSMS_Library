* Item 1 -- join semantics : CONCERN

Core mechanics are right.  Four sub-findings, one of which contradicts the
function's own error message.

** 1.1 Keys present in only one side -- as documented (PASS)

A key the table declares that =crop_production= lacks is DROPPED from the
join; a key the frame carries that the table lacks is ignored.  Verified on
all three frame shapes named in the brief.

** 1.2 A =condition=-keyed table on a frame WITHOUT =condition= -- silently applied (documented)

Ethiopia shape =(t,i,plot_id,j,u)=, table keyed =(j,u,condition)= with ONE
condition per =(j,u)=:

: [P1d] -> (['shipped'], [50.0], {... 'shipped': 1 ...})

The =shelled= factor is served to a frame that never said the harvest was
shelled.  Silent.  This IS documented (=_shipped_factor_lookup= docstring:
"where either lacks it, they join ignoring it"), and the *two*-condition case
is loud:

: [P1e] RAISED ValueError: shipped_factors is ambiguous on the join keys
:   ['j', 'u']: 1 duplicated key(s), e.g. [('maize', 'basket')].
:   ['condition'] could not be joined on because crop_production carries no
:   such level, which is what left the remaining keys ambiguous ...

So the refusal fires exactly when the dropped axis actually disagrees.  That
is a good design and the hint naming =['condition']= is excellent.  Recorded
here because a loader that filters its table to one condition before passing
it gets a national, condition-blind application with no signal at all.

** 1.3 A =region=-keyed table on a frame WITHOUT =region= -- the same, and this is the dangerous one (CONCERN)

: [P1c] -> (['shipped', 'shipped'], [50.0, 50.0],
:          {'reported': 0, 'shipped': 2, ...})

A table loaded for ONE region (Ethiopia's =Crop_CF= is crop x unit x region;
Malawi's IHS5 adds condition) applied to a frame the caller forgot to resolve
=region= onto goes NATIONAL, silently, at full precedence.  The caller is not
warned.  The docstring tells the caller to resolve =region= first and warns
that =cluster_features= spells it =Region=; nothing checks that they did.
The failure is asymmetric with 1.2: a multi-region table raises (duplicates),
a single-region table does not -- so the loader that is most careless (pulls
one region) is the one that gets no protection.

Suggestion (do not implement here): when =dropped= is non-empty AND any row
matched, emit a warning naming the dropped keys.  It costs nothing on the
correct path and converts the silent case into the loud one.

** 1.4 A table keyed on =j= alone -- accepted, contradicting the function's own error text (CONCERN)

=_shipped_factor_lookup='s "nothing joinable" error says the loader must key
"at minimum the unit 'u'".  Nothing enforces it:

: [P1a] -> (['shipped', 'inferred', 'none'], [50.0, 1.0, nan],
:          {... 'shipped': 1, 'shipped_implausible': 1 ...})

=('Maize', 50.0)= is served to the =basket= row at 50 kg/unit.  Two mitigations
happen to fire on the other two rows -- the screen rejects it on the =Kg= row,
the sentinel excludes it on the =Unknown= row -- but neither is the =u= key,
and a =sack= row would have taken 50 kg as happily as the basket.  Either
enforce =u in table_keys= or drop the "at minimum the unit 'u'" clause from
the message; as it stands the message states a rule the code does not have.

Note the Tanzania shape =(t,i,plot_id,j)= (no =u= at all) is NOT a hazard here:
=harvest_kg_factors= already raises upstream, in =_kg_factor_series= --

: [P1b] RAISED ValueError: expected a 'u' unit level or column

-- so ledger §4's worry ("a table with no =u= key at all would fabricate
weights for unit-less rows") is covered by a PRE-EXISTING guard, not by the
sentinel.  Worth correcting in the ledger, since the sentinel is credited with
protection it does not provide on that path.

* Item 4 -- ambiguity : PASS

- two rows, same key, different values -> raises, naming the keys (=[P1e]=, =[P1h]=)
- two rows, same key, IDENTICAL values -> ALSO raises (stricter than core's
  grain rule, deliberately):
  : [P4e] RAISED ValueError: ... 1 duplicated key(s), e.g. [('maize','basket')]
- same key at different =t= -> no raise, and each wave gets its own factor:
  : [P4a] -> [50.0, 40.0]
- NaN in a key column -> normalised to the private =_KEY_NA= sentinel on BOTH
  sides.  It matches NaN-for-NaN:
  : [P4c] frame condition=NaN, table condition=NaN -> src 'shipped', 50.0
  and two table rows NaN in the same key position are refused as duplicates,
  with the sentinel visible in the message:
  : [P4d] RAISED ... e.g. [('maize', 'basket', '\x00<NA>')]

The NaN-matches-NaN behaviour is defensible ("condition not applicable" on
both sides) but is NOT stated in any docstring.  Worth one sentence, because
=pd.merge='s null-matching is called out as a hazard in CLAUDE.md and a reader
who knows that rule will assume this join avoided it entirely; it did not, it
made it explicit and deterministic instead.

Also verified: a table keyed as plain COLUMNS rather than index levels works
(=[F]=), and extra non-join columns (=note=, =crop_code=) are ignored (=[G]=).
A raw =Crop_CF= file left with a =crop_code= column and a decoded =j= column
therefore joins on =j= and silently ignores =crop_code= -- correct, but it is
another way a mis-keyed table looks like a working one.

* Item 9 -- does =data_info.yml:555-557= license storing a shipped factor in =KgFactor=?

Read plainly, yes -- and the ledger's decision to keep it out is a design
preference, not something the note compels.  The note's operative sentences
are "REPORTED, NEVER CONSTRUCTED.  Only a number the survey (or a
survey-supplied conversion table) actually wrote down belongs in this column.
Nothing inferred goes here -- not a median over sibling rows, not a factor
from the library's unit tables."  The parenthetical is not decorative: it
names a second admissible SOURCE, and Ethiopia's =Crop_CF_Wave{2..5}= is
precisely "a survey-supplied conversion table" -- shipped by the WB alongside
the instrument.  What the note forbids is INFERENCE (a median, a library unit
table), and a lookup in the survey's own conversion table is not inference; it
is transcription with a join.  The "construction happens at read time" clause
that follows is subordinate to that -- it explains where the forbidden
inference lives, not that lookups are banned from the column.  So a future
Ethiopia loader could read line 555-557 as licence to bake =Crop_CF= into the
stored column and would not be misreading it.  The ledger's contrary argument
is a good one on the merits -- the de-duplication decision (crop 74 / unit 62,
4.34 vs 6.125) and the region join would become invisible inside a parquet,
and the =reported_vs_shipped= audit would be impossible because the shipped
value would have BECOME the reported one -- but those are auditability
arguments, not a reading of the text.  That is exactly why §6 Q2 asks for the
note to be tightened, and the tightening is worth doing BEFORE #852 lands,
since the note as written points a loader author the other way.
