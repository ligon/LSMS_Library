* Item 2 -- the =_qty_reported= pre-mask :: CONCERN

** First: what GH #861 actually requires

Read directly (=gh issue view 861=), because the FAIL/CONCERN label turns on it.
The issue's "What it must NOT do" section says, in full:

- "Never strip a large quantity that is merely near 99999 (99998, 100000) --
  target the literal sentinel value, not a range."
- "Never zero out or impute the stripped rows; *they become missing*, as both of
  EPAR's rules do."
- "Do NOT adopt EPAR's =A5aq11=-conditional form alone (=:483=) and stop there."

*Nowhere does #861 ask that the rows survive.*  "Do not drop rows" is the
commit message's own framing, not the issue's.  The issue's checklist -- exact-
value strip, per-season counts in =CONTENTS.org=, a test that the strip is
exact-value not a range, close the TODO with before/after, "A Uganda re-warm" --
is *satisfied in full* by this commit.  So the finding below is a CONCERN about a
mechanism that does nothing and a documented claim that is wrong, not a failure
to fix the issue.

pre-fix filter =q0.notna() | qsold.notna() | vsold.notna()=.  Confirmed
empirically against the real pre-fix module on all seven waves -- rows, household
counts, Quantity sums and the *entire index* are byte-identical in the six waves
that declare no sentinel:

** But the rows it saves are deleted one layer up

=Country._finalize_result= (=lsms_library/country.py:3014=) runs

: df = df.dropna(how='all')

described in its own comment as "the universal safety-net ... drop any row where
every non-index column is NaN".  A 2009-10 sentinel row has *all six* data
columns NaN: =Quantity= (just nulled), =Quantity_sold=, =Value_sold=,
=harvest_month= (2009-10 declares =month: None=), =KgFactor= (unwired for this
wave), =intercropped= (NaN for 2009-10 -- AGSEC4A is not joinable, per the
colmap's own comment).  So:

| layer                                       | 2009-10 rows | all-3-measures-null | households |
|---------------------------------------------+--------------+---------------------+------------|
| wave parquet / =crop_production_for_wave=    | 25,485       | 3,077               | 2,330      |
| L2-country =var/crop_production.parquet=     | 25,485       | 3,077               | 2,330      |
| =ll.Country('Uganda').crop_production()=     | *22,408*     | *0*                 | *2,323*    |

Attributed directly, not by subtraction -- re-running the warm build with
=logging.getLogger('lsms_library').setLevel(INFO)= prints the block's own line:

: INFO lsms_library.country: Uganda/crop_production: dropna(how='all') removed
:   3077 of 133683 rows (2.3%) -- every dropped row had NO non-index data at all

Corpus-wide: the country parquet is 133,683 rows, the API returns *130,606* --
the difference is exactly the 3,077.  The arithmetic closes with no residual
(25,485 - 3,077 = 22,408 delivered for 2009-10), which also proves *no other*
step -- the =v=-join, =id_walk=, the index normalisation -- drops a 2009-10 row.
That is what licenses the pre-fix comparison: the pre-fix parquet has *0*
all-null rows, so a pre-fix API read returned all 25,485 rows and 2,330
households.  *Seven households* (=1021001910=,
=1051000103=, =1133001911=, =3093000202=, =3103000808=, =3203002401=,
=4163000708=) appear in 2009-10 =crop_production= *only* through sentinel rows and
are therefore absent from the delivered table post-fix, where pre-fix they were
present (carrying a fake 99999 harvest).  The API =Quantity= null count for
2009-10 is *9* -- the pre-fix number -- because every newly-nulled row was
deleted.

Consequences to state plainly:

1. The commit message's "the row stays; only the value is nulled (GH #861)" and
   =CONTENTS.org='s "rows (both seasons) 25,485 (unchanged)" are true of the
   *parquet*, and false of what a user gets.  If #861 means "do not drop rows"
   at the API, *the issue is not fixed*.
2. =_qty_reported= is therefore *dead weight at the delivered layer*: deleting
   the whole mechanism would produce an identical API result.  Two cases, and
   they exhaust the possibilities: a de-dup group made *only* of sentinel rows
   is absent without the mechanism and all-NaN-then-deleted with it; a group
   mixing a sentinel row with a real one is unaffected either way, because
   =sum(min_count=1)= and =first()= skip NaN exactly as if the row were absent.
   (Reasoned, not run.)  The added complexity buys a difference only for someone
   reading the raw parquet.
3. The =dropna(how='all')= deletion is =logger.info=, not a warning -- invisible
   in a normal session.  This is the exact failure mode that comment itself
   warns about ("a *value* corruption upstream turns into a silent *deletion*").

Two ways out, both cheap, neither taken: (a) accept the deletion and say so --
then drop =_qty_reported= and correct the row-count claim; (b) if the rows must
survive, they need a non-null column (the row *is* a reported crop-on-plot
record), or a documented exemption from =dropna(how='all')=.

** The consistency argument, both sides, with numbers

/For keeping them/ (the fix's position): #861 says do not drop rows; a nulled
value is not a licence to delete a record; and =dropna(how='all')= is a
framework-level safety net whose deletions the library elsewhere treats as a
defect to be surfaced.

/For dropping them/ (the original filter's intent): the filter exists to delete
rows with *no reported measure*, and a sentinel row IS one.  The evidence says
these are blank rows: their raw unit code and condition code are NULL on 3,168
of 3,169 raw sentinel rows, and =Quantity_sold= / =Value_sold= / =KgFactor= are
null on *all* of them.  They carry nothing but a crop label.

And the delivered parquet is now internally inconsistent about them:

| wave    | rows kept with ALL 3 measures null | rows *deleted* by the filter (crop label, no measure at all) |
|---------+------------------------------------+--------------------------------------------------------------|
| 2009-10 | *3,077*                            | 907                                                          |
| 2010-11 | 0                                  | 2,235                                                        |
| 2011-12 | 0                                  | 2,466                                                        |
| 2013-14 | 0                                  | 3,535                                                        |
| 2015-16 | 0                                  | 0                                                            |
| 2018-19 | 0                                  | 0                                                            |
| 2019-20 | 0                                  | 10,475                                                       |

So *inside 2009-10*, a row whose quantity cell is blank is deleted (907 of them)
while a row whose quantity cell says "99999 = no information reported" is kept,
though the survey means the same thing by both.  And 2009-10 becomes the only
wave in the parquet carrying an all-measures-null row class.  Nothing in
=CONTENTS.org= records either asymmetry.  (At the API the asymmetry vanishes --
because =dropna(how='all')= deletes the kept class too.)

* Item 5 -- =Unknown= is a property of the sentinel rows, not of the wave :: PASS (off by one)

=CONTENTS.org='s "2009-10 ... no value labels at all; matched by code
distribution" refers to *Stata* value labels.  The library decodes the numeric
codes through =categorical_mapping.org=, so labels resolve fine and 2009-10 is
*not* a wave of unlabelled rows:

- non-sentinel 2009-10 rows: u = Plastic Basin (15 lts) 4,510; Sack (100 kgs)
  3,314; Kg 2,808; Unknown 2,562; Bunch (Medium) 1,580; ... (40+ labels);
  condition = fresh 7,593; dried_grain 6,499; unknown_condition 2,811; ...
- sentinel rows: u = *Unknown 3,096* + 1; condition = *unknown_condition 3,096* + 1.
- raw codes on sentinel rows: unit code notna *0 of 1,411* (season A) and
  *1 of 1,758* (season B); condition code likewise.

So the =Unknown= is caused by a NULL raw code on the sentinel rows themselves,
which corroborates the "these are blank rows" reading in item 2.

*Off by one*: one season-B sentinel row carries unit code 22 and condition code
45 -- =u='Plastic Basin (15 lts)'=, =condition='dried_grain'= -- i.e. an otherwise
fully-populated harvest record whose quantity is 99999.  The commit /
=CONTENTS.org= claim about =Quantity_sold= / =Value_sold= / =KgFactor= (0 / 0 / 0
non-null on sentinel rows) is *exactly true*; the implied "all of them are blank
Unknown rows" is true of 3,096 of 3,097.

* Item 8 -- pandas 3.0 :: PASS

- =qty.where(qty != qty_sentinel, np.nan)= -- =qty= is float64 out of
  =pd.to_numeric=; =np.nan= in a numeric float column is explicitly allowed.
  =NaN != 99999= is True, so existing NaNs are preserved.  =.where= returns a new
  object.
- No =inplace==; no chained assignment (=df[mask]['col']= form absent); no
  =fillna(method=...)=; no positional =series[0]=.
- =df = df[... | df['_qty_reported']]= is boolean-mask row selection on a numpy
  bool column (from =.notna()=), so the =|= cannot meet =pd.NA=.
- =df.drop(columns=['_qty_reported'])= is non-inplace and unconditional; the
  early return (=if not pieces:=) precedes any reference to the column, so an
  empty build raises no =KeyError=.

* Recommendation

*Mergeable as "closes #861"* -- every requirement the issue states is met, and
the strip is correct, exactly scoped and exactly measured.  Three corrections
should land with it:

1. *Item 2.*  Either delete the =_qty_reported= mechanism (it changes nothing a
   user sees) and say plainly that the sentinel rows are dropped at the API, or
   keep it and make it real (the rows need a non-null column, or an exemption
   from =_finalize_result='s =dropna(how='all')=).  Either way =CONTENTS.org='s
   "rows (both seasons) 25,485 -> 25,485 (unchanged)" must be corrected: the
   delivered 2009-10 table goes 25,485 -> *22,408* rows and 2,330 -> *2,323*
   households, and 7 named households leave =crop_production= entirely.
   If the mechanism is kept, add one assertion at the
   =ll.Country('Uganda').crop_production()= layer -- the current tests all sit at
   the wave layer, which is why this shipped green.
2. *Item 6.*  Say that the re-warm is *all 28 Uganda tables*, not
   =crop_production=.  (#861 does ask for "A Uganda re-warm"; the commit and
   =CONTENTS.org= do not size it.)
3. *Item 5.*  Record the one sentinel row that is a fully-populated harvest
   record (=u='Plastic Basin (15 lts)'=, =condition='dried_grain'=), so the
   "all 3,097 are blank Unknown rows" reading is not carried forward.

Worth one line in =CONTENTS.org= too: 20 index tuples read =Quantity= *0.0*
rather than NaN after the strip, because a sentinel row shared a de-dup group
with a real row reporting 0.  That is the pre-existing =sum(min_count=1)=
semantics, not an imputation -- but those 20 rows are non-null, so unlike the
other 3,077 they *do* reach the API.
