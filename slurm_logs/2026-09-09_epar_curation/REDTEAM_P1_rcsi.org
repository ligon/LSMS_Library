** Reproducing "40,152 vs 40,143, the 9 match the 22 dropped rows" -- PASS, arithmetic closes exactly

My first pass here only counted =distinct (t, i)= pairs that appear in
=food_coping= with at least one row (40,149) and concluded the brief's 40,152
didn't reproduce. That was wrong: a household that has its *entire* battery
dropped (all 5 rows NaN'd out) never appears in =food_coping= at all, so a
naive distinct-count of the table silently excludes it -- those households
are *inferred from arithmetic closure* (Module-H total minus distinct =i=
present), not directly observed in any table. The correct household universe
is Malawi's own Module-H count. Read =Malawi/_/CONTENTS.org:30-34= in full
(not just grepped): the GH #637 audit there reports, for
=food_coping_for_wave=, row counts 61,355 / 19,994 / 62,232 / 57,157, and, on
the next line, for =months_food_inadequate_for_wave=, group counts 12,271 /
4,000 / 12,447 / 11,434 -- with the document stating explicitly that the
latter is "precisely each wave's Module H household count."
=months_food_inadequate= is built from the same Module-H source but is not
subject to =food_coping='s per-strategy row-dropping, so its count is the
right denominator: total Module-H household-waves, before any
=food_coping=-specific loss. Comparing the two lines: short by 0 / 6 / 3 / 13
rows per wave -- exactly the "(6 / 3 / 13 rows)" the commit message cites as
design evidence.

Summing the household counts: 12,271 + 4,000 + 12,447 + 11,434 = *40,152* --
the brief's number, sourced from CONTENTS.org, not invented. Re-ran =rcsi()=
on warm Malawi =food_coping()= (200,738 rows total, matching 61,355+19,994+
62,232+57,157 exactly) and broke it down per wave:

| wave | Module-H HH (CONTENTS.org) | distinct i in food_coping (>=1 row) | zero-row HH (Module-H - distinct i) | incomplete-but-present HH | rcsi()-scored HH | rows dropped |
|---+---+---+---+---+---+---|
| 2010-11 | 12,271 | 12,271 | 0 | 0 | 12,271 | 0 |
| 2013-14 | 4,000 | 3,999 | 1 | 1 (4/5 strategies) | 3,998 | 6 |
| 2016-17 | 12,447 | 12,447 | 0 | 2 (one 4/5, one 3/5) | 12,445 | 3 |
| 2019-20 | 11,434 | 11,432 | 2 | 3 (each 4/5) | 11,429 | 13 |
| *total* | *40,152* | *40,149* | *3* | *6* | *40,143* | *22* |

Every column closes:

- =rcsi()= output row count is 40,143 in every wave (=out.reset_index().groupby('t').size()= = 12271 / 3998 / 12445 / 11429), matching the brief exactly.

So the brief's claim is fully reproducible and internally consistent with

* CONCERN (non-blocking): the "defensive, not expected to fire" branch does fire

=rcsi()='s comment at the =wide.groupby(level=group_by).first()= line
(=transformations.py=, just after the =unstack('Strategy')=) says: "food_coping's
canonical grain is exactly (t, i, Strategy), so this branch is not expected

=['i', 't', 'v'] != ['t', 'i']=, and the branch DOES execute on every
real-country call, not just synthetic frames with an explicit extra level.

It is harmless here, and this time actually measured rather than inferred
from the §2 reconciliation (which also grouped on =['t','i']= and so would
agree regardless of whether =v= varies): ran
=fc.reset_index().groupby(['t','i'])['v'].nunique().max()= directly on warm
Malawi =food_coping()= and got *1* -- =v= is functionally determined by
=(t, i)= (one cluster per household-wave) in this table, so =.first()= on the
=v= dimension is a genuine no-op here. But the comment overstates its own
rarity, and =groupby().first()= silently skips NA per column (per CLAUDE.md's
own warning about that method) -- if a future country's =food_coping= ever
carried an extra index level that is NOT functionally determined by =(t, i)=,
this branch would collapse it silently rather than raising. Worth updating
the comment (or adding a `v`-degenerate-check) in a follow-up, but not a
reason to block this PR.
