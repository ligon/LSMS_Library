** The issue's EHCVM hypothesis is FALSE, measured

#813 says the 81+8 French keys are "unreached because the EHCVM countries'
categorical mappings now translate before kinship".  They do not.  Harvested at
the =_expand_kinship= call site, every EHCVM country hands kinship the
instrument's own French (or Portuguese) label verbatim:

| country       | top labels reaching kinship                                          |
|---------------+----------------------------------------------------------------------|
| Senegal       | =Fils, Fille= 47,472; =Chef De Ménage= 14,276; =Conjoint ( E )= 11,861 |
| Mali          | =Fils, Fille= 98,262; =Chef De Ménage= 24,939                         |
| Burkina Faso  | =Fils ou fille= 36,541; =Chef de ménage= 21,037                       |
| Benin / Togo  | =Fils, Fille=; =Chef de ménage=; =Conjoint ( e )=                     |
| Guinea-Bissau | =Filho, Filha= 15,607; =Chefe do agregado familiar= 5,351 (Portuguese) |
| Niger, CIV    | a MIX -- English on the pre-EHCVM waves, French on 2018-19 onward      |

*The real reason is orthographic.*  Every EHCVM instrument spells a
both-genders code with a COMMA (=Fils, Fille=; =Père, Mère=; =Frère, sœur=;
=Petit fils, petite fille=).  The =d1a983f3= block guessed bare words and SLASH
pairs.  So the keys are not dead because of a deliberate design change -- they
are dead because nobody checked the instruments before writing 81 entries.
That is a *different disposition*: it argues for trimming on grounds of
"speculative and never validated", not "superseded by a translation layer".

The hypothesis IS true for exactly one key in the 130, and in a country the
issue does not mention: GhanaLSS translates =Househelp (Other Relative)= ->
=Servant= in its =categorical_mapping.org= before kinship (row 6).

* (b) GH #804 -- the Tajikistan 1999 codebook IS obtainable from here

*Answer: yes.*  =download/11687= is =tajbid.pdf=, titled *"Basic Information
Living Standards Survey in the Republic of Tajikistan (TLSS)"*, classified

*Caveat on the route.*  =data_access.get_data_file()= will NOT fetch it: that
chain is local -> DVCFileSystem -> =_find_stata_zip_url= (the survey's Stata
data zip), and a related-materials PDF is not in it.  The catalog id also does
not resolve through the JSON API -- =api/catalog/279= and
=api/catalog/study/279= both return =400 IDNO-NOT-FOUND= (279 is a numeric
=id=, not an =idno=).  The working route is the plain catalog download URL
above, with the API key in the =X-API-KEY= header; the related-materials page
(=/index.php/catalog/279/related-materials=, HTML) is where the download ids
and titles come from.  So #804 is *unblocked but needs a small acquisition
step*, not an existing library call.

The same page also lists =11676= = =HH012007-00.pdf=, the TLSS household
questionnaire already in =Tajikistan/1999/Documentation/= -- so the codebook
sits beside a document the repo already holds, which is corroboration that
=11687= is the right artefact.

* Carried forward from PR #951's verification (for any future normalisation)

1. *=str.title()= mangles apostrophes*: =Lodger's= -> =Lodger'S=, because
   =str.title= treats =’='= as a word boundary.  So the "title-cased spelling"
   of =Lodger/Lodger's relative= and =Servant or servant's relative= is a form
   no contributor would write.  That is an argument against =.title()= as the
   canonical form if option 2 (normalise at load) is ever taken up.
2. *The mid-word =Ñ= in the two Peru/Guatemala keys is a SOURCE artefact*, not
   something =.title()= produces: =Compañero.title()= and =CompaÑero.title()=
   both give =Compañero=.  Both existing keys (=Esposo (A) O CompaÑero (A)=,
   =CuÑado (A)=) carry an upstream ASCII-only case fold that left the non-ASCII
   byte alone, so the sane canonical spelling is not a key at all.  *Re-spell
   them, do not merely de-duplicate them* -- and note the served labels are
   Guatemala's =esposo (a) o compaÑero (a)= (5,554 people) and =cuÑado (a)=
   (126), so a re-spelling is a live data change, not a file edit.
