* Root cause

=lsms_library/country.py= (development, line 1931), in =Wave.grab_data='s
=dfs:= branch:

#+begin_src python
merge_on =list(set('t').union(data_info.get('merge_on')))#a list
#+end_src

Python randomises =str= hashing per process, so the order of that list is
drawn from =PYTHONHASHSEED= each time the interpreter starts.  For example,
={'t','v','i'}= iterates as =v,i,t= under seed 1 and as =t,i,v= under seed 3.
=pd.merge(..., how='outer')= sorts its result lexicographically by the keys in
the order given.  With two or more non-=t= keys, a process therefore wrote the
L2-wave parquet sorted either by cluster or by household id.  =t= is constant
inside one =dfs:= build, so it never matters.

The issue's "cold vs warm" and "re-seed vs earlier reads" pairs were two
processes with different seeds.  Builds under the same seed are
order-identical, whatever the backend or worker count:

| condition varied                             | result                                                         |
|----------------------------------------------+----------------------------------------------------------------|
| two cold builds, same random/fixed seed      | identical (Benin: A=B=seed1=seed12345)                          |
| =LSMS_BUILD_BACKEND=make= vs default         | differed once, but =make= under seed 3 = default under seed 3   |
| =PYTHONHASHSEED= 1 vs 3 (=[v, i]= flips)     | *differs* (table below)                                         |
| =LSMS_BUILD_WORKERS= 1 vs 2 (dev, seed 1)    | identical                                                       |
| =LSMS_BUILD_WORKERS= 1 vs 4 (branch, seeds 1/3) | identical                                                    |

* Fix

#+begin_src python
merge_on = list(dict.fromkeys(['t', *data_info.get('merge_on')]))
#+end_src

The keys are =t=, then the declared =merge_on= order.  For the EHCVM rosters
(=merge_on: [v, i]=, =final_index: [v, i, pid]=) the rows are therefore ordered by
the index prefix =(t, v, i)=, with ties in member-file order.  This is not a
blanket sort, so a =dfs:= block that was already deterministic keeps its order.

* Which blocks can depend on key order (census of all 90 =dfs:= blocks)

- 14 blocks are =outer= with >= 2 non-=t= keys, in 10 =(country, table)= cells:
  =household_roster= for Benin, Burkina_Faso (x2), CotedIvoire, Guinea-Bissau,
  Mali (x2), Niger (x2), Senegal (x2) and Togo; Nigeria 2012-13 =assets=
  (=[i, j]=); and Serbia 2007 =sample= (=[opstina, popkrug]=).
- 70 blocks have one non-=t= key.  Because =t= is constant, =(t,k)= and =(k,t)=
  sort identically.
- 6 blocks are GhanaSPS =merge_how: left=.  A left join preserves left order.
- No sub-df maps =t=, and every =merge_on= is a list.
