* Finding 0: the coverage baseline was stale, and it mattered

=.coder/coverage/latest.csv= is dated *2026-06-26*.  The grader fix =8dcd2bcb=
("Phase 0 -- fix the ruler") landed *2026-07-12*, i.e. *after* that snapshot,
and its own commit message records that 128 of the 138 =builds= cells in the
2026-06-26 snapshot were a *grading artefact* rather than a defect: the
per-wave =no_all_null_columns= check was firing on columns that are legitimately
absent in one wave's slice but populated country-wide.

Reading the committed snapshot therefore gave a materially wrong picture of

with the L1 DVC blob cache symlinked in so no blob is re-fetched) gives:

|---------+---------------------------------+------------------------------------|

| builds  |                              15 |                                  0 |
| dropped |                               3 |                                  3 |
| absent  |                              11 |                                 11 |

*All 15 =builds= cells were the artefact.  All 3 =dropped= cells are real* and

Cold snapshots are written to =ghana_cold_matrix.csv= (pre-fix) and

** Recommendation

Refresh =.coder/coverage/latest.csv=.  =refresh_status.json= claims a 30-day
interval and an expiry of 2026-12-26, but the snapshot is ~8 weeks old and
predates a grader change that altered how ~93% of the non-sane cells are

* Finding 1: a silent, empty categorical decode killed 3 waves (FIXED)

** The mechanism

=local_tools.get_categorical_mapping(tablename=X)= called *without* a
value-column keyword returns an *empty dict*.  It passes =idxvars='Code'= and
no myvars, so =df_data_grabber= drops the Label column and the subsequent
=.squeeze()= yields nothing.

Nothing raises.  Every lookup against the empty dict simply misses and returns
=pd.NA=, so the affected column comes out 100% null and the build reports
success.  This is the repo's own documented failure mode -- see the docstring
of =GhanaLSS/1991-92/_/mapping.py::_code_label_map=, written when the same bug
was fixed for that one wave.

** Blast radius, established by AST sweep, not grep

A line-based grep is *misleading* here, because most call sites are multi-line
and pass their value column on a continuation line.  Parsing every
=lsms_library/countries/**/*.py= with =ast= and inspecting the actual keyword
set of each =get_categorical_mapping= call gives:

| call sites                                             | count |
|--------------------------------------------------------+-------|
| total                                                  |    77 |
| pass a value column explicitly                         |     1 |
| pass one via the ~**{value: value}~ idiom              |    69 |
| *pass none -- return ~{}~ by construction*             | *7*   |

All 7 broken sites are GhanaLSS, in exactly three waves:

| file                          | lines      |
|-------------------------------+------------|
| =1987-88/_/mapping.py=        | 9, 41      |
| =1988-89/_/mapping.py=        | 9, 44      |
| =1998-99/_/mapping.py=        | 9, 10, 42  |

Those are *exactly* the three waves whose =cluster_features= graded =dropped=.

** Measured damage, before the fix, on a cold cache

| wave    | =cluster_features=                     | =household_roster= columns 100% null              |
|---------+----------------------------------------+---------------------------------------------------|
| 1987-88 | *0 rows*                               | Birthplace, Relationship, Generation, Distance, Affinity |
| 1988-89 | 14,924 rows, sole column 100% null     | same                                              |
| 1998-99 | 5,998 rows, both columns 100% null     | same                                              |

1987-88 returns *zero* rows because its =mapping.py::cluster_features= infers
the cluster's region from members' birth region and then groups by it --
=groupby()= drops the all-NA key, so every row disappears.

That is *56,817 people* (15,492 + 14,914 + 26,411) carrying no kinship data at
all.  =Generation=, =Distance= and =Affinity= are *required* columns for
=household_roster= in =lsms_library/data_info.yml=.

The underlying source data was fine throughout.  =SEC0A.DTA= carries =region=
(codes 1--10, 0 nulls) and =loc2= (1/2, 0 nulls) under exactly those names; the
=region= / =rural= / =relationship= org tables all exist and are correct.  Only
the decode was dead.

** The fix (commit =18b6ca51=)

Added =local_tools.code_label_map= -- a *new* helper, so it cannot change the
behaviour of any existing caller -- which passes the value column and keys the
result by *both* the string and the integer form of each numeric code.  The
dual keying matters: =df_data_grabber= stringifies the Code index via
=format_id=, while wave mapping functions variously look up with =int(value)=
or =str(value)=, and both historical bugs (#348, #377) were partly key-type
mismatches.  Then pointed the three waves at it.

*** A correction to an earlier draft of this file

An earlier draft claimed 1988-89 "lands exactly on the documented figure" of
170 and that 1987-88 was "2 short".  That over-claimed, and the reason is worth
recording because it is a vocabulary trap in this survey.

GLSS1's DDI overview says the realised sample was "something less than 200
sampling areas (specifically 178 in 1987-88 and 170 in 1988-89)".  But the
*same sentence* continues:

#+begin_quote
Each group of 16, 32 or 48 households within a sampling area is referred to as
a cluster in the GLSS data sets and in this document.
#+end_quote

So in GLSS terminology a *sampling area* is not a *cluster* -- a sampling area
may contain more than one cluster.  The observed households-per-cluster
distribution matches the quoted design (1987-88: min 10, median 16, max 48;
1988-89: min 14, median 16, max 47), i.e. mostly one "group of 16" per cluster.

The right statement is therefore: the recovered cluster counts (176, 170) are
*corroborated by, but not identical to*, GSS's realised sampling-area figures
(178, 170).  They are exactly the counts present in the source file.  Do not
cite 170 as an exact documentary match.

* Finding 2: 1988-89 was collapsing an arbitrary person's birthplace (FIXED)

Surfaced *by* the fix above, and only visible once the decode worked.

GLSS1 and GLSS2 have *no cluster-location variable*.  Both waves read
=cluster_features.Region= and =household_roster.Birthplace= from the *same*
source column, =Y01A.DAT:REGION= -- which is the *person's region of birth*,
not where the cluster is.  1987-88 handles this with an explicit heuristic in
=mapping.py::cluster_features=: infer the cluster's region as the modal birth
region among members under 12 (least likely to have migrated).

*1988-89 had no such function.*  Once its decode was revived, the framework
collapsed the person-grain frame with =groupby().first()= -- taking an
arbitrary person's birth region as the whole cluster's region.  The grain audit
caught it:

#+begin_quote
GhanaLSS/cluster_features/1988-89: declared index (t, v) is NOT UNIQUE.
Collapsing it with groupby().first() DESTROYED 14,559 of 14,924 rows whose
values DISAGREE (167 conflicting index tuples).
#+end_quote

167 of 170 clusters held members born in more than one region, so =.first()=
was very nearly always picking arbitrarily.

Ported the 1987-88 heuristic to 1988-89 (and added =Age: AGEY= to its
=cluster_features= myvars, which is why 1987-88's config pulls =Age= at all --
the heuristic filters on it, then drops it).  Result: 170 clusters, zero grain
warnings.

idiosyncrasy entry.

* Finding 3: GLSS4 relationship codes -- deliberately NOT fixed

The obvious "finish the job" move would have been to decode 1998-99's
=Relationship= through the same country-level table.  *That would have silently
corrupted the data.*

- GLSS4's =rel= (=SEC1.DTA=, variable label "Relationship to HH head") takes
  *nine* codes, 1--9.  Code 1 occurs exactly 5,998 times = the household count,
  so 1 = Head.
- The country-level =relationship= table has *fourteen* codes and explicitly
  cites *GLSS1*'s data dictionary (=catalog/2313/data-dictionary/F184?file_name=y01a=).
- GLSS1 and GLSS2 raw data *do* use codes 1--14 (verified: code 1 occurs 3,136
  and 3,192 times respectively = their household counts).  So the country table
  is right for them and almost certainly *wrong* for GLSS4.
- =SEC1.DTA= carries *no* embedded Stata value labels (=value_labels() == []=),
  so the GLSS4 list has to come off the questionnaire.

1998-99 =Relationship= is therefore left explicitly unmapped, with the reasoning
and the one-line re-enable recorded in the code.  A null column is honest; a
mis-labelled kinship column propagates into =Generation=/=Distance=/=Affinity=
and is not recoverable downstream.

Status: a dedicated agent is reading the GLSS4 questionnaire and data-entry
manual.  See =FINDINGS_glss4_relationship_codes.org=.

** The matrix could not see the biggest part of this defect

Worth stating on its own, because it bears on how much the coverage matrix can
be trusted as a defect detector.

*The 56,817 people missing all kinship data never showed up as a non-=sane=
cell.*  =household_roster= graded =sane= in all three affected waves both
before and after the fix.  The reason is the wave-slice exemption added by
=8dcd2bcb=: the per-wave =no_all_null_columns= check exempts any column that is
populated *somewhere* in the country, and =Relationship= /
=Generation= / =Distance= / =Affinity= are populated in the other four waves.

That exemption is *correct* -- it removed 128 false positives repo-wide, and
=coverage_matrix.py:576-586= says plainly that it "deliberately hides
wave-level column gaps from the sanity grade, because a sanity grade is the
wrong instrument for them."  But the consequence is worth internalising:

#+begin_quote
A =sane= cell does not mean the wave's columns are populated.  It means no
column is dead *country-wide*.  A required column can be 100% null in three of
seven waves and every cell still grades =sane=.
#+end_quote

The three =dropped= =cluster_features= cells were the only visible symptom of a
defect whose larger half was invisible.  Chasing that one thread is what
surfaced the rest.  There is no per-wave column-completeness readout in the
library today; GH #591 and #592 are inventories of two such gaps that were
caught by accident before the exemption landed.

* Follow-up worth proposing (NOT done here)

After this fix, *zero* bare =get_categorical_mapping(tablename=...)= callers
remain in the repo -- the AST sweep now finds 70 correct call sites and none
broken.  But the footgun itself is unchanged: the next person to call the bare
form still gets =\{\}= silently.

This is the *third* recurrence of the same failure in this one country, and the
repo's stated ethos is that a known-bad stays loud.  A small change --
=get_categorical_mapping= warns (or raises) when it is about to return an empty
mapping *because no value column was requested* -- would convert a silent
100%-null column into a loud error at the call site.

Deliberately *not* folded into this session's commits: it is a behaviour change
to a library function with 70 call sites across 15 countries, so it wants its
own PR, its own test, and a decision on warn-vs-raise.

* Addendum: GLSS4 region codes were WRONG, and this session's own fix activated it

Found while reading the GLSS4 questionnaire for the relationship codes, and
verified by reading the PDF directly rather than accepting the report.

=1998-99/_/categorical_mapping.org='s =region= table had codes *9 and 10
swapped*, and no code 11 at all.  The GLSS4 Household Questionnaire, PDF page
7, Section 1 column 10 ("In what region/country was (NAME) born?") reads:

: ... Northern ......8 | Upper West ....9 | Upper East ...10 | Foreign [11]

The repo table agreed with the questionnaire on codes 1--8 -- *including*
GLSS4's non-standard 4=Eastern, 5=Volta -- but reversed the two northern
regions, evidently by borrowing the country-level table's ordering.  GLSS3
(1991-92) has the same northern reversal and is already documented; GLSS4 was
not.

*This was latent while the decode was dead, and commit =18b6ca51= activated
it*: 2,056 people went from honest NA to wrongly-labelled Upper East <->
Upper West, and 260 foreign-born stayed NA because code 11 was missing.  Live
for about forty minutes.  Fixed in =f5e6b66c=.

Three independent lines agree on the corrected ordering:

1. the questionnaire (primary source, read directly);
2. cover-page counts -- 120 households under code 9 against 260 under code 10;
3. the 2000 census -- Upper East ~920k, Upper West ~576k, so the larger is
   code 10.

Birthplace null fraction: 0.0098 -> *0.0*.

*The lesson is not "check the region table".*  It is that reviving a dead
decode does not restore data -- it starts *trusting* a mapping table that
nobody has had reason to validate, possibly for years, because while the decode
was dead the table's contents could not be observed.  Any fix of this shape
should re-verify the table against a primary source, not just make it non-empty.

|    4 | Grandchild                                 | Grandchild         |

* Test status

Full suite at =f5e6b66c=: *2,402 passed, 77 skipped, 4 xfailed, 1 xpassed,
1 failed*.

The single failure is
=test_table_structure.py::...[CotedIvoire/cluster_features]= -- "declared
column 'Latitude' not found".  *Not caused by this work*, and confirmed by
running it against =master= (=ad4b9c1f=) in an isolated worktree, with the

workstation*.  The test reads a cached parquet.  Ours dates from 2026-07-21 and
has columns =['Region','Rural']=; a cold rebuild of the same table yields
=['Region','Rural','Latitude','Longitude']= (Latitude 34.8% null).

*That gap is worth a look on its own*: the cached parquet carries a
content-hash that grades it *fresh*, yet its content is degraded.  The likely
path is the GH #515 optional-sub-df fallback -- if the geo file could not be
fetched at build time, the sub-df is dropped with a warning and the parquet is
written *without* Latitude but *with* a valid hash.  A degraded build then
caches as though it were a good one, and no amount of hash checking will
re-derive it.  Filed here as an observation, not chased (CotedIvoire is out of
scope for this audit).
