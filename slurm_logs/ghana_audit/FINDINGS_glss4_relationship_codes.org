* Idiosyncrasies found in GhanaLSS/_/CONTENTS.org

Named, not merely "read":

1. *Every GLSS round is an independent cross-section.*  "Seven rounds span
   1987--2017.  Each round is designed as an independent nationally
   representative cross-section; there is no rotating panel or refreshment
   sample mechanism."  Consequence for this task: *there is no reason to
   expect code lists to be stable across rounds*, and the GLSS1 dictionary
   carries no authority over GLSS4.  (CONTENTS.org itself later flags this
   sentence as in tension with the GLSS1->GLSS2 panel evidence, but the
   cross-section framing holds for GLSS4.)

2. *GLSS4 codes have been hand-decoded from the questionnaire before, and the
   file says so.*  The =individual_education= section records for 1998-99:
   =SEC2A.DTA=, =s2aq2=, "hand-decoded (no embedded value labels)" -- in
   contrast to 2005-06 / 2012-13 / 2016-17, which carry "embedded value
   labels".  This is the direct precedent for the present task and it also
   established that *the GLSS4 household questionnaire has a usable text
   layer*.

3. *The GLSS1/GLSS2 questionnaires are scanned-image PDFs with no text
   layer*, which is why GLSS1/GLSS2 education is left unwired ("so the codes
   cannot be reliably decoded").  GLSS4 is *not* in that position -- verified
   here: its household questionnaire extracts as ASCII box-art with a full
   text layer.

4. *GLSS3 is the cautionary tale about guessing.*  "the correct file is not
   identifiable from the cached set, so it is left unwired rather than
   guessed."  The house norm is: leave it null rather than fabricate.

5. *The GH #348 silent-failure gotcha, recorded in the "Unit handling"
   section*: "=get_categorical_mapping(tablename='units')= was called with no
   value column, so =df_data_grabber= returned a column-less frame and the
   dict came back *empty* -- every code passed through".  This exact failure
   mode is reproduced and re-confirmed below, and it is what
   =code_label_map()= exists to prevent.

6. *GLSS4 sampling facts used as corroboration here*: cluster ids are =4xxx=;
   =sample= reads =SEC0A.DTA= with =i = [clust, nh]=; =Rural= is =loc2=
   (1=Urban, 2=Rural); GLSS1--GLSS4 carry no expansion weights.

7. *Documentation-provenance discipline.*  The "Sampling universe" section
   insists on "Verbatim or nothing", "Nothing is inferred from the data",
   "Gaps are recorded as gaps", and declares an explicit ASCII exception for
   verbatim transcription.  This file follows those rules, including declaring
   its one character substitution.

* Why the country-level 14-code table is wrong here, and what it would cost

The country-level =relationship= table cites the *GLSS1* data dictionary
(catalog 2313, file =y01a=) and has 14 codes.  Overlaying it on GLSS4:

| Code | GLSS1 table (in repo) | GLSS4 truth (this file)                    | Agrees? | Rows |
|------+-----------------------+--------------------------------------------+---------+------|
|    1 | Head                  | Head                                       | yes     | 5998 |
|    2 | Spouse                | Wife/husband                               | yes     | 3375 |
|    3 | Child                 | Son/daughter                               | yes     | 12694 |
|    4 | Grandchild            | Grandchild                                 | yes     | 1979 |
|    5 | Parent                | Father/mother                              | yes     |  369 |
|    6 | Sibling               | Relative of head or head's spouse          | *NO*    | 1766 |
|    7 | Niece/nephew          | Servant and his/her relative               | *NO*    |   53 |
|    8 | Son/daughter in-law   | Tenant and his/her relative                | *NO*    |    6 |
|    9 | Brother/sister in-law | Other not related to head or head's spouse | *NO*    |  171 |

*This is the trap.*  Codes 1-5 coincide semantically, so a spot check of the
common categories looks perfect while codes 6-9 are silently wrong:
*1,996 of 26,411 person-rows (7.6%)*.

The errors are *kinship-significant*, not cosmetic, because
=_expand_kinship()= turns =Relationship= into =(Sex, Generation, Distance,
Affinity)=:

- code 7 is a *servant* but would be labelled "Niece/nephew" -- a
  *consanguineal* blood relative;
- code 9 is *explicitly not related to the head* but would be labelled
  "Brother/sister in-law" -- an *affinal* relative;
- code 6 is a *generic* "relative of head or head's spouse" but would be
  pinned to the specific tuple for "Sibling".

*Flag for whoever wires this (not acted on here):* the GLSS4 labels
"Relative of head or head's spouse", "Servant and his/her relative", "Tenant
and his/her relative" and "Other not related to head or head's spouse" are
unlikely to exist in =lsms_library/categorical_mapping/kinship.yml= and will
need entries (an unrecognized label only warns).  "Relative of head or head's
spouse" is genuinely underdetermined as a kinship tuple -- GLSS4 simply does
not resolve it -- and that should be represented honestly rather than guessed.

* Current behaviour at commit 18b6ca51 (verified, not assumed)

=Relationship= for GLSS4 is *100% NA today, by deliberate choice* -- the
mislabeling above is a *latent* risk, not a live defect.
=1998-99/_/mapping.py= sets =_relationship_dict = {}= behind a comment that
independently states the same conclusion this file reaches:

#+begin_quote
# GLSS4's `rel` (SEC1.DTA, label "Relationship to HH head") uses a NINE-code
# scheme (observed codes 1..9; code 1 occurs exactly 5998 times = the household
# count, so 1=Head).  The country-level `relationship` table in
# ../../_/categorical_mapping.org is the GLSS1 FOURTEEN-code scheme -- it cites

# use codes 1..14.  Decoding GLSS4 through it would silently MIS-LABEL kinship,

*This findings file supplies exactly what that comment asks for.*  Note the
comment's own instruction about placement: the table must go in the *wave*
directory, with the wave dir searched *first*, so lookup cannot fall through

=local_tools.get_categorical_mapping= returns on the *first* directory in
=dirs= that yields the table, and =1998-99/_/categorical_mapping.org= has *no*
=relationship= table at present, which is precisely why a fall-through to the
country-level GLSS1 table is the failure waiting to happen.

1. *Codes 9 and 10 are swapped.*  =Birthplace= currently mislabels *725* people

2. *Code 11 is silently dropped.*  =mapping.py='s =region_dict= is built with
   the *wave* dir first, and =1998-99/_/categorical_mapping.org='s =region=
   table stops at 10 -- it has no "Foreign Country" row (the *country*-level

about a documentation question, and GLSS4 allocation is demonstrably not
strictly proportional (the eight-region ratios themselves vary nearly
two-fold), so it is recorded as supporting evidence only.*

* Confidence statement

- *Codes 1-9 for =rel= in GLSS4 =SEC1.DTA=: HIGH confidence.*  Two independent
  primary documents shipped with the wave -- the administered instrument and
  the official code book -- give the identical 9-code list; the code book page
  names =SEC1.SSD= and states "Records: 26,411", which matches the file's row
  count exactly; the data contains exactly codes 1-9; and code 1 occurs
  exactly once per household.  Nothing was inferred from code frequencies, and
  no sibling wave (GLSS5/6/7) was used at any point.
- *The country-level 14-code table is wrong for GLSS4: HIGH confidence*, with
  the specific consequence quantified (codes 6-9; 1,996 rows; 7.6%).
- *=s1q10= disagrees with the repo =region= table on codes 9/10 and omits code
  11: HIGH confidence* -- both primary sources agree against the repo, and the
  0.0098 null fraction pins which table is in force.
- *Which region order is correct for the cover-page =REGION=: UNRESOLVED,
  LOW confidence either way.*  The code book contradicts itself across

- *Wording of code 6 and code 9 labels: HIGH confidence on meaning, and the
