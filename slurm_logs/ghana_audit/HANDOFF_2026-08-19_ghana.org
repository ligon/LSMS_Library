** 1. The =get_categorical_mapping= footgun is still armed

After this work, *zero* bare callers remain (AST sweep: 70 correct sites, 0

is requested, so the next caller gets the same 100%-null-column failure.  This

Proposed: make it warn or raise when it is about to return an empty mapping
*because no value column was requested*.  Small change plus a test, but it is a
behaviour change to a library function with 70 call sites across 15 countries,

* The methodological point worth carrying forward

Three times this session a *plausible, confidently-reported rule* was wrong in
a way that would have silently corrupted data, and each was caught only by
checking it directly against the source:

1. =(id1, id2, id3)= as GhanaSPS wave-1's cluster key -- splits EA 183, which
   spans two district codes, into two pseudo-clusters.
2. =FPrimary[3:6]= as waves 2/3's key -- shifts on the 37 ten-character ids in
   wave 3, inventing 2 EAs.  *Agrees with the correct rule on 2013-14*, so
   checking one wave would have passed.
3. The repo's own GLSS4 =region= table -- 9 and 10 swapped against the
   questionnaire.

And the general lesson from (3), which is the one most likely to recur:
*reviving a dead decode does not restore data -- it starts TRUSTING a mapping
table that nobody has had reason to validate, precisely because while the
decode was dead its contents could not be observed.*  This session's own fix
(=18b6ca51=) turned 2,056 people from honest NAs into wrongly-labelled Upper
East <-> Upper West, and it was live for about forty minutes.  Any fix of that
shape must re-verify the table against a primary source, not merely make it
non-empty.
