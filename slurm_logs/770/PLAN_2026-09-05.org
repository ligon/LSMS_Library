* What is actually wrong (corrected)
=conversion_to_kgs= infers a kg-per-unit factor for *every non-metric label that
carries an Expenditure*.  =Value= gets one for exactly the same reason =Heap=
(0.2268), =Bowl= (0.6048) and =Piece= (0.2041) do.

*My earlier causal claim was FALSE.*  I wrote that the factor is degenerate
"because =Quantity == Expenditure=".  It is not: in =conversion_to_kgs=,
=po= is the median *Expenditure*, and =Quantity= enters only through
=Kgs = Quantity x unit_conversion=, which is NaN for =Value=.  *The inferred
factor does not depend on =Quantity= at all* -- verified by holding Expenditure
fixed and scaling =Value=-row =Quantity= by 1x / 3x / 100x and by a constant
sentinel: the factor is =1.9= in every case.  GhanaLSS's =all= (142,997 rows)
and =none= (2,304 rows) escape only because their =Expenditure= is 100% null --
an accident, not a recognition.

What *does* depend on =Quantity == Expenditure= is the SYMPTOM: with it,
=food_prices(kgvalue) = Expenditure / (Expenditure x f) = 1/f= exactly.  That
link is real (GhanaLSS: =1/0.49139133 = 2.035038=, per-wave =std= 2.1e-17 in six
of seven waves).

* The diagnosis (EL's -- unchanged, and it survives)
=Value= is not a non-physical unit.  Value = Quantity x Price, so Value is
denominated in LCU, and Value / Price = Quantity: *prices are the units in which
value measures quantity*.  The kg factor for =Value= exists and equals
=1/price=.  The bug is a *granularity error* -- =conversion_to_kgs= returns one
factor PER UNIT LABEL, but =1/price= varies over =(j, t, m)=.  NaN is therefore
the honest INTERIM state, not a terminal verdict.

* Step 2: the price ladder (EL's rule, 2026-09-05)

** The rule
#+begin_quote
Price = Expenditure/Quantity | those being well-defined; otherwise look for
alternative price data.  (Also: the first formula is really for unit values,
isn't it?)
#+end_quote

Two things, and the second reframes the first.

** It IS a unit value, and the distinction is economic, not nominal
=Expenditure / Quantity= is a *unit value*, not a price.  The library already
encodes this in its mode names -- =kgvalue= / =unitvalue= are denominator-
explicit precisely so they are not mistaken for the survey's reported price
(=kgprice= / =unitprice=); see =AGENTS.md:372= on the deliberate departure from
the Deaton (1988, 1997) term-of-art.  What remains mis-named is the *method*:
=food_prices()= returns unit values by default.

Why it matters beyond naming: a unit value is expenditure over quantity *within
an item aggregate*, so it moves with quality choice and with measurement error
in the quantity.  A household buying better rice records a higher "price" that
is partly quality.  Community/market prices carry no such quality term.  So the
community source is *not merely a fallback for missing data* -- for demand
estimation it is arguably the cleaner instrument, and that is an argument for
=source== being an explicit, documented choice rather than a silent rescue.

** SUPERSEDED by =price_source== -- source is its OWN AXIS (EL, 2026-09-05)
#+begin_quote
Whether we're using individually reported prices (or really the median) or
community prices is a different axis than whether we're computing unit values
or kgvalues, etc.  I think we should add a price_source flag, with values
'hh', 'community', ..., and 'auto', the last being the default which stitches
things together as well as possible.
#+end_quote

My "row-level ladder" folded the fallback INTO =units==.  That crosses two
independent axes and is wrong:

| axis | kwarg | question it answers |
|------+-------+---------------------|
| basis | =units== | kg or native unit; value-derived or reported price |
| source | =price_source== | WHOSE report: =hh= (median of household reports), =community=, ..., =auto= |

They compose: a =kgvalue= can be computed from =hh= or from =community=.
Neither axis is a special case of the other.  =auto= is the default and
stitches as well as possible.

*** The grain problem -- this is the hard part, MEASURED
The two sources are not at the same grain:

| source | grain |
|--------+-------|
| =food_prices= today | =(t, v, i, j, u, s)= -- *household* (=data_info.yml:26=) |
| =community_prices= | market/community -- *no =i== |

=food_prices_from_acquired= already medians over =visit= (a sub-household
recall level), but it returns *per-household* rows.  So "individually reported
prices" are not yet prices in the usable sense -- EL's "(or really the median)"
names the missing step.  Stitching two sources requires a common grain, so
=price_source== forces the question =units== never had to ask:

1. *Median hh up to market grain.*  Economically the natural object -- a price
   at =(j, t, m)=, which is what Deaton-style demand work wants and what
   =community_prices= already is.  But it CHANGES THE SHAPE of =food_prices()=
   from household to market grain.
2. *Broadcast community down to household rows.*  Preserves today's shape and
   today's callers.  But a broadcast value repeated across households is NOT a
   measurement, and must be marked as such.

Not resolved here.  Note =m= is itself user-chosen (=_add_market_index()= fires
only when the caller passes =market='Region'=), so the join key for a community
price depends on a kwarg -- =price_source= and =market== interact.

*** INVARIANT for =auto=: fill, never override
=auto= must supply a price only where the higher-precedence source is absent,
and must never replace a well-defined =hh= value with a =community= one.  Then
the change is *additive*: every row today's callers get keeps the value it has
today, and previously-dropped rows appear.  (Recall =_drop_unpriceable= DROPS
unpriceable rows rather than returning NaN, so filling them is visible as a row
count rising, not as values moving.)  Without this invariant =auto= silently
rewrites existing numbers, which is not a default anyone can adopt safely.

*** This REVISES the constraint recorded in 11dd02c1
That commit said a fallback must be opt-in, reading =AGENTS.md:370= ("the
=*price= modes return NaN where the survey did not record a unit price; *no
silent fallback* to the =*value= modes").  With the axes separated, that
guarantee is about crossing *within =units==* -- value-derived vs
reported-price -- and it stays intact.  =auto= stitches along the *source*
axis, which the guarantee never covered, and EL has chosen it as the default.
The two are consistent.  What makes =auto= safe is not opt-in but the
fill-never-override invariant *plus* per-row provenance: with =auto= as the
default, the marker stops being a nicety and becomes the only way a caller can
tell what they were served.

** (superseded) The ladder was framed as ROW-level, not source-level
The earlier reading of "default to individual, fall over to community" was
source-level: pick one source per call.  EL's formulation is sharper -- the
condition is *well-definedness of Expenditure and Quantity*, which is a
property of a ROW, not of a country or a wave:

1. Expenditure and Quantity both well-defined -> unit value.
2. Otherwise -> alternative price data at the coarsest granularity that has it.

This closes the loop Step 1 deliberately left open.  Step 1 makes
=Quantity_kg= NaN for currency-denominated =u= (the factor is =1/price=, which
varies over =(j, t, m)= and no per-label constant can represent it), and its
own comment calls NaN "the honest INTERIM state ... recoverable per =(j, t, m)=
from a price source".  Step 2 IS that recovery: with a community price at
=(j, t, m)=, =Quantity = Value / Price= for exactly the rows Step 1 emptied.
The two steps are one mechanism split across two PRs, not a bug fix plus a
feature.

** REQUIREMENT: the output must say which rung it came from
A row-level ladder that returns one column silently mixes unit values and
reported prices.  That is the same disease as every other defect this repo has
had to dig out: =u='Value'= served as kilograms, the two incompatible weight
scales, the =.replace()= / =rename= pass-through of #782.  A number whose
provenance is unrecoverable is a number no one can audit.

So Step 2 must return provenance alongside the value -- an index level or a
companion column marking each row =unitvalue= / =community= (and, where the
survey reports one, =reported=).  *Do not* merge the two into an unmarked
=Price= column, however tempting the tidy shape is.  A caller doing demand
estimation has to be able to drop or instrument the unit-value rows; a caller
who cannot tell them apart is silently pooling a quality-contaminated
regressor with a clean one.

** Consequently, still open
- Granularity of the community source: =community_prices= is =(t, m, j)=-ish,
  =food_acquired= is household.  Joining a cluster/market price onto household
  rows is a broadcast, and a broadcast is not a measurement -- say so in the
  provenance marker.
** RESOLVED: no =unit_values()= sibling, and =units== is the vocabulary (EL)
#+begin_quote
food_prices already takes a units kwarg; we certainly don't need a unit_value
#+end_quote
=food_prices(units='unitvalue')= already *is* "give me unit values".  A second
method would be a second way to say the same thing.  The naming tension noted
above is therefore already resolved by the existing kwarg -- the method name is
the generic access point, =units== names the basis.  Dropped.

*The provenance marker must reuse that vocabulary*, not invent a parallel one:
a row is =unitvalue=-derived or =community=-derived, in the words =units==
already uses.

** CONSTRAINT this implies: the ladder MUST be opt-in
=units== has a documented guarantee (=AGENTS.md:370=): the =*price= modes
"return NaN where the survey did not record a unit price; *no silent fallback*
to the =*value= modes."  A row-level ladder IS a fallback.  So Step 2 must not
change what =units== alone returns -- the ladder is reached only by passing
=source==, and =food_prices(units='kgprice')= keeps returning NaN rather than
quietly borrowing a community price.  Otherwise Step 2 silently revokes a
promise the library currently makes, which is worse than the gap it fills.
- =NumberOfUnits=: =community_prices.Price= is the price of =NumberOfUnits=,
  not of one unit (measured: ratio 0.9946 with the division, 2.2917 without).
  Any join must divide first.
